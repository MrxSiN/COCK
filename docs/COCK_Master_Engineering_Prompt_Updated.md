# PART 1 — EIGHT-COMMAND BRAINFUCK WITH HUMAN-READABLE SOURCE

**The executable language remains exactly Brainfuck.** Readable comments and whitespace are source annotations, **not commands, macros or a ninth instruction**. The human-readable annotation grammar in Part 1 is normative for implementation; every source reader must enforce it in tests. It does not add an executable instruction.

- [ ] **Canonical authored `.bf` format:** every checked-in or manually authored `.bf` file MUST have a human-readable header describing purpose, input, output and tape cells; use blank lines, indentation, and explanatory comment lines for each nontrivial block. Keep code reasonably separated into small modules.
- [ ] **Eight real commands:** the only executable symbols are ASCII `+ - < > [ ] . ,`, with their ordinary Brainfuck meanings. The host does not execute any annotation text, alternative opcode, foreign script, macro, helper DSL, or embedded executable module.
- [ ] **Strict line-level annotation convention:** a comment occupies an entire line whose first non-whitespace character is `#`. The remainder of that line MUST be printable ASCII and MUST contain **none** of the eight BF command characters `+-<>[].,` (even inside words, examples or punctuation). A code line may contain the eight commands and ASCII spaces/tabs only; no inline comments. Empty lines and CRLF/LF line endings are allowed. Reject NUL, non-ASCII, forbidden control characters, or an unrecognized character on a code line.
- [ ] **Portable execution:** because comment-line characters contain no commands, a standards-style BF interpreter that ignores non-instruction bytes executes exactly the command stream visible on code lines. Source validation MUST enforce the convention before execution; a permissive third-party interpreter is not evidence that an invalid comment is safe.
- [ ] **No disguised instructions:** source comments may document algorithms and tape layouts but must not encode executable instructions or payload data to be reconstructed as hidden code; all production algorithms are authored in actual BF instructions. Production preprocessing, if used, is BF-authored, deterministic, and performs only approved lexical skipping and checking.
- [ ] **Original-offset source maps:** decode and bracket-match only real command positions; preserve original byte offsets for errors, traces and fuel. Annotations and whitespace consume zero guest instruction fuel and never become input/output bytes. Changed annotation text changes raw-source identity but not the filtered command stream; cache provenance binds both raw source and semantic stream where needed.
- [ ] **Empty-source exception:** exact empty source is a valid guest fixture to test execution semantics; the human-readable annotation requirement applies to authored tracked `.bf` implementation modules, not synthetic empty fixture bytes.
- [ ] **Minimal source contract:** a build may receive a raw legal byte-only BF snippet as an untracked *input fixture* if the calling interface explicitly supports raw source. Any `.bf` source file created/committed as a COCK implementation, test module or example must be annotated as above. The guest semantic stream is always the same eight-command language.
- [ ] **Pure repository-wide executable ownership:** every executable algorithm stored, generated as source, or maintained inside the repository is BF-authored, including the interpreter, compiler, tests, independent BF-based oracle, test launcher, debugger, byte router and build orchestration. Future linking/ELF, Android integration, packaging, hashing/signing and optimizer logic are BF-authored when implemented. No foreign-language executable files or embedded scripts may appear anywhere in the repository, even if labeled development-only.
- [ ] **Trust boundary:** a preinstalled **outside-repository** standards-only BF executor may launch the BF-in-BF seed; subsequent normal Stage A compiler execution runs within the BF-in-BF interpreter. Outside-repository OS/host facilities may perform *mechanical* open/read/write/close, exact byte-count/error reporting, byte transport and file operations as documented platform services. No foreign-language adapter **source or script** is committed, generated as executable source, or vendored into the repository. External tools may not choose compiler modules, parse build configuration, implement application behavior, compile/link production logic, create production manifest/APK, hash for production policy or sign releases on behalf of BF.
- [ ] **Development-only verification:** all checked-in validation, differential-oracle, fuzz-test, benchmarking and debugging **source code must be BF**, with no exception for tests. Existing externally installed independent disassemblers, Android platform tools and test systems may be *invoked* for inspection/verification and externally installed Android debug packaging/signing, without importing their source, wrappers, scripts or source-level logic into the repository. Their independently reported results remain independent evidence; BF-only tests alone cannot impersonate an independent native/device validator. External packaging/signing remains **DEBUG-ONLY** and cannot satisfy production purity/release gates.
- [ ] **Output distinction:** generated DEX, machine code, ELF, ZIP/APK, binary resources, certificates, assets and external platform APIs are not themselves constrained to eight command bytes. Every app-specific executable output must have documented BF-source provenance; external opaque executable templates are forbidden.
- [ ] **Repository contents:** annotated `.bf` is the **only executable source language for any purpose**; non-executable Markdown, literal JSON/source manifests, tabular test vectors, binary expected-output fixtures, image assets and generated binary artifacts may exist as inert data. Do not check in executable Makefile recipes, shell/PowerShell/batch scripts, notebooks, CI script blocks, foreign-language snippets intended for execution, bytecode masquerading as fixtures, code-generating configurations, third-party executable sources or generated foreign-language source. Documentation may list commands to invoke installed outside-repository tools but may not contain a second implementation.

**Annotated `.bf` style example — design illustration, not implemented source:**

```brainfuck
# MODULE emit A
# PURPOSE send ASCII letter A to output
# INPUT no bytes
# OUTPUT one byte
# TAPE cell zero stores the output value

+++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++.

# END output complete
```

The linked <https://github.com/MrxSiN/MrxSiN> is a **stylistic inspiration** for Brainfuck-first engineering, not a formal comment grammar. Use comment headings, blank lines and explained tape layouts everywhere BF source is authored. Do **not** insert `.` or `-` into comment prose; those are executable commands.

# PART 2 — LOCK THE BRAINFUCK EXECUTION PROFILE

Define `COCK` before building major modules. Specify eight-bit unsigned wrapping cells; zero-initialized logical tape; pointer initially at cell zero; right-growing, dynamically addressable logical tape; behavior on movement left of cell zero; binary-safe stdin/stdout; explicit and testable EOF semantics; deterministic nested loops; and precise errors on unavailable memory or other resource exhaustion.

The logical memory model must not have a small hardcoded maximum tape length. Grow physical storage as needed, subject to available resources and configured security budgets. An unavailable allocation must fail explicitly instead of corrupting data. Do not confuse theoretically unbounded memory with literally infinite device memory.

Define a versioned binary-framing format where components need structured input, multiple files, status messages, or errors. Normal byte values, including `0x00` and `0xFF`, must never be confused with control messages or EOF. The protocol is **data on standard Brainfuck I/O**, not a new instruction.

Implement compliance tests for wrapping, pointer boundaries, nested loops, EOF, binary bytes, large tape movement, invalid source, and deterministic errors. Freeze the semantics as a compatibility contract. **Part 2.2 fixes the normative COCK reference decisions; do not let implementation backends silently choose their own.**

### 2.1 — Logical resource limits versus physical exhaustion

Define a **logical resource contract** independently of a physical allocator: whether tape storage is committed on movement or on access, how newly addressed cells are initialized, how logical cell/address budgets are counted, and precisely which operation triggers a deterministic budget error. Document these decisions in `COCK` **before** enabling pointer/tape optimizations. The baseline interpreter and compiled execution must expose the same behavior under identical configured logical budgets; such budgets must be configurable and must not impose a universal small tape cap.

Treat **physical allocation failure** separately. Contiguous and segmented allocators, operating systems, execution hosts, and optimization modes can exhaust physical memory at different points. They must detect exhaustion, fail without corruption, and report the resource failure accurately, but COCK **must not falsely promise identical physical-OOM timing** across implementations. Do not suppress required logical tape-growth checks or deterministically specified failures when optimizing.

Test the following independently: left-of-zero movement; logical tape/address budget exhaustion; allocator failure injection; integer overflow in tape offsets; zero initialization after growth; equivalent output and failures under fixed logical budgets; safe cleanup and honest diagnostics under host-dependent physical exhaustion.

### 2.2 — Concrete `COCK` reference decisions

These are the normative **guest runtime** defaults; source admission is the annotated eight-command format in Part 1. The profile identifier is `COCK`. This is the first implementation contract and has not yet shipped; once released, any incompatible guest semantics change requires a separately identified profile and conformance suite. Implement and test these decisions during development.

- [ ] **Source bytes:** authored `.bf` accepts only BF command lines, legal blank/whitespace, and non-executing `#` comment lines conforming to Part 1. Decode a command stream consisting only of ASCII `+-<>[].,`; an empty command stream is valid. Reject forbidden bytes, unsafe annotations, malformed line forms and unmatched brackets before guest commands or output.
- [ ] **Cells and commands:** logical cells are unsigned bytes in `[0,255]`; `+` and `-` wrap modulo 256; `.` emits exactly the current byte; `,` consumes exactly one raw input byte when available.
- [ ] **EOF:** on a `,` with no byte remaining, write `0x00` to the current cell. Raw BF code cannot otherwise distinguish EOF from an actual zero byte; structured callers must use the separately specified length/status-bearing frame protocol, not a ninth instruction or forbidden sentinel byte.
- [ ] **Pointer and tape:** start at address 0; all logical cells initially read as zero. `<` at address 0 traps **before** changing pointer/state. The tape may grow rightward subject only to actual host resources and *configured*, explicit budgets.
- [ ] **Logical-address accounting:** reaching address `i` via `>` makes logical cells `0..i` addressable and zero-initialized. If a configured maximum addressable-cell count would be exceeded, trap **at that movement** before the pointer change. Physical backing may be allocated lazily, but it cannot change logical-address visibility or when a deterministic configured budget trap occurs. Use checked arithmetic for all address/length calculations.
- [ ] **Loops:** `[` checks the current cell and, if zero, resumes after the matching `]`; otherwise continues into its body. `]` checks the current cell and, if nonzero, resumes with the *first command after* its matching `[`; otherwise continues after `]`. Validate bracket pairing before execution.
- [ ] **Output/failure contract:** byte output must preserve order and exact values, including `0x00` and `0xFF`; malformed source and locked-profile traps report a defined error/status out of band from program output or through a specified caller protocol. Never misrepresent a partial output as a completed result.
- [ ] **Optional execution fuel:** if a deterministic guest instruction limit is configured, count each executed *original BF source command* (including evaluated brackets) in the defined reference trace; reject the command that would exceed the allowance before its effects. Fused/compiled operations must account for skipped interior commands and preserve the same observable cutoff, or use an unfused slow path near exhaustion. Distinguish guest fuel from host interpreter overhead and physical CPU timeouts.
- [ ] **Resource separation:** report deterministic *guest* logical-budget/fuel violations separately from unpredictable outer interpreter/tool-process OOM or OS termination. Conformance compares guest state, output, and logical errors under identical explicit budgets, not exact host-dependent physical OOM timing.
- [ ] **Conformance vectors:** cover `+`/`-` wrapping; exact empty source; legal LF/CRLF, indentation and inert `#` comments; comments that include forbidden `+`, `.` or brackets; random prose on code lines; NUL/UTF-8/BOM; unmatched brackets and original error offsets; `<>` at pointer zero; `><` at the last budgeted cell; newly zeroed cells; EOF versus binary zero; nested loops; interrupted optimized runs; original-command fuel cutoffs and resource failures.

An input frame's message length and EOF/status fields are **data**, not BF instruction semantics. For large data, use bounded, repeated frames rather than interpreting a per-frame length as a universal project or APK cap. Treat any proposed change to the profile as a compatibility-breaking design decision.

### 2.3 — Reference trace, failure ordering, and preflight fixtures

**This section makes Part 2.2 testable; it does not introduce a new Brainfuck instruction or alter `COCK` semantics.** The exact reference guest trace is the correctness oracle when debugging, differentiating implementations, and enforcing optional guest fuel. Optimized executors may compress or omit internal trace storage, but must reproduce the same guest-visible results and configured deterministic cutoffs.

- [ ] **Preflight before effects:** use Part 2.7's trusted complete-input boundary, then validate every source byte and all bracket pairs **before executing the first guest command or emitting guest output**. An invalid suffix (including unmatched brackets) must not leave earlier source-side effects. If complete source cannot fit in memory, use a bounded, spoolable validation/decoding strategy while preserving this order; a streamed source chunk is not automatically a complete valid program.
- [ ] **Trace record:** for independent tests, record `(source byte offset, original BF command, guest pointer before/after, touched cell before/after if any, logical high-watermark, input bytes consumed, output bytes emitted, guest-command count, guest status/error)`. Use checked counts and trace sampling or streamed records for very long runs.
- [ ] **Program counter:** identify each guest command by its *original source-byte offset*, not its fused IR index. In this locked profile, a nonzero `]` jumps to the **first command after** its partner `[`: it does not reexecute `[` merely to iterate. A zero-valued `[` skips its interior and matching `]` without charging fuel for skipped commands.
- [ ] **Fuel and trap priority:** when fuel is enabled, check whether the *next executed original command* fits the remaining allowance **before any effects of that command**. An admitted command consumes one guest-fuel unit even if its own boundary/budget check then traps; a command rejected for insufficient fuel consumes none. If it cannot, report the fuel violation without performing that command's pointer movement, I/O, or cell update. If fuel is available, process its ordinary checks and traps in reference order (e.g., a `<` at zero traps before moving; an overflowing `>` budget traps before moving). A fused operation must deoptimize or otherwise reconstruct precisely the same command boundary and resulting state at every tested cutoff.
- [ ] **Physical and transport failures:** distinguish malformed source, guest pointer/budget/fuel traps, host allocation failure, and underlying I/O failure. End-of-input is the documented `,`→`0x00` guest action; a host read error is **not** silently converted to EOF. Do not claim physical-OOM or external-I/O failure timing is universally deterministic across hosts.
- [ ] **Terminal-result record:** compare exact stdout bytes, count of consumed stdin bytes, guest pointer/cell state where available, logical high-watermark, executed guest-command count, completion/error kind, and error-producing source offset. Generated apps must preserve any externally observable partial-output and completion-status contract of their chosen application ABI.

**Small reference fixtures (all sources below contain only legal BF characters):**

| Guest source | Condition | Expected guest result |
| --- | --- | --- |
| `[]` | initial zero cell | Success, **1** executed command (`[` only) |
| `+[-]` | unlimited fuel | Success, cell 0 is zero, **4** executed commands |
| `++[-]` | unlimited fuel | Success, cell 0 is zero, **7** executed commands; `[` executes once |
| `+-` | fuel = 1 | Fuel trap before `-`; cell 0 remains `1`; never equivalent to an empty source under this budget |
| `<>` | default pointer 0 | Left-boundary trap on `<` |
| `><` | maximum logical cell count = 1 | Budget trap on first `>` (even though net movement is zero) |
| `,.` | empty stdin | Success, one emitted `0x00` byte; consumed stdin count `0` |
| `,.` | stdin is one `0x00` byte | Success, same emitted byte but consumed stdin count `1` |

Also test invalid-source suffixes after output-producing prefixes, zero-fuel entry, fuel exhaustion just before a `[` or `]`, long pointer runs near the logical budget, and `0xFF` input/output. The above fixtures are **expected reference vectors**, not a statement that COCK currently passes them. Implement the independent oracle before promoting an optimized decoder or AOT rewrite.

### 2.4 — `COCK-FRAME-v1`: minimal complete, EOF-detectable binary transport

**Authority:** This section defines the **framed data protocol**, not an extension to the eight Brainfuck source instructions. The independent reference executor may still run an ordinary raw BF program using raw stdin/stdout. Frames are used only by COCK modules/build/event adapters that need typed messages, binary files, or out-of-band status. Framing/deframing and all semantic routing in production are Brainfuck-authored; a permitted conventional host may transport exact bytes or persist stdout, but must not generate COCK algorithms, code, signatures, or package fields. The host-side physical read/write outcome is an independent transport fact.

**Exactly one v1 frame** (`u64` values little-endian; integer arithmetic checked):

| Byte offset | Width | Field / v1 requirement |
| --- | ---: | --- |
| 0 | 4 | ASCII magic `BFIO` (`42 46 49 4F` hex) |
| 4 | 1 | Major version `01` |
| 5 | 1 | Minor version `00` |
| 6 | 1 | Kind: `01` data, `02` result/status, `03` Android event, `04` Android action, `05` file chunk, `06` end-of-stream |
| 7 | 1 | Flags `00` (all nonzero bits rejected in v1) |
| 8 | 8 | Payload length as unsigned `u64` little-endian |
| 16 | 8 | Correlation identifier as unsigned `u64` little-endian (`0` when not used) |
| 24 | N | Exactly `N` unescaped payload bytes, including legal `00` and `FF` |
| 24+N | 1 | Required terminal byte `A5` (nonzero completion guard) |

- [ ] **Complete frame:** accept only magic, supported version/kind/flags, a checked representable total length `25+N`, a configured per-frame resource budget, all declared bytes, and the exact `A5` terminal guard. Reject any kind outside `01`–`06` and any version other than **major `01`, minor `00`** in v1. Future minor-version negotiation requires an explicitly specified, published and compatibility-tested protocol contract, never silent inference.
- [ ] **EOF and truncation:** `COCK`'s `,` returns `00` at actual EOF, indistinguishable from a legitimate zero payload byte in isolation. The mandatory *nonzero trailer at the length-defined location* ensures that a truncated input followed only by EOF zeros cannot look like a completed frame; do not silently pad or accept a missing trailer. This detects termination-induced truncation, **not** arbitrary substitution/corruption/reordering or a malicious intermediary that fabricates a valid trailer. Supply an independently checked checksum/authentication **only where the chosen transport's threat model needs integrity**; neither the trailer nor a CRC is cryptographic authentication.
- [ ] **Length and streaming:** use bounded repeated frames for huge streams; a frame-length budget limits a single message, never total app size or module count. A kind `05` `file chunk` payload begins with a `u64` **nonzero** file ID and `u64` zero-based byte offset, followed by at least one literal file byte (minimum kind `05` payload 17 bytes; use kind `06` alone for an empty file). **v1 chunks for each file MUST arrive in increasing, contiguous offset order**; the first offset is zero, and the next offset equals the previous offset plus data length. Kind `06` `end-of-stream` has **exactly 16 bytes**, `u64` file ID and `u64` final file size. A file ID may be finalized once, cannot be reused during the same build session, and cannot receive chunks afterward. Check the final size against accumulated bytes, reject missing/duplicate `END`, and require a successful build status before marking the complete APK final. Chunks and END carry no hidden executable operation; production ownership of file names/paths and outputs stays with BF-authored code.
- [ ] **Result/status envelope:** kind `02` has **exactly 36 bytes** of v1 payload: `u16 status_code`, `u16 phase`, `u64 original_source_offset`, `u64 executed_guest_commands`, `u64 guest_input_bytes_consumed`, `u64 guest_logical_cell_count`, with no additional v1 diagnostic bytes (human-readable details remain in independent reports). Source offset `0xFFFFFFFFFFFFFFFF` means not applicable; all numeric fields use little-endian, and the status is separate from raw BF stdout.
- [ ] **Status codes:** `0=OK`, `1=INVALID_SOURCE_BYTE`, `2=UNMATCHED_OPEN`, `3=UNMATCHED_CLOSE`, `4=LEFT_BOUNDARY`, `5=GUEST_LOGICAL_BUDGET`, `6=GUEST_FUEL`, `7=HOST_ALLOCATION_FAILURE`, `8=HOST_READ_FAILURE`, `9=HOST_WRITE_FAILURE`, `10=CHECKED_INTEGER_OVERFLOW`, `11=MALFORMED_FRAME`, `12=UNSUPPORTED_PROTOCOL`, `13=UNSUPPORTED_CAPABILITY`, `14=ABI_VIOLATION`, `15=INVALID_BINARY_ARTIFACT`, `16=SIGNATURE_FAILURE`, `17=CANCELLED`. Unknown codes must be reported, not silently interpreted as success. Phases: `0=preflight`, `1=guest_execution`, `2=compiler`, `3=packager`, `4=Android_gateway`, `5=transport`; unknown phases remain explicit.
- [ ] **Termination versus status:** `END` / end-of-stream is a *framed record*, not a replacement for process success or guest completion; require a valid final status and exact expected outputs where the caller contract requires it. For raw BF application execution, use the executor's out-of-band process status rather than injecting diagnostics into application stdout. Host write/read errors must not be forged as BF guest operations.
- [ ] **Mandatory transport fixtures:** empty payload with valid `A5`; arbitrary `00`, `A5`, `FF` payload; truncated header; truncated zero-tail payload; absent/mutated guard; `u64` size overflow; oversized length; unknown flags/version/kind; reordered or missing chunks; valid status and mismatched status/output termination.

**v1 session grammar for artifact-output transport (binding where kind `05`/`06` is used):** An invocation begins with zero or more kind `01` output declarations, each carrying exactly `u64 nonzero file_id`, `u64 nonzero UTF-8 path_byte_length`, and exactly that many bytes of normalized relative output path (`16+path_byte_length` bytes of payload). All integers are checked little-endian; path validation follows Part 3.4. Each declaration binds one unique file ID to one unique relative output path, as computed by the BF-authored build planner. The declaration phase closes at the first `05`, `06`, or `02` frame and cannot reopen. The frozen declared set is the expected file set. For each file ID, emit zero or more `05` contiguous chunks and exactly one `06` END; an empty file has END with size zero and no chunks. The session ends with **one and only one kind `02` terminal result** after all expected END records. An APK-producing build must declare at least one output artifact; a no-artifact successful operation requires its own separately specified consumer contract. A kind `02` received early, repeated, or followed by additional frame bytes is a protocol error. No undeclared file ID, absent END, missing expected file, duplicate terminal result, changed file-path binding, or status `OK` with a failed producer may publish a result. Input sessions and Android event sessions use their own explicit grammars, not an accidental assumption that this output grammar fits every frame stream.

**Transport closure:** `OK` is not established by the presence of a status-looking byte sequence. The declared production executor/dispatcher must report successful completion, all expected bytes must have been received, the stream must terminate on an exact frame boundary, and the underlying host file/pipe write must have succeeded. The `BFIO` trailer detects EOF-filled truncation *within a frame*, but it does **not** independently prove a stream ended after its final frame; a trusted host read-count/end-of-stream signal or a validated, bound outer transport completion is mandatory. With raw eight-command BF alone, absence of further input cannot reliably authenticate stream closure. Guest-emitted `02` bytes are **untrusted data** unless emitted by the validated BF-authored status authority after observing guest completion. A dispatcher can issue a *provisional* `OK` only after guest completion; it cannot attest its own future process exit or downstream host writes. The finalizer must therefore treat even an authoritative `OK` as **non-final** until independent host exit and transport completion are observed. Distinguish external host exit/write failure from a BF guest instruction failure; do not accept `OK` as final before all of these facts are known.

**Frame-sequence and closure fixtures (design requirements, NOT executed):** empty/unexpected output declaration; declaration after first data chunk; missing expected file; END with no chunks (zero-byte file); chunks after END; duplicate END/status; missing final status; early status then additional data; unknown output ID; output-path collision; all payload bytes correct but process exits nonzero; guest forges `OK` then traps; valid status with trailing junk; and truncated last frame. Assert that no failing session can publish a finalized artifact.

**Illustrative envelope-only frame check (design bytes, NOT executed code and NOT a valid artifact-output or build-input session declaration):** a kind-`01` frame with three payload bytes `00 A5 FF`, zero correlation ID and a valid `A5` guard is: `42 46 49 4F 01 00 01 00 03 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 A5 FF A5` (28 total bytes). The guard is recognized by **length-defined position**, not by scanning for `A5` inside data. Replace the last `A5` with an EOF-produced `00` and the receiver must reject the frame.

**Non-optional v1 observation:** without a length-defined nonzero completion guard or a trustworthy out-of-band read-count/status, pure eight-command BF code **cannot distinguish missing input bytes from genuine zero bytes** after a `,`. This is a protocol-layer fact, not permission to alter Part 2.2 EOF behavior.

### 2.5 — Additional oracle conventions and source-validation precedence

- [ ] **Vocabulary:** initial address is `0`; highest successfully reached logical address is initially `0`, and `logical_cell_count = highest_address + 1`, initially `1`. On a trapped `>` movement neither pointer nor cell-count changes. Use the `logical_cell_count` integer in the v1 result frame; source trace records may also expose highest address. This *clarifies* the Part 2.2 budget vocabulary.
- [ ] **Preflight precedence:** first scan complete source in increasing original-byte order for bytes/lines disallowed by Part 1, reporting the **first illegal-byte or invalid-annotation offset** if any. If all bytes legal, perform bracket matching left-to-right; report the **first unmatched closing** bracket encountered, else the **earliest unmatched opening** bracket remaining. Stop without running any guest command or consuming guest stdin for *any* source-preflight failure. Physical source-read failures take precedence over a successful preflight result; do not mask them as EOF.
- [ ] **Guest phase:** valid empty source terminates successfully even when fuel `0` is configured; a valid nonempty source with fuel `0` traps before offset `0`. Every admitted original command, including one that traps, consumes one unit. A skipped command consumes none. Any required terminal I/O, cleanup, or platform behavior is accounted for outside guest-command fuel.
- [ ] **Named precedence and fixtures:** `+<` at fuel `1` traps for fuel **before** executing `<` (cell 0 `1`); the same source at fuel `2` traps for left boundary (executed `2`). `+>` with one logical cell and fuel `1` stops on fuel before `>`; at fuel `2` stops for logical budget after charging `>`. Invalid source `+.x` reports source error at offset `2` with **no output and zero guest commands**, regardless of input/fuel. Source `[]` with fuel `1` succeeds; `+[-]` with fuel `3` traps before `]` with cell `0`, guest commands `3`. These complement the Part 2.3 goldens.
- [ ] **Host-versus-guest evidence:** record external host timeouts, crashes, read/write faults, allocations, and process exit separately. Do not promise identically timed physical OOM across executors; do not weaken source preflight or deterministic guest trap precedence to match host failures.

### 2.6 — Completion authority and failure surfaces

- [ ] Distinguish four facts: **(a)** guest executable termination and trapped source offset, **(b)** BF-authored dispatcher/result synthesis, **(c)** exact framed byte-stream validation, and **(d)** host transport/process exit status. None can be inferred solely from a self-declared guest `OK` frame. Treat unknown exit or failed transport as failure.
- [ ] **Source preflight** has no guest effects. Temporary buffering or validation spooling is permitted; no app-visible output is emitted before full source validation. A physical read failure while obtaining a *complete source input* fails preflight rather than pretending EOF and executing a possibly truncated source. Preserve Part 2.5's precedence for successfully read, complete source.
- [ ] Define cancellation/timeout at the *guest dispatch boundary*: signal cancellation externally, stop accepting actions immediately, drain/terminate according to declared executor capabilities, and generate `CANCELLED` only when the authority can truthfully attest cancellation; if host state is unknown, mark outcome uncertain and do not commit.
- [ ] No successful completion is inferred from a file existing, a status-like payload, a clean-looking last byte, or the presence of an ELF/APK/ZIP header. Acceptance is a checked tuple: exact input identity, command status, complete output set/stream, independent artifact validation, and permitted publication.


### 2.7 — Strict source length, zero bytes, and complete-input authority

**Critical impossibility boundary:** `COCK` specifies `,` writes zero at EOF (Part 2.2). An unframed source loader cannot distinguish a real illegal source NUL byte from EOF through `,` alone. Source loading therefore requires exact byte length and trusted stream closure. The annotated source grammar in Part 1 still forbids NUL; line breaks and safe annotations are now legal. A nonzero sentinel from an untrusted caller is not proof of completeness. Do not change guest EOF semantics to disguise this.

- [ ] **Preflight input authority:** before any production compiler/interpreter accepts an annotated guest-source file, acquire the *exact complete source byte sequence* with a trusted byte count and validated transport-closure outcome, or a valid length-delimited source record/snapshot whose framing and closure were checked. The permitted external host byte router may communicate factual file/read counts and process/pipe errors, but **all source-grammar and byte-level inspection, source hashing when used for production decisions, grammar validation, bracket matching, and build logic are BF-authored**. The host is part of the declared trusted I/O boundary, not a covert conventional-language compiler.
- [ ] **Do not trust metadata as contents:** manifest-declared lengths, filesystem sizes, hashes, and cache records are untrusted claims until reconciled with actual bytes read and final closure. Source preflight must reject an embedded or terminal `0x00`, illegal line/comment text, an invalid nonzero byte, premature EOF, extra bytes, or a mismatched count *before executing any guest instruction*. Validate empty source as a legitimate exact zero-length file. A source byte that happens to equal a frame trailer `0xA5` is **invalid source**; framing does not make it valid BF syntax.
- [ ] **Admission modes:** annotated module files from the sealed Part 3.4 build snapshot are admissible when their true length and read status are known; an annotated source record inside a fully verified length-bearing frame is admissible; a bootstrap/reference executor that independently validates complete annotated source grammar and matching brackets before guest execution is admissible as described in Part 3.2. A raw zero-terminated stream with no reliable length/closure **is not admissible as an exact-byte source-validation interface**. Direct raw BF *guest data* stdin is still permitted where the caller accepts its EOF-zero semantics; do not conflate guest input with source loading.
- [ ] **Required negative vectors:** empty exact source; legal `+.`; source `2B 00 2E` hex (`+`, illegal NUL, `.`); `2B 0A` hex (legal trailing LF); `2B 00 0A` hex (illegal embedded NUL); legal `2B` followed by unexpected extra bytes; declared length longer/shorter than bytes delivered; forged source-size metadata; a read error after a legal prefix; an invalid suffix after an output-capable prefix. Every failed preflight has **zero executed guest commands, zero guest output and zero guest stdin consumption**; record the first invalid original byte offset only where full source bytes are available.

The preflight's *observable source-byte semantics* are still the locked `COCK` semantics. This section clarifies the admissible source **transport**, not the meaning of the eight commands.

### 2.8 — v1 session selection, isolation, and final-closure contract

- [ ] **Session type is fixed before parsing:** an **artifact-output** invocation follows the exact kind `01` declarations / kind `05` chunks / kind `06` file ENDs / kind `02` terminal status grammar of Part 2.4. An **Android handler** receives exactly one complete kind `03` event frame, while the dispatcher accepts one provisional kind `04` action and emits one terminal kind `02` authority record under Part 12.2–12.3. **Build inputs** consist of the sealed, length-known manifest/source/asset snapshot from Part 3.4 (with the independently versioned Part 2.9 wire grammar if streamed); they do not silently masquerade as an artifact-output stream. The optional complete multi-file wire form is now precisely described by **`COCK-BUILD-INPUT-v1` in Part 2.9**; it remains design-only and unsupported until implemented and verified.
- [ ] **Identity and interleaving:** if a build-output stream uses a nonzero `correlation_id`, every frame in that invocation must carry the identical ID; if the caller explicitly selects non-correlated single-session mode, all frames use `0`. Never permit multiple producers to interleave frames in one v1 artifact-output stream. Isolation is by the declared execution/session handle plus its frozen input hash and expected output set; a correlation ID alone is not proof of provenance or authentication.
- [ ] **No status laundering:** data printed by an arbitrary guest, even a syntactically valid kind `02`, is not an authoritative success signal. Distinguish the guest's raw output channel from BF-authored dispatcher-controlled result synthesis and trusted host completion. If an executor cannot separate these authorities for the chosen mode, declare that mode unsupported rather than interpreting guest bytes as privileged status.
- [ ] **Publication proof:** require completed guest execution, dispatcher outcome when applicable, validated full output-set grammar, exact stream boundary and host transport completion, independent target-format validation, and verified publication path (Parts 2.4, 2.6, 11.2). A process exit check belongs to terminated **build subprocesses**; a persistent Android application's event completion instead uses the invocation-level checks in Part 12.3. A missing host closure result is **UNKNOWN / NO-COMMIT**, not success.
- [ ] **Session negatives:** mismatched midstream correlation ID, cross-session frame injection, guest-forged terminal `OK`, output after final status, duplicate terminal status, valid bytes but failed host close, host death after `OK`, file END without declared ID, action frame supplied to an artifact-output parser, and treating an event handler's still-running app process as failed solely because it has not exited.

### 2.9 — `COCK-BUILD-INPUT-v1`: exact, self-delimiting multi-file input session

**Problem closed:** Parts 2.7, 2.8 and 3.4 guarantee an exact sealed byte snapshot, but did not specify how a BF-authored build-tool consumer receives *several* distinct source/asset files with verifiable boundaries. A manifest with paths does not magically give an eight-command program filesystem primitives. The following is a **separate input-session grammar**, not the artifact-output grammar, a ninth instruction, or permission for a conventional-language build planner. It reuses the unchanged `COCK-FRAME-v1` frame envelope, kind values and file chunk/END payloads in Part 2.4. Its independent version identifier is **`COCK-BUILD-INPUT-v1`**.

- [ ] **Session admission:** the exact input root and manifest path are selected explicitly by the invoking user/host as non-executable invocation parameters. A trusted byte router first obtains the complete selected manifest and later the BF-selected paths from one sealed snapshot. It must report **actual byte counts, read errors and final transport closure** as facts; it may not infer EOF from guest `,` returning zero. The BF-authored snapshot assembler parses the manifest, selects source/asset paths, validates every annotated BF source line and extracted instruction, owns all BFIO framing, and emits a completed input session. A conventional router **must not** parse JSON, choose a dependency graph, calculate production build hashes, generate frame headers, validate BF syntax, or implement compilation. Its trusted filesystem boundary may enforce OS path confinement and read integrity as defense in depth, not in place of BF-authored semantic checks.
- [ ] **Declarations:** an input session starts with one or more kind `01` declaration frames, all with identical selected `correlation_id` (zero only in explicitly selected single-session noncorrelated mode). Each declaration payload is **exactly** `u8 role | u64 file_id | u64 declared_size | u64 path_len | path[path_len]` (little-endian unsigned integers; total payload length `25+path_len`). Roles `1=build manifest`, `2=annotated BF module source`, `3=opaque non-executable asset`; all other roles are unsupported in v1. `file_id` and `path_len` must be nonzero, and each ID and normalized relative path must be unique. `declared_size` may be zero. The first declaration MUST be the sole role-1 manifest. The other declarations, after the BF-authored manifest is validated, are ordered by **unsigned UTF-8 path-byte lexicographic order**, with unique normalized paths. **Canonical reproducible input sessions assign file IDs `1..n` in declaration order (manifest ID `1`)**; a noncanonical ID assignment cannot be presented as a byte-for-byte canonical session. Fail if the declared file count exceeds checked `u64` representation. No undeclared, missing, surplus, or mismatched manifest module/asset inputs are allowed. Disallow a path assigned both source and asset roles.
- [ ] **Data and close:** after the last input declaration, transfer each file in its declaration order using zero or more kind `05` contiguous chunks (as defined in Part 2.4: `u64 file_id | u64 offset | 1+ data bytes`) and **exactly one** kind `06` END (`u64 file_id | u64 final_size`). Zero-sized files have no chunks and one END. Require the received byte count, each END `final_size`, the original sealed snapshot count and its declared `declared_size` all to agree; reject gaps, duplicate bytes, out-of-order chunks, overflow, undeclared IDs, premature END, chunks after END and inter-file interleaving. A source may contain illegal BF bytes in transport, but its **BF-authored preflight** must reject them before any **application guest** is executed or its source is compiled. The BF-authored transport assembler and syntax validator are the explicitly authorized prerequisites, not an exception permitting compilation of unchecked guest source.
- [ ] **Terminal status and closure:** after ALL declared files close, the BF-authored trusted input-session assembler emits exactly **one** kind `02` result (`phase=5`, `source_offset=0xFFFFFFFFFFFFFFFF`, guest counts zero because this is transport, and status `OK` only on verified BF-side success). No later bytes are permitted. The receiving compiler accepts input only when this complete grammar validates **and** the external host provides an independent successful transport/process-closure result tied to the same sealed snapshot; a status-looking frame alone is not authorization. If the assembler or router dies, closes early, misreads a file, reports an unknown outcome, or cannot provide independent closure, the build is **NO-COMMIT**. For a BF-hosted assembler run, distinguish the assembler's outer host command count from any future guest command accounting; its terminal result is a transport record, not a forged guest execution result.
- [ ] **Streaming and physical limits:** checked `u64` arithmetic, bounded frame windows and spillable sealed snapshots are allowed. Session total bytes and file count are limited by configured resources/format representation, **never** a fixed global COCK project-size policy. Any protocol ID/length field finite width is a **versioned wire representation limit**, and overflows fail explicitly; future larger representations require a separately specified and compatibility-tested wire protocol.
- [ ] **Minimum complete review fixtures:** empty decoded-command source; `+.` annotated-source-compatible input; embedded `00` in an annotated source (transport succeeds but annotated-source preflight fails); byte `00` and `FF` in an asset (transport succeeds); manifest missing a declared source; source present but not listed in manifest; swapped source and asset roles; extra appended file; manifest changed after snapshot; stale or forged declared byte count; `declared_size` under/overflow; chunk reordering; file-ID reuse; corrupted trailer; duplicate status; host read error after a valid prefix; source stream ending on EOF-filled zeros; producer printing forged `OK`; and all frames correct but host close/execution failed. No failing case may reach guest execution or publish an artifact.

**Preflight order:** the complete transport/snapshot must first be known successful, then the BF-authored config/syntax validator decides whether source is valid using Part 2.5's complete-source precedence. The assembler/validator necessarily runs as a privileged BF-authored *tool* to establish this fact; the prohibition on early execution concerns **application guest programs and their code generation**, not the BF-authored input assembler performing validation. A router's independent failure makes the input incomplete even when the prefix contains an obvious illegal byte; do not claim a complete-source byte offset if the final source identity could not be established. These rules add **no observable change** to the locked `COCK` guest profile.

**Bootstrap feasibility note:** this input assembler may itself run as annotated eight-command Brainfuck under the expressly permitted conventional *standards-only* BF executor. The manifest bytes, BF-emitted frozen path requests, file bytes, checked size/closure facts and exact routed output bytes cross the documented host I/O trust boundary. The distinct physical transport and stdin/stdout multiplexing are specified by **`COCK-HOST-IO-v1` (Part 3.7)**. Until that adapter is independently tested, **multi-file mode is DESIGNED, NOT IMPLEMENTED**, even though the canonical build-input session is specified here. An input stream assembled instead by a conventional build program is **not** a compliant production path. If the host/guest adapter cannot actually deliver trusted exact lengths/closure without taking over BF-authored parsing/framing, mark this production mode **UNSUPPORTED**, not implicitly solved by a manifest.

### 2.10 — Canonical artifact-output session order and publication receipt

This section **tightens the artifact-output session grammar of Part 2.4**, without changing `COCK-FRAME-v1` header, kinds, or guest execution semantics. No earlier document version has an implementation entitled to assume another output ordering.

- [ ] **Canonical declaration order:** emit kind-`01` output declarations in ascending **unsigned UTF-8 path-byte order** after the Part 3.4 normalized-path checks. Require strictly unique paths and file IDs; the zero file ID is invalid. **For the canonical reproducible output session assign file IDs `1..n` in this same path order**, rejecting checked-`u64` overflow; any alternate ID assignment is a different explicitly declared, noncanonical output mode and cannot support byte-for-byte canonical session claims. Declaration frames are contiguous and precede file contents. Normalize names once from the BF-authored build plan; do not let a host filesystem directory enumeration choose their order.
- [ ] **No output interleaving in v1:** for each declared file, in declaration order emit zero or more contiguous kind-`05` chunks followed by exactly one kind-`06` END, then proceed to the next file. Zero-sized files contain no chunks. A chunk for a later file before the previous END, duplicate END, undeclared file or extra output is a protocol error. Chunk size is a configurable bounded window, not an application size limit.
- [ ] **Precise completion receipt:** the independent host/release validator records `(invocation identity, sealed-input identity, BF producer executable/source identity, producer process or invocation completion, received exact byte count, complete BFIO session, external write/close result, validator result, staged-output hash, published-output hash)`. Bind the receipt to the **same** invocation and bytes; `correlation_id` alone, a forged guest `OK`, or a successful final rename alone is insufficient. No implementation may invent missing receipt fields as successes.
- [ ] **Failure rule:** if a stage cannot independently determine process/stream closure, publication identity or host durability outcome, mark `UNKNOWN / NO-COMMIT`. Cancel, quarantine or keep staged outputs non-final; preserve a previously validated release. Do not claim atomic publication on a filesystem without demonstrated atomicity and durability semantics.
- [ ] **Review fixtures:** two declarations in reversed order; equal names with different spellings that normalize/case-fold to the same target path; two files whose chunks interleave; a zero-byte file; a missing final END; all frames valid but producer exit failed; wrong staged/published hash; and lost host close acknowledgement. A failure never publishes a completed artifact.


### 2.11 — Distinguish envelope validation, session validation and producer completion

The `BFIO` kind byte **does not uniquely determine the payload schema outside a preselected session grammar**. A syntactically valid 28-byte `BFIO` kind-`01` envelope containing the test bytes `00 A5 FF` is deliberately **not** a valid kind-`01` *file declaration* under either the artifact-output or build-input session grammar. A frame-only fixture passes **envelope** validation while a session validator **must reject** it. This explicit distinction prevents an independently passing frame parser from accidentally certifying a whole build stream.

- [ ] Run three separate validators with three distinct results: **envelope** (magic/version/length/guard/kind/flags), **selected session grammar** (file declaration shape, exact required file set, ordering, uniqueness, final status), and **independent producer/transport completion** (correct invocation, process outcome, actual byte counts, verified staged/publication hashes). None is a shortcut for the next layer.
- [ ] An `OK` frame is always provisional until independent successful transport and source-of-authority closure. A valid session with nonzero exit status or unknown close must fail publication. Treat EOF-filled zero suffixes, truncated trailers and framing collisions as errors; neither the trailer nor a correlation ID authenticates an adversary.
- [ ] Include a negative cross-session fixture where a complete, valid kind-`01` **build-input** declaration is injected into a selected **artifact-output** session. It must fail even if both use `COCK-FRAME-v1`, and vice versa. Unknown/extra bytes following a terminal frame fail.
- [ ] Check payload and total frame arithmetic in bounded integer operations, and check all resulting offsets before any tape write or file publication. A finite `u64` field is a **versioned representation bound**, not an arbitrary COCK project limit.

# PART 3 — APPLICATION-DRIVEN, DYNAMIC ARCHITECTURE

Use a modular architecture:

```text
Brainfuck application source + declarative build inputs + assets
                            |
                            v
              Brainfuck-authored build planner
                            |
         feature/dependency graph + validated cache
                            |
      profile-aware policy + checked resource budgets
                            |
           +----------------+----------------+
           |                                 |
    Brainfuck AOT compiler             Conditional builders
    + selected optimizer                ELF / DEX / resources
    + AArch64 code generator              manifest / ZIP / signing
           |                                 |
           +----------------+----------------+
                            |
          required-only linking + APK cost audit
                            |
                  Verified signed Android APK
                            |
                Android operating system/APIs
                            |
             Only the app-specific runtime components
```

The system **must not** use a single fixed Hello World output, hardcoded app layout, static list of screens, static number of functions, or copied complete executable templates. Make code generation parameterized and dependent on each application's source and configuration.

At build time, determine which runtime modules, libraries, permissions, activity/service/receiver declarations, native dependencies, DEX classes, Android resources, ABIs, and assets the application actually needs. Include them only when required. Support more than one module and more than one application; do not set a universal count limit.

Use a small core plus optional reusable modules. A large project can grow naturally through modules and additional platform components. Keep module boundaries, calling conventions, and binary interfaces stable and versioned.

Maintain two separable planes: a potentially large **off-device engineering plane** (parsers, optimizers, validators, autotuning, benchmarking, caches, signing, build graph) and a minimal **on-device execution plane** (only required native application logic, platform integration, metadata, and assets). Neither profiling infrastructure nor the build planner may appear in the APK by default. Application input/configuration—not the sophistication of COCK itself—determines the runtime dependency closure.

### 3.1 — Host-tool execution versus Android application target

The **build host** and **generated Android target** are separate, explicitly versioned execution targets; never assume a native executable can run on both. A generated Android AArch64 shared object (`.so`/Bionic ABI) is **not** automatically a host Linux, macOS, or Windows executable, even when the processor architecture matches.

| Plane | Executable environment | Required contract |
| --- | --- | --- |
| Root bootstrap | Externally installed standards-only Brainfuck executor on the declared host, never stored as source in the repo | Executes the BF-in-BF seed only; does not implement production or checked-in development algorithms |
| Self-hosted Stage A tools | BF-in-BF interpreter source executed by the root BF host | Executes the BF-authored mini compiler (and other BF build/test utilities); this chain is mandatory from the first accepted build |
| Optimized host tools | Verified Brainfuck-generated host-compatible machine code *when a host codegen/linking path exists* | Declare host OS, architecture, object/executable format, ABI, entry point, loader, and library dependencies |
| Generated apps | Android-compatible artifacts for declared target ABI/API | Native Android `.so`, manifest, resources, optional DEX, ZIP/APK signing and lifecycle contracts |

The host and target may share Brainfuck-authored IR, algorithms, and backends, but each output must be independently validated on its declared execution environment. If no verified host-code generation path exists, run the **BF-in-BF interpreter** via the external root BF executor to execute **Brainfuck-authored** build tools. Do not bypass BF-in-BF by directly running the mini compiler as the normal claimed self-hosted build, and never quietly use a conventional compiler or an Android-target `.so` as a host executable. Adding a host backend or controlled compatible emulation is optional and must be justified by measured benefit.

### 3.2 — Exact production-versus-bootstrap boundary

- [ ] **Executable ownership:** for every generated executable byte range or dispatched Android callback, name the `.bf` source algorithm, its Brainfuck-authored generator version, input artifact hashes, emitted module, and independent test evidence. Never treat a development harness as a normative production transformation.
- [ ] **Bootstrap contract:** the externally installed standard BF executor starts only the BF-in-BF interpreter after a documented, verified annotated-source preflight gate; it is not a repository component. The Stage A BF-in-BF interpreter must execute the **actual mini compiler as guest source**, not merely interpret demo snippets. The BF-authored preflight/module coordinator owns semantics; the outside executor cannot implement COCK AST construction, optimized compilation, linking, manifest/signature generation or Android API dispatch.
- [ ] **Generated host-tools contract:** a compiled COCK tool must have a verified host executable format and entry/loader ABI; an Android `AArch64` `.so` cannot be invoked as a generic host command by assertion. Keep **BF-in-BF** interpreter execution as the mandatory self-hosted correctness-first fallback.
- [ ] **Android bridge contract:** explicitly distinguish source-level `,`/`.` byte exchange from Android callback entry points. Only BF-generated dispatch, serialization, state transitions, and protocol handlers may transform events/commands; the OS/NDK/JNI supplies documented platform services, not hidden COCK application algorithms.
- [ ] **End-to-end provenance smoke test:** independent verification traces one input BF program and one changed configuration through source validation, emitted bytes, native entry, event response, output artifact, and declared host/Android test results. Same-byte opaque template substitution does not pass.

Make cache and policy decisions explicit in the dependency graph so optional optimization can be enabled, skipped, or replayed without changing application semantics. Missing profiles or unreliable estimates must fall back to a simple, verified build path.

Accept different application sizes: tiny single-screen apps, multi-screen apps, interactive tools, data-driven apps, and larger feature-rich apps. The practical ceiling is the selected device, Android version, file formats, available storage/memory, signing scheme, and validated implementation capability—not an arbitrary COCK size target.

### 3.3 — Conservative v1 module contract, input ownership, and dispatch

**Design-only defaults for `COCK-APP-ABI-v1` (Part 12.1):** until an alternative gets its own explicitly specified and tested ABI compatibility identifier, each application module is an eight-command BF-authored execution unit, identified by a unique declarative module ID. A module is *not* a BF source-level function definition: the eight commands provide no calls, imports, symbols, native API access, or named handlers. All module linking, generated entrypoints, dispatchers, and state marshalling are Brainfuck-authored build/runtime transformations. Every v1 feature is either explicitly in a checked capability registry or rejected: aspirational API support is not permission to generate a placeholder implementation. Ordinary-language validators may inspect this work only.

- [ ] **Manifest format:** use a versioned UTF-8 JSON `COCK-BUILD-CONFIG-v1` file as *data* (`config_version` integer `1`), with required `config_version`, `application_id`, `target_abi`, `min_sdk`, `target_sdk`, `modules[]`, `entrypoints`, and `requested_capabilities[]`; permit optional `assets[]`, `features[]`, and optimization policy. Reject duplicate JSON keys, unknown executable-shaped fields, scripts/macros in config, path traversal, duplicate module IDs, incompatible versions, and unresolved dependencies. Sort/canonicalize manifest interpretation deterministically without imposing a global module or asset count limit. The JSON parser/compiler used for production must itself be authored in eight-command BF.
**Required `COCK-BUILD-CONFIG-v1` type/routing rules:** `config_version` is integer `1`; `application_id` is a validated Android package-name string; `target_abi` is one explicitly supported ABI string; `min_sdk`/`target_sdk` are checked positive Android API integers within an independently verified supported platform matrix, with `min_sdk <= target_sdk`; `modules` is a nonempty array of module objects; `requested_capabilities` is a string array with unique registered names; `entrypoints` is an object containing at least one recognized non-null `main_module_id` (ASCII module ID) or `event_handler_id` (`u32`), and every supplied entrypoint must resolve to a compatible declared module or event handler. Each module has required `id` (ASCII ID), `source` (relative path to annotated eight-command BF bytes), `_profile` (`COCK`), and for event modules `handler_id` (unique nonzero `u32`) plus `state_schema` (`u64`); optional declared `dependencies`, `imports`, `exports` and capabilities are data-only arrays. In initial v1, dependencies form an acyclic graph; named direct-call imports/exports are rejected as `UNSUPPORTED_CAPABILITY` until a separately documented BF-generated link/signature contract is validated; the BF-generated dispatcher may route separate external events and declared main-entry invocations to isolated modules, but **arbitrary nested module-to-module calls are not a v1 capability**, even if expressed as a frame; they require a separately specified and tested call/return grammar. Optional `assets` are declared relative-path inputs with untrusted bytes; optional `features` list names requested capabilities. Unknown keys at every schema level, duplicate keys, unresolved IDs, unsupported capabilities/profiles/ABIs, invalid encodings, and all ambiguous values fail before any guest execution or artifact output. Whitespace/key order in valid JSON are not executable directives; preserve semantically ordered arrays and make unordered maps deterministic. An application's complexity remains governed by platform/device limits, not by a COCK-wide fixed object count. A build manifest never authorizes the execution of JavaScript/foreign code hidden in strings.

- [ ] **Module declaration:** record identifier, actual BF annotated source bytes/hash, role/handler identifiers (including a **unique nonzero unsigned-32-bit `handler_id`** where applicable), declared input/output frame kinds, resource requirements, profile/ABI version, exports/dependencies, and initial-state rule. IDs are ASCII `[A-Za-z_][A-Za-z0-9_]*` and must be unique within an application; IDs are *labels in data*, not new Brainfuck source syntax. Reject incompatible signatures instead of guessing a calling convention. Each entrypoint must target an existing module/handler of the declared role. The v1 graph rejects every cycle, even if it might be tolerable in a future version; no silent dependency elision.
- [ ] **Isolation-first semantics:** default each handler invocation to a newly zeroed logical guest tape with pointer `0`, a bounded input frame stream, and an output stream; state that survives invocations is explicitly provided in a versioned state blob and returned/committed with a successful action. If a handler fails, do not partially commit state unless its separately declared transaction policy explicitly allows it. The app dispatcher preserves event ordering/cancellation/ownership specified by Part 12.1; it may use platform-backed persistence only through the BF-generated gateway.
- [ ] **Byte ownership:** define whether the raw guest input is the *complete frame bytes* or its *payload* before executing; **v1 handlers receive the complete checked `BFIO` frame, including header and trailer**. A handler can emit one provisional checked action frame, while the BF-generated dispatcher owns the authoritative terminal status after verified guest completion as specified in Part 12.2. Frame decoding, application event routing, and state validation are BF-authored algorithms. End-of-input beyond the last frame follows Part 2.2, and an uncompleted/malformed frame is an error rather than extra zero input.
- [ ] **Cross-module routing versus calls:** v1 supports isolated modules selected by the BF-generated entry/event dispatcher, not arbitrary synchronous/nested calls between modules. Each dispatched event uses the verified one-invocation frame contract in Part 12; unresolved or unknown routing fails. Requested direct native calls, named imports/exports, or general frame-mediated module-to-module calls must return `UNSUPPORTED_CAPABILITY` until a separate versioned request/response ABI is defined and tested. No guest-pointer/tape sharing, implicit source concatenation, or guessed calling convention is permitted; a future direct-call optimization requires independent reentrancy, cancellation, resource and native AArch64 ABI proofs.
- [ ] **Executable transport:** a permitted ordinary BF executor and OS redirection can feed exact declared input bytes and persist exact output bytes. Ordinary-language development-only adapters can multiplex byte streams for testing but cannot be a disguised production linker, serializer, signing tool, or event implementation. Required production parsing, frame assembly, file-size decisions, and semantic transformations originate in annotated BF source.
- [ ] **Design and test acceptance:** show two non-identical application/module manifests, one binary event frame with `00` and `FF`, one state handoff and failure rollback example, and an explicit unsupported-feature error. Until real BF-authored builds and device tests exist, those examples are only *illustrations* and do not satisfy Stage E acceptance.

### 3.4 — Build-input and source snapshot safety

- [ ] **Validated paths:** satisfy Part 2.7's exact-byte source input boundary; resolve every module/source/asset path relative to one declared build-input root. For v1 reject absolute paths, `..` traversal components, NULs, platform-ambiguous separators, symlinks escaping the root, and case-folded or normalization-equivalent output collisions on the actual target filesystem. Reject unsupported path encodings rather than guessing. Do not follow mutable aliases outside the sealed input set.
- [ ] **Immutable inputs:** snapshot or securely open and hash each source, config, asset, profile and dependency once, then use those exact bytes for both cache decisions and generation. Re-read differences or unexpected replacement/TOCTOU events invalidate the build. Independent verification can repeat those hashes from the final review/build evidence.
- [ ] **Canonical interpretation:** reject duplicate JSON keys at all nesting levels, ambiguous numbers (including non-integer or out-of-range SDK/ID values), invalid UTF-8 and unregistered capability strings; preserve ordered arrays and make map iteration independent of input key order. Define canonical output byte order and metadata when a particular format permits reproducible bytes.
- [ ] **Capability and resource negotiation:** check the declared app features, API/ABI/profile combinations, import/export support, and memory/size/security budgets *before* invoking a generation backend. If a feature is absent, fail with an explicit capability error and missing requirement; never silently convert a complex app to a simpler template.
- [ ] **Version governance:** `COCK-BUILD-CONFIG-v1`, `COCK`, `COCK-FRAME-v1`, `COCK-BUILD-INPUT-v1`, `COCK-HOST-IO-v1`, and `COCK-APP-ABI-v1` are separate identifiers. New observable semantics require a separately specified, compatibility-tested identifier for the affected contract. Editing this document alone never silently changes an independently published guest profile or wire/ABI contract; the annotated-source decision here is explicit and requires independent review before implementation.

**Representative negative review vectors:** path traversal and symlink escape; duplicate keys across nested objects; two paths normalizing to one output; a manifest referencing a non-existent handler; two handlers with same ID; a dependency cycle; an unknown capability; a source file changed after hashing; and two semantically equivalent key orders producing different build outputs.

### 3.5 — `COCK-BUILD-CONFIG-v1` remaining defaults and deterministic failure rules

This supplements Part 3.3's existing required fields, examples, and capabilities without extending executable Brainfuck syntax. The *frozen v1 interpretation* of existing optional fields must be conservative:

- [ ] **JSON numbers:** require complete valid UTF-8 JSON with no duplicate object keys, no `NaN`/`Infinity`, and no duplicate normalized IDs/paths. For fields specified as integers, accept only nonnegative decimal integer JSON tokens (no sign, fraction or exponent), checked against the field width (`u32`, `u64`, or the supported SDK integer range); `true`, `1.0`, `1e0` and quoted numeric strings are not integers. Implement integer parsing without lossy floating-point conversion, including all documented `u64` values. Reject out-of-range or negative values; no silent rounding/truncation.
- [ ] **Entrypoints and modules:** a module declaring `handler_id` is an event module and **requires `state_schema`**; a module with neither is a main module. A v1 main module must not specify `state_schema` alone. `main_module_id` resolves only to a main module; `event_handler_id` resolves only to the declared unique event module. Both may be present if each resolves correctly. Empty `dependencies`, `imports`, `exports`, and module capability arrays mean no such relationships. Nonempty named `imports`/`exports` remain `UNSUPPORTED_CAPABILITY` in v1; no implicit direct calls.
- [ ] **Dependencies:** all dependency IDs are existing modules, deduplicated per declaring module, and non-self-referential. Reject the entire manifest on a cycle. For independent nodes, use bytewise ASCII module-ID order as the deterministic topological tie-break. A dependency declaration grants build order and provenance, **not** shared mutable BF tape, native symbol access, or an invented function-call instruction.
- [ ] **Capabilities and features:** all `requested_capabilities`, module-level capabilities, and optional `features[]` values are unique exact registered strings. `features[]`, when present, is only an additional checked selection of registered requested capabilities; every listed feature and module requirement must be a member of `requested_capabilities[]`. Unsupported registry IDs, incompatible platform/API/capability combinations, and missing requirements fail before execution. Examples like `ui.touch` and `ui.text` in Part 3.3 are **design requests**, not proof that a renderer or event adapter has been implemented.
- [ ] **Assets and optimizer policy:** `assets[]`, if present, is a list of unique relative UTF-8 path strings satisfying Part 3.4; it conveys immutable bytes only, not code execution. Reject or declare unsupported assets mapped into executable loading locations/roles (such as packaged DEX, native libraries, loadable scripts or third-party plugin payloads) unless a separately documented capability proves that every shipped app-specific executable byte has a compliant BF-generated provenance. File extensions alone are insufficient: validate the planned loading role and deployment location, and do not allow arbitrary assets to bypass this check. If an `optimization_policy` object is present in v1, its only admitted keys are `effort` (`fast-dev`, `balanced`, or `release`) and `objective` (`size`, `speed`, or `balanced`); omitted keys default to `fast-dev` and `balanced`, respectively. Unknown options are rejected, and a selected mode does not imply an optimizer already exists. No free-form code, scripts or inline build hooks are admitted.
- [ ] **State default:** absent a separately verified persistence capability, a handler's first invocation and an invocation after process restart start with **empty prior-state bytes**, pointer `0`, and zeroed guest tape. `state_schema` identifies the byte contract but does not imply contents or magic default data. Subsequent state is the exact previously committed opaque blob under the same schema; schema mismatch is a hard ABI error, never auto-conversion.
- [ ] **Stable outputs:** semantically equivalent JSON object key order and insignificant JSON whitespace produce the same *interpreted build plan*; artifact reproducibility also requires identical declared input bytes, generator versions and release policy. Preserve array order when semantically specified, and use documented sorting only for unordered sets. Bind cache keys to parsed semantics **and** the sealed actual file bytes; never let inconsistent alias normalization, stale input reads, or toolchain version changes reuse output silently.
- [ ] **Negative fixtures:** fractional, exponential or overflowed `u64`; integer encoded as a JSON string; a duplicate nested key; `state_schema` without `handler_id`; main entrypoint pointing at an event module; unknown optimizer option; unregistered `ui.touch`; module requesting an undeclared capability; duplicate dependency; dependency cycle; path alias; and changed post-snapshot assets. A rejected manifest emits no finalized artifact.

**Registration boundary:** a complete table for an optional Android capability is a future separately versioned, testable adapter deliverable at Stage A debug proof / Stage E UI extension. Until it exists and passes its tests, return `UNSUPPORTED_CAPABILITY` rather than fake a renderer, network adapter, gesture recognizer, or managed API.

### 3.6 — Trusted host I/O and snapshot authority matrix

| Operation | Owner for a compliant production build | Why it is allowed / disallowed |
| --- | --- | --- |
| OS open/read/close; raw byte routing; real read count; filesystem read error; process/pipe status | Explicit, declared trusted host I/O boundary | Physical platform service, not a production language algorithm; **cannot substitute an EOF-guessed zero** for a trusted byte count |
| Manifest semantics, module graph, source byte grammar, bracket pairing, original-source hash for production decisions, build cache keys | **BF-authored tool running through Stage A BF-in-BF (rooted in externally installed standard BF) or separately verified self-hosted BF-generated host executable** | Production transformation; conventional helpers are independent checkers only |
| Build-input `BFIO` declaration/chunk/END/status generation, file identity checks and semantic routing | **BF-authored snapshot assembler / dispatcher** | Host may carry exact already-produced bytes, but cannot act as the hidden input-bundle generator |
| On-disk staging/persistence and OS-level atomic rename | Declared host filesystem primitive commanded by BF-authored planner, with independently checked host success | The host does not select filenames, decide success, or perform packaging/signing algorithms |
| Final independent format verification, disassembly and cross-tool signature check | Conventional development/release verifier, separately identified | **Independent verification evidence**, not production code generation; it may veto publication |

- [ ] Make every stage name its executable, authority, exact input identity, output identity, status channel, retry and cancellation rule, and what happens on interrupted read/write. If a host stage is doing anything other than an allowed physical transport or verification function, **fail the purity gate**.
- [ ] For concurrent builds, seal isolation by session handle plus snapshot identity; the `u64` correlation field is not authentication. Reject stale cached streams from previous snapshots even when their filenames agree.
- [ ] A sealed snapshot can be constructed using content-addressed copied files or securely opened immutable handles. Validate against source mutation/aliasing and read errors, and **require the BF-side semantic hashes to match verified actual bytes**. Never use a symlink/path normalization rule that differs between BF plan and host filesystem.
- [ ] Keep a clearly labeled fallback: a single complete verified source with a trusted byte count is sufficient to run one raw guest via the reference executor, **not** to claim multi-file COCK production build capability. Missing general snapshot transport is a milestone blocker, not a reason to install an opaque packager.

### 3.7 — `COCK-HOST-IO-v1` minimal physical byte-router handoff

**Why a separate wire name is necessary:** `COCK-BUILD-INPUT-v1` contains BF-authored *semantic build records*. A plain Brainfuck program has only `,` and `.`, not built-in filesystem-open operations. To give its BF-authored assembler access to several sealed source files without a covert conventional build planner, define a tiny **physical I/O service**, which is the explicit permitted Part 1 item 7 exception. Its records report host observations, *not* decisions about which modules an application needs. `BHIO` below is **not** the `BFIO` build-frame protocol and is not a new guest-source instruction.

**Physical router record** (checked unsigned integers, little-endian, no escaped payload): `ASCII "BHIO"` (4 bytes), version `u8=1`, kind `u8`, request ID `u64`, status `u16`, metadata length `u64`, data length `u64`, followed by exactly metadata bytes, exactly data bytes, and a final nonzero `A5` guard. Total length is `33 + metadata_length + data_length`. The router checks lengths and bounds before transmission. The BF consumer validates all received fields and the final guard; an EOF-produced `00` cannot substitute for a lost `A5`. The independently checked host read/close outcome is still mandatory; the guard alone is not authentication or proof of final process success.

- [ ] **Initial manifest delivery:** the host supplies one kind `01=BOOTSTRAP_MANIFEST`, request ID `0`, status `0`, with metadata equal to the invoking user's normalized manifest-relative UTF-8 path (nonempty) and data equal to the exact sealed manifest bytes, including legal zero bytes for later JSON rejection. The host conveys its truthful completed read-count/error/closure facts; if the manifest cannot be obtained completely, it MUST fail before a normal bootstrap record is issued. BF-authored code validates and parses the complete record and never assumes that a `,` returning zero is EOF.
- [ ] **Stat request/response:** a BF-authored planner emits kind `02=STAT_REQUEST` with a fresh nonzero request ID, status `0`, nonempty relative-path metadata and zero data length. The host responds with kind `03=STAT_RESULT` and the same ID; on success status `0`, metadata exactly `u64 sealed_size`, zero data bytes; on failure metadata/data lengths are both zero and the status is `1=NOT_FOUND`, `2=DENIED_OR_ESCAPES_ROOT`, `3=HOST_IO_ERROR`, `4=SNAPSHOT_CHANGED`, or `5=PHYSICAL_RESOURCE_FAILURE`. The host performs only physical file/stat operations on the sealed snapshot; the BF tool checks whether paths are allowed/required by the manifest and chooses file IDs and semantic declarations.
- [ ] **Read request/response:** BF emits kind `04=READ_REQUEST`, a fresh request ID and relative-path metadata, status `0`, no data. Host emits one or more kind `05=READ_CHUNK` responses for that ID, each status `0`, metadata exactly two `u64` numbers `(sealed_size, zero_based_chunk_offset)` and one or more literal data bytes; offsets are contiguous from zero. Finish with kind `06=READ_END`, status `0`, metadata exactly `(sealed_size, actual_total_bytes_read)` as two `u64`, zero data. BF requires stat/read sizes to match, full bytes to arrive contiguously and the independent host file-read closure to have succeeded; zero-sized files have zero chunks and one READ_END. An attempted failed read sends kind `07=READ_ERROR`, one declared nonzero router error code as above, zero metadata/data, and terminates the request with **no** READ_END. All partial/faulty reads veto semantic input-session success.
- [ ] **Strict direction, identity and control:** kinds `01`, `03`, `05`, `06`, `07` flow host-to-BF; kinds `02`, `04` flow BF-to-host. Reject duplicates, stale/unrequested responses, wrong IDs, unknown record kinds/versions/status, overlapping outstanding requests in the initial serial-v1 profile, extra bytes and mismatched sizes. Bind the adapter invocation out of band to the selected sealed snapshot identity and exact host process handle; a request ID is not cryptographic authentication. Host completion/transport closure is an independently reported **physical observation**, never a field inferred by the BF assembler from a self-issued terminal frame. Fail close on pipe closure, unknown host state, unmatched request, timeout or cancellation.
- [ ] **Single BF stdin/stdout multiplexing:** the trusted BF assembler's **stdout** can contain (a) complete `BHIO` requests to the router and (b) complete BF-authored `BFIO` build-input frames to the compiler, distinguishable by their **different 4-byte magic values and checked explicit lengths**. The router must reject any other stdout byte, partial header, excess output or stream before selecting a complete magic and checked record length; it may mechanically separate and relay complete frames without modifying any `BFIO` byte, reading application semantics, synthesizing semantic frame fields, or interpreting `BHIO` as guest output. It must never treat a guest-emitted magic prefix as a privileged command: only the specifically bound trusted assembler process is eligible for control, and its child/guest stdout is isolated as raw guest data. Router **stdin** responses contain only its matching complete `BHIO` physical-result records. If a host cannot maintain strict channel authority, timely flush, full-duplex flow control and exact read/write closure safely, declare the adapter `UNSUPPORTED`.
- [ ] **No cyclic pipe waits:** the router must separate service of `BHIO` requests/responses from relay of `BFIO` input bytes using bounded queues and a spillable staging sink when necessary. It must not synchronously block on a downstream compiler that waits for full input closure while the assembler is waiting for the next `BHIO` response. Preserve complete `BFIO` bytes and their original order; stage them under the same invocation/snapshot identity, reject surplus/raw bytes, and resume or fail explicitly under configured spool limits. A successful router close requires **both** fully serviced requests and a complete verified staged semantic stream; it cannot report success merely because a pipe accepted bytes. Test input larger than each relevant pipe buffer and several consecutive `READ_CHUNK` records to prove no backpressure deadlock.
- [ ] **Streaming order and publication:** the BF assembler reads/manifests and stats all BF-planned files before emitting semantic input-file declarations, then uses read responses to generate correct `BFIO` file chunks/ENDs with bounded windows in the declaration order. It emits one BF-authored terminal `BFIO` status only after checking all requested bytes. The consuming compiler stages and verifies the entire `COCK-BUILD-INPUT-v1` session **before interpreting or compiling any guest module**. Independent host read/process/pipe closure completes afterward; an early BF `OK` is always provisional. This permits large inputs without the requirement that all asset contents fit simultaneously in the guest tape, subject to real I/O and configured budgets.
- [ ] **Mandatory trust-boundary fixtures:** payload byte `00` or `A5`; empty source; early EOF before a response trailer; false stat size; changed file between stat/read; wrong request ID; extra READ_CHUNK after END; host `READ_ERROR` after a successful prefix; BF-generated `BFIO` containing status-looking bytes; untrusted guest emitting `BHIO`-looking bytes; >pipe-capacity input while BF service responses are still required; staged bytes rejected on failed source closure; router attempts to interpret JSON or construct a semantic `BFIO` header; and host process failure after a complete output session. Reject/fail without a finalized artifact.

**Implementation gate:** this defines the physical service contract but does **not** assert that a standard BF executor can already implement interactive full-duplex I/O with the necessary control, or that a secure host router exists. Both sides must pass independent full-stream tests before multi-file production capability is claimed. The host's strictly physical `BHIO` wrapper is **not** the BF-authored production `BFIO` framing implementation; do not relabel a conventional packaging/program-transformation engine as a router.

### 3.8 — Bootstrap executor conformance and no hidden guest semantics

A conventional Brainfuck executor is permitted **as the physical bootstrap executor**, not as an unexamined correctness oracle or general production compiler. "Standard BF" is not by itself a complete portable contract: real executors differ in EOF behavior, tape representation, pointer boundaries, diagnostics, ignored source bytes and I/O buffering.

- [ ] **Declare the outer-executor contract:** identify implementation/version, platform, actual cell width/wrapping, pointer origin/boundary, tape allocation behavior, `,` EOF effects, raw-byte stdin/stdout behavior, bracket parsing, process exit/error channels, execution/resource limits, and source admission. Freeze a tested configuration. Unknown behavior is `UNSUPPORTED`, not an implicit `COCK` default.
- [ ] **Separate two obligations:** (a) a raw **guest** executed directly by a bootstrap program must implement the exact locked `COCK` profile, including whole-source preflight and logical traps; (b) a BF-in-BF tool or guest interpreter may use a different documented **outer** executor only if it **emulates every required guest `COCK` observation**, never relies on incompatible outer behavior, and passes independent differential vectors. The outer executor must not interpret guest source or build config on the BF tool's behalf.
- [ ] **Capability probing is development-only evidence:** compare a certified independent `COCK` oracle to direct raw execution where claimed and to BF-in-BF execution, including `0x00/0xFF`, `,` at EOF, invalid unsafe-annotation or invalid-source suffixes, boundary errors, logical-cell budgets, loop PC trace and fuel cutoffs. A host interpreter that ignores illegal characters cannot supply Part 1 guest source preflight without a **separate complete-source validator** satisfying Part 2.7.
- [ ] **Interactive transport capability:** prove the actual executor can sustain the Part 3.7 bidirectional BHIO request/response schedule, flush output at frame boundaries, preserve arbitrary bytes, avoid deadlock and distinguish stdout/stderr/process failure. If it buffers until process exit, multi-file interactive router mode is **UNSUPPORTED** with that executor. A one-file noninteractive mode does not prove this capability.
- [ ] **Trusted computing base:** record executable hash/configuration, environment and resource budgets, known nonportable assumptions and a tested fallback. A conventional executable's presence is not proof that guest interpretation, framing, snapshotting or compiler semantics are compliant.

### 3.9 — Reproducible snapshot identity and canonical manifest semantics

- [ ] **Clarify what is sealed:** the initial manifest is individually delivered and read completely before the BF planner can discover required file paths; the subsequent module/asset collection is a **verified immutable materialized input set**, not a magically atomic whole-project filesystem snapshot. Either use an OS-backed atomic snapshot for the requested root or copy each BF-selected file through confined secure handles into BF-planner-named immutable staging; **BF-authored algorithms compute any content-addressed identities used for production decisions**, while conventional tooling may hash only for independent validation. If different source files might have been captured at different instants, report the absence of project-wide simultaneity honestly, even when each copied byte sequence is exact.
- [ ] **Detect observed races:** pin opened file identity where supported; compare actual bytes read, stat/read metadata, final successful close, independently rechecked hashes and observed source replacement. If a file changes during collection or cannot be verified as the same selected object, **abort and restart the entire input collection** rather than mixing old hashes with new bytes. Unknown source mutation is `NO-COMMIT`. Once frozen, generation/cache decisions read only sealed bytes, not mutable originals. A double-stat comparison alone does not prove an atomic snapshot.
- [ ] **Canonical JSON identity:** apply strict UTF-8 decoding; reject malformed escape sequences and lone surrogates; decode JSON escapes **before** detecting duplicate object keys, IDs, capability strings and paths (for example, `"id"` and `"\u0069d"` are the same key). Preserve ordered arrays and reject conflicting duplicate/aliased paths. Normalize accepted paths to a single specified Unicode normalization form (v1: NFC), reject noncanonical spellings or unsupported host equivalences, and use the same canonical bytes in BF planning, host confinement, BFIO declarations and cache keys. Reject path separators/aliases incompatible with the target host rather than opportunistically translating them.
- [ ] **Bind input identity:** produce the build-input identity from the exact canonical interpreted manifest **and** all sealed raw source/asset bytes, ordered canonical paths, source roles, profile/ABI/config versions and generator policy; distinguish input identity from file-size metadata, user-supplied hash claims and session correlation numbers. The host may independently check the digest but cannot choose the BF-authored semantic cache key. Explicitly mark independent digest/provenance failures as `NO-COMMIT`.
- [ ] **Negative review fixtures:** JSON key escape aliases, a lone UTF-16 surrogate escape, overlong UTF-8, NFC/non-NFC equivalents, platform case-fold collisions, manifest modified after bootstrap, source mutation during stat/read/copy, two copies with equal path but unequal bytes, symlink swap, falsely successful close, and an unavailable atomic snapshot. Record whether a verified exact set was obtained versus whether a simultaneous project snapshot was genuinely guaranteed.


### 3.10 — Minimal end-to-end ownership sequence for the first multi-file build

The boundary is implementable only when the following **full chain** is demonstrated. The links below are responsibilities and acceptance tests, **not** claims that working programs, platform processes or signing keys exist:

1. The user/host chooses the invocation's root and manifest path; the trusted physical host obtains exact manifest bytes and factual read/close results, then gives the BF assembler its declared `BHIO` bootstrap record. A filesystem read error means `NO-COMMIT`.
2. The **BF-authored** assembler validates/parses that record and `COCK-BUILD-CONFIG-v1`, chooses all referenced module/asset paths, rejects aliased/unsafe paths, and asks the host **only** for physical file stat/read operations using `BHIO`. The host may enforce confinement but may not choose the build graph.
3. The host returns literal bytes, actual counts and truthful physical I/O outcomes. The **BF-authored** assembler first issues canonical `BFIO` declarations after checking manifest and physical sizes, then emits BF-generated contiguous file chunks/END records as it reads and checks file data in declared order; validates annotated `.bf` grammar and command bytes and computes semantic identity. The consuming compiler must wait for the **entire verified completed session and exact source preflight** before any guest compile/execute action. An invalid source can make previously transmitted *staged input* fail, but no such partial stream authorizes a build. A project-wide *atomic* filesystem snapshot is claimed only where OS snapshot evidence exists; otherwise promise an exact verified materialized input set, not simultaneity.
4. The production BF-authored compiler consumes the complete selected `COCK-BUILD-INPUT-v1` session **only after** verified closure, then emits a correct output plan and selected binary artifacts. The guest application must never run during malformed-input preflight.
5. The BF-authored packager/signing code owns all executable transformations and final content bytes; independent conventional validators may **reject** invalid output but never repair, generate, or silently sign it.
6. The trusted host mechanically persists BF-chosen output paths only after the complete artifact-output session, independent successful producer/transport closure, validated artifact bytes and publication receipt; failed/unknown close, cancellation or validation is `NO-COMMIT`.
7. Any unavailable executor flush behavior, secure file set, native target ABI, device capability, signer or independently validated output is marked **UNSUPPORTED / NOT VERIFIED**. This failure is an explicit **milestone blocker**, not permission for a conventional substitute production compiler or an opaque APK template.

**Testability:** each link has one happy-path literal-byte fixture and at least one interrupted/forged/mismatched-length fixture. Keep the test suite limited to that link until it passes; don't build a full Android pipeline just to debug the host router. A one-file pure BF reference invocation is a *scoped* fallback, not proof of this multi-file sequence.

### 3.11 — Canonical identity, safe snapshot handles, and reproducibility limits

This section narrows the *optional* production content-addressed-cache identity. It does not make caching, hashing, or a multi-file build prerequisites for the one-file Stage A debug compiler, and does not modify existing BFIO/BHIO records.

- [ ] **Canonical parsed-manifest form:** after strict Part 3.5 parsing and Part 3.9 unescaping/NFC/path checks, serialize an accepted manifest AST as typed binary values, rather than hashing arbitrary JSON whitespace. Type tags are single ASCII bytes: `S` (UTF-8 string), `U` (checked nonnegative `u64` integer), `A` (array), `O` (object). Encode `S` as tag + `u64` byte length + exact UTF-8 bytes; `U` as tag + 8 little-endian bytes; `A` as tag + `u64` element count + each recursively encoded element; `O` as tag + `u64` key count + each key encoded as `S` followed by its value, keys in strictly increasing **unsigned UTF-8 key-byte order**. Reject types not in the supported schema (including booleans, null and floating point); recursion/depth and total lengths are checked against configured budgets. Decode JSON escape sequences before string normalization, duplicate detection, and serialization. Numbers are never converted through floating-point.
- [ ] **Set-like versus ordered arrays:** sort accepted `modules[]` by ASCII module `id` and sort `assets[]`, `requested_capabilities[]`, `features[]`, per-module `dependencies[]`, `imports[]`, `exports[]`, and capability arrays by the already normalized unsigned UTF-8 element bytes; check uniqueness first. Preserve order for any future array explicitly registered as semantically ordered. Unknown array field semantics fail schema validation rather than being silently sorted. The normalized AST is the identity authority; a raw-JSON-byte digest may additionally be kept as forensic input provenance, not used as a substitute for semantic canonicalization.
- [ ] **Content-set identity:** construct a prefix-free byte sequence starting with the exact ASCII domain `COCK-SNAPSHOT` and byte `00`, then `u64` length plus canonical manifest-AST bytes, then `u64` file count. For each sealed source/asset, in ascending canonical path-byte order append `u8 role` (`2` or `3`), `u64 path_length`, path bytes, `u64 actual_file_length`, and exact file bytes. Append explicit length-prefixed UTF-8 identifiers for the selected language profile, config/wire/ABI contracts, BF generator identity, target, and policy; each identifier has a fixed field position and a defined empty string if not applicable. **The production BF-authored algorithm computes SHA-256 over this exact sequence**, not over a process-specific map iteration or host-provided metadata hash; independent conventional verification may recalculate it. If any identity input is unavailable, caching is disabled and there is no cache-hit claim.
- [ ] **Canonical cache-key identifier order:** the trailing length-prefixed UTF-8 identity fields in the preceding content-set rule appear in this exact order: (1) selected `COCK` guest profile; (2) build-config contract identifier; (3) `BFIO` frame contract identifier; (4) selected build-input session contract identifier or the empty string for direct single-source input; (5) selected `BHIO` physical-router contract identifier or the empty string when not used; (6) application ABI identifier or empty if none; (7) native guest-entry ABI identifier or empty if none; (8) selected UI capability-profile identifier or empty if none; (9) a canonical BF-authored producer identity that binds every output-affecting generator/runtime module and declared dependency; (10) a canonical target descriptor including OS, architecture, ABI, API/SDK and loader/packaging constraints; and (11) canonical build/optimization-policy bytes encoded as UTF-8 under one documented deterministic field grammar. An explicitly not-applicable field is `u64(0)` followed by zero bytes; an unknown identity that might affect emitted bytes is a **cache miss / no reproducibility claim**, not an arbitrary empty field. Check all lengths and fail closed on encoding ambiguity. Do not use an input path, unverified host cache claim, or session correlation ID in place of these identity-critical bytes. The identities are existing contract values, **not a document version number**.
- [ ] **File confinement and acquisition:** use a declared OS mechanism that confines every physical open to the chosen root and checks opened-handle identity (for example descriptor-relative no-follow traversal where supported), rejecting symlink/reparse-point races, dangerous platform aliases, special/device files and mutation while capturing the input set. If the available platform lacks an independently demonstrable safe mechanism, refuse the multi-file mode rather than rely on string-prefix path checks or a double-stat illusion. Read and seal actual bytes once; only those sealed copies feed BF planning, compilation and caching.
- [ ] **Separate three identities:** (a) semantic project identity as above; (b) *raw* exact source and manifest byte hashes for diagnostics/source offsets; and (c) a bound invocation/session identity for routing and host completion. Equal semantic manifests can have different raw byte hashes; identical session correlation IDs cannot establish identity or authorization. Pin generator/target dependencies that can change output in the cache key; do not claim reproducible output if required tool/environment inputs are omitted.
- [ ] **Review negatives:** reordered JSON keys versus changed ordered arrays; escape-equivalent keys; duplicate/case-folded paths; modified raw annotations with identical BF commands; an altered asset byte; mismatched file role; hidden module-capability dependency; empty and maximum-`u64` lengths; parser overflow; a race replacing a symlink after validation; and a correctly framed but different invocation. A cache hit must be rejected whenever the identity-critical bytes or policy differ.

# PART 4 — COMPILATION AND EXECUTION STRATEGY

**For the first usable compiler, default to ahead-of-time (AOT) native compilation** of Brainfuck application logic into AArch64 instructions when that provides better runtime speed, startup time, and APK size. Compile operations and loops into generated native code. Do not embed a Brainfuck interpreter in every APK merely because the build system has an interpreter.

Also implement a **separate optional Brainfuck-interpreted application mode** when runtime-loaded scripts, bytecode-like program updates, dynamic program evaluation, or other genuine application requirements justify it. Preserve the Brainfuck-written interpreter and eventual self-hosting goals, but avoid forcing interpreted execution overhead onto applications that do not need it.

The development toolchain can be large while generated applications remain lean. Conversely, never reject a necessary feature just to meet an arbitrary APK-size goal. Prefer **baseline-correct generation first**, with optional deeper optimization only after it proves net value against a measured baseline. **After the first Stage A Android compiler is usable, optionally prioritize independently verified host AOT-compiled versions of BF-authored build tools** so repeated builds need not interpret an entire toolchain. The native tools must be generated by the Brainfuck-authored compiler, run only on a compatible and independently verified target OS/ABI (or a declared test/emulation environment), preserve the locked profile, and have reproducible provenance; this never authorizes conventional-language production implementations.

**Host execution acceptance:** before promoting any AOT-compiled COCK build tool, record its exact host triple (OS, architecture, ABI), executable format, interpreter/loader requirements, provenance, and reproducible reference-interpreter differential tests. A compiler supporting only Android ELF shared libraries has **not yet** established a native development-host toolchain. The fallback is reference execution of its pure Brainfuck source, not unverified cross-execution.

**Chronological progression (Part 21 governs acceptance):**

- [ ] **Stage A first:** choose one real Android ABI/API and minimal app behavior; inventory and draft **all** needed mini-compiler/source/fixture/debug tool files, then finish implementation; only afterward independently test and optimize. Generate app-specific ARM64/ELF bytes from BF and use clearly disclosed debug-only packaging/signing to produce two working Android apps.
- [ ] **Stage B:** expand the already usable Android compiler to correctly handle all eight BF operations, nested loops, source/fuel/trap behavior and differential correctness.
- [ ] **Stage C:** add Brainfuck-in-Brainfuck interpretation as a separately testable mode, without gating the functioning Android compiler.
- [ ] **Stage D:** implement BF-authored manifest/ZIP/APK and appropriate signing, independently prove installable fully BF-produced signed artifacts.
- [ ] **Stage E:** gradually add live UI/event/state, multiple modules, dynamic resources, API gateway, optional DEX and advanced real Android features.
- [ ] **Stage F:** conditionally add host self-hosting, caching, parallelism, profiling and optimizers only with measured benefit.

Every stage repeats **acceptance-vector and complete file-inventory → bulk drafting and first-pass implementation of all slice files → bulk unit/oracle/integration/device testing → batch defect repair and full retest → passing unoptimized baseline → bulk measured optimization → complete regression testing → integration**. Running isolated tests while files are still being drafted is not the selected AI-usage strategy. A failed batch is repaired and retested before optimization or publication. No external debug packager/signer is a conforming production BF generator.

# PART 5 — DYNAMIC MEMORY, DATA, AND MODULE CONVENTIONS

Implement Brainfuck-only reusable primitives for arithmetic; multiplication/division; comparison; signed/unsigned, 16/32/64-bit and arbitrary-precision integers when needed; bit operations; shifting; copying; clearing; indexed arrays; records; stacks; symbol tables; UTF-8 byte handling; endianness; and binary serialization.

Choose documented tape layouts and module calling conventions. Describe ownership, temporary cells, preserved cells, error states, and valid ranges. Support resizable logical buffers and streaming data. Never rely on a fixed small buffer silently truncating bigger applications or resources. Where profiling supports it, reuse temporary scratch regions and pooling/arena-like allocation patterns, minimize copies and pointer chasing, and benchmark contiguous versus segmented physical tape storage. Preserve zero-initialization, checked growth, logical boundary behavior, deterministic logical-budget errors, and safe reporting of environment-dependent physical exhaustion (Part 2.1).

For large source files and binary artifacts, use bounded working windows, multi-pass compilation, streamed output, spillable intermediate representations where feasible, and checked size/offset arithmetic. Memory must scale with actual work without assuming that the complete APK fits into the tape at once.

A requested operation exceeding genuine environmental resources must produce a clear failure with the missing requirement. Do not silently simplify or omit the requested application feature.

# PART 6 — BRAINFUCK-NATIVE INTERPRETER

Write a Brainfuck interpreter in Brainfuck, supporting source input, instruction tracking, dynamically represented tape, nested loops, malformed bracket detection, structured errors, binary input/output, and `COCK` semantics. Decode and validate source once where feasible; compute matching-bracket targets in advance for constant-time loop jumps; keep dispatch and tape-access paths compact; and measure specialized internal decoded operations when appropriate. Do not change the language or introduce a ninth Brainfuck source command.

Verify Hello World, nested loops, binary echo, arbitrary byte values, long programs, large logical tape regions, EOF, malformed source, and cross-interpreter consistency. Benchmark interpreted instruction throughput, dispatch overhead, tape-growth behavior, interpreter startup, and peak memory with fixed repeatable workloads.

Keep the toolchain interpreter distinct from the **optional** on-device interpreter. Self-hosting the toolchain does not require shipping it inside generated applications.

### 6.1 — Interpreter stages and fast-path checklist

- [ ] **I0: BF-only oracle and external observations.** Author a deliberately simple **independent Brainfuck** reference model/test oracle as `.bf`, separate in algorithm from the BF-in-BF interpreter. Use externally installed, unmodified standard BF executors and native/platform tools as additional *outside-repository* checks; their source and test harness implementations must never be checked in. Test source traces, logical budgets, errors and exact byte output.
- [ ] **I1: mandatory Stage A BF-in-BF self-hosting kernel.** Encode guest source, matching jumps, guest pointer/tape and input/output streams as data on the outer executor tape; document guest-versus-outer resource boundaries. Implement and validate **all features exercised by the real BF mini compiler and by one inner copy of I1 itself**, including input framing, loop semantics, resource bounds and completion/error rules; run the compiler under I1 as the default Stage A build path and show **I1 → I1 → compiler** byte equivalence under bounded resources. Add complete guest-profile support incrementally where it is not required for this first self-hosting proof. A BF-in-BF interpreter that runs only Hello World or sample guests does NOT satisfy Stage A self-hosting.
- [ ] **I2: predecoded interpreter.** Have a *Brainfuck-authored* decoder validate and compute jumps once, then execute compact internal operations without repeated bracket search. Keep a non-optimized reference path and compare exact output/errors.
- [ ] **I3: measured shortcuts.** Optionally cache decoded source, combine operations, use specialized loop kernels, or change backing tape representation only under proof or reference-differential tests. Measure setup costs as well as per-command throughput.
- [ ] **I4: device interpreter (optional).** Package only when an actual app requests dynamic BF execution; define isolation, cancellation, input framing, execution budgets, and size/latency cost.
- [ ] **Acceptance:** for every stage, test empty/invalid/large source, `0x00`/`0xFF`, EOF, arbitrary output bytes, brackets, growth, left faults, fuel cutoffs and injected physical OOM; report executable/source size, startup, warm throughput, peak memory, and exact environment.

### 6.2 — Choosing the cheapest correct execution path

The BF-in-BF interpreter is a **mandatory Stage A self-hosting execution path**, not an automatic throughput winner. Treat interpreted execution, decoded execution, and AOT as separate cost envelopes:

- [ ] Keep **I0** as the development-only truth oracle; measure **I1/I2** as Brainfuck-authored production algorithms executed by the declared host, without equating guest commands/second to outer executor commands/second.
- [ ] Prefer a lightweight **BF-in-BF reference execution** for tiny one-shot build guests when decoding/compiler setup cannot be amortized; root-host direct execution of the BF compiler is allowed only as an explicitly labeled **bootstrap diagnostic comparison**, never as the normal accepted self-hosted build path. Select predecoded interpretation when repeated loop dispatch makes upfront decoding worthwhile.
- [ ] Prefer verified host-compatible AOT tools for repeated build operations **after** compilation, loading, startup, and artifact-size costs have been measured; no Android-only `.so` can substitute for an unproven host executable.
- [ ] For each option report `preflight + decode/compile + link/load + guest execution + cleanup` as an **end-to-end** cost, with peak memory, output/tool bytes, and first-run versus repeated-run scenarios. Optimization break-even thresholds must be measured per workload/target, never hardcoded as universal program-length rules.
- [ ] Share `COCK` validation/trap/trace fixtures across all modes, but do not require that the independent oracle, BF-in-BF interpreter, AOT runtime, and optional Android interpreter share a single production implementation or dependency tree.
- [ ] Fall back to the simplest already-verified compatible path when cache, host backend, profile, optimizer, or runtime is unavailable; label the missing optimization separately from any failure of required functionality.

# PART 7 — PARAMETERIZED AArch64 COMPILER

Implement a Brainfuck-authored AArch64 assembler/code generator with enough instructions for constants, register arithmetic, comparisons, branches, loads/stores, stack access, address calculation, function calls, returns, and position-independent code.

Support labels, symbol resolution, branch fixups, relocation as required, alignment, immediate bounds checks, and little-endian output. Make encoders parameterized rather than copying entire precompiled functions as opaque byte arrays.

Compile variable-length Brainfuck programs, with correct loop matching and scalable symbol/branch tables. Implement a compact, versioned IR suitable for streaming, source locations, operation counts, jump destinations, and checked offsets; avoid constructing a large AST when a compact representation suffices. Add measured optimizations: run-length compression for operations, clear-loop recognition when semantics permit, constant propagation, dead-code elimination, reducing dispatch overhead, **checked partial evaluation of static application inputs, safe tape-access specialization, selective inlining, and profile-guided code layout where practical**. Use scalable bracket/jump resolution and single-pass scanning where feasible. **Optimization must preserve the locked `COCK` semantics and its deterministic logical resource-error behavior, including intermediate pointer movements and required tape-growth/budget checks (Part 2.1).** For example, `<>` cannot be erased if the `<` operation could cross the left boundary, and `><` cannot be erased when the rightward movement is required to trigger a logical resource-limit failure. Physical out-of-memory failure must remain safely handled; its exact occurrence is not promised equivalent across different allocation strategies.

Accept only supported instructions and ABI patterns. Report unsupported features instead of generating subtly invalid code. Verify generated instruction bytes by independent disassembly and execution.

### 7.1 — Minimal BF-specific compiler pipeline

Build this pipeline **before** abstracting it into a general-purpose language compiler:

```text
annotated BF source bytes with extracted eight-command stream
      ↓ checked single-pass scan + bracket pairing
compact linear operations + source offsets + loop/jump table
      ↓ optional semantics-preserving BF-specific rewrites
validated operations + explicit safety/fuel checks
      ↓ BF-authored AArch64 lowering + patch/fixups
checked native code + target-specific ABI bridge
      ↓ BF-authored ELF / resources / package / signing
independently verified artifact
```

- [ ] For a compiler advertised as implementing the **complete `COCK` language**, emit a **correct baseline for all eight commands and nested loops** before enabling general optimizations. The explicitly restricted Stage A mini compiler may instead optimize only its **already tested supported subset** after its own passing correctness/device baseline; it must reject unsupported guest commands and must not claim full-language optimization or conformance. Include slow-path runtime helpers when their *Brainfuck-authored generation* and target import model are documented and proven.
- [ ] Use a bracket stack and compact opcode/count/jump/source-offset records, not a heavyweight AST, Pratt parser, symbol table, type checker, or SSA by default: plain BF has no expressions, identifiers, or type syntax demanding them.
- [ ] Keep the encoder, relocation/fixup logic, register/calling convention plan, and output streaming separately testable. Validate instruction immediates and branch reach; choose a correct fallback such as a documented long-branch sequence instead of truncating offsets.
- [ ] Begin with safe local operations and test their **unoptimized versus optimized output, guest errors, and instruction-budget checkpoints**. Guard or decline rewrites whose correctness under `COCK` cannot be established.
- [ ] Separate *fast compiler latency* (minimal passes, bounded buffers, no mandatory profiling) from *fast generated code* (optional deeper release passes). Test cold start, parse time, lowering time, relocation time, peak memory and emitted bytes independently.
- [ ] Generic AST/type-inference/SSA/graph coloring/JIT are **explicitly deferred**, not feature-completeness requirements for an eight-command source language. Consider them only for a future verified intermediate representation or workload that proves a net benefit and does not alter Brainfuck-native authorship.

---

### 7.2 — Proof obligations for every BF optimizer pass

A small compiler is easiest to maintain when every rewrite has an explicit, mechanically testable contract. Do **not** require a generic optimizing compiler framework to satisfy this contract.

- [ ] **Before the pass:** specify the input operation range, required static facts, whether it touches `+ - < > [ ] . ,`, target ABI restrictions, expected compile-time overhead, and an unchanged baseline alternative.
- [ ] **Semantic invariants:** preserve modulo-256 cells, bracket behavior, source preflight, input/output order, input consumption, left-of-zero traps, logical address high-watermark/budget checks, and exact declared error/status semantics.
- [ ] **Fuel-aware equivalence:** if guest fuel is enabled, retain enough original-command/source-offset information to reproduce the reference cutoff and state (Part 2.3). A clear-loop/transfer-loop shortcut may execute via a fast path only when that equivalence can be proved or enforced through a checked slow path.
- [ ] **Safe arithmetic:** treat counts and pointer offsets as checked multi-byte integers in BF-authored implementation code; do not let a decoded-run counter, branch displacement, IR length, or ELF offset overflow silently.
- [ ] **Loop proof:** justify termination and modular arithmetic, pointer travel, intermediate traps, and byte I/O before specializing `[-]`, `[+]`, transfer loops, or tape scans. Loop bodies that read input, write output, or can cross tape boundaries demand explicit guards or refusal to optimize.
- [ ] **Verification:** run differential fixtures against the nonoptimized oracle under unlimited fuel, selected boundary budgets, and strategically chosen fuel cutoffs; include empty/invalid input, short programs, nested loops, and large counts. Compare guest state where inspectable, not only stdout.
- [ ] **Promotion:** record new emitted-code size, compiler cost, peak memory, runtime/startup distribution, debugging/source-map impact, and fallback behavior. Keep passes individually reversible and disable one that worsens the declared workload objective without sufficient countervailing benefit.

**Example:** `+-` may be collapsed for an unrestricted, externally equivalent completed computation, but not to a zero-command sequence under a fuel budget that can stop after `+`. Similarly, `><` cannot disappear if the intermediate rightward step is supposed to trip a logical address budget. Maintain an `O0`-like correctness path permanently.

### 7.3 — Minimal IR execution contracts and optimizer reproducibility

- [ ] For each compact IR record retain: opcode/run kind, checked repeat count (if any), original BF source start/end offsets, bracket target for a loop operation, mandatory intermediate pointer-travel checks, and the mapping needed to reconstruct every charged original command when fuel is enabled. All ranges must be checked before widening or truncation in the AArch64 lowering.
- [ ] **Do not remove `[]` or any loop purely because its source contains no `.` or `,`.** Boundary errors, logical high-water marks, nontermination, exact instruction fuel and interruption points can still be observable. A loop's optional accelerated form needs a proven termination/cutoff argument plus an O0 replay path. The optimizer may decline a transformation without compromising correctness.
- [ ] Source-invalidity preflight always precedes the IR optimizer. No optimization result may be used to justify skipping an invalid byte, unmatched bracket, zero-fuel trap, or exact-source identity check.
- [ ] Classify every pass as `ALWAYS_SAFE`, `GUARDED`, or `DISABLED` *for a stated target, profile and budget mode*, with proof/test evidence. If disabling checks for unrestricted guest execution, confirm that their absence does not conceal mandated pointer or deterministic trap behavior; host-dependent OOM remains a separate failure surface.
- [ ] Pin pass order and decision inputs in release-policy data. For the same sealed source/configuration/profiles/target, no uncontrolled measurement, host time, entropy or implicit cache state may change the selected transformation or unsigned output without a documented reproducibility exception.

### 7.4 — Minimal versioned native guest entry handoff

`COCK-NATIVE-ENTRY-v1` is a **target runtime interface** for future verified AOT applications, distinct from source `COCK`, Android's platform ABI, event `COCK-APP-ABI-v1`, and any unverified host tool ABI. It does **not** add a source command, promise a working native runtime, or grant conventional host code authority to implement guest algorithms.

- [ ] **Android arm64 guest entry (not the OS launch callback):** use AAPCS64 for a BF-generated exported symbol named `cock_guest_run_v1`. At entry `x0` contains an aligned pointer to a caller-owned versioned guest-context header; `x1` contains an aligned writable result header. On normal return, `w0` contains the same declared status code as the result; report target-specific nonreturning traps through the declared lifecycle/OS error channel. Standard ABI rules for callee-saved registers, stack alignment, reentrancy and thread affinity apply. This symbol is **COCK internal**: Android `NativeActivity` does not invoke it merely because it exists. A separate BF-generated Android-compatible `ANativeActivity_onCreate` entry/selected documented equivalent must arrange the real invocation and lifecycle. A host-tool executable has a *separate* OS loader/entry contract, not an Android `.so` substituted for a host command.
- [ ] **v1 context header:** 40 bytes at byte offsets `0:u32 abi_version=1`, `4:u32 struct_size=40`, `8:u64 flags=0`, `16:u64 runtime_handle`, `24:u64 invocation_id`, `32:u64 reserved=0`, with little-endian fields. A nonzero runtime handle identifies a BF-generated, invocation-scoped tape/I/O/budget service under a fully documented internal runtime contract; `0` is permitted **only** when guest operations and required checks are inlined with no external guest service. The handle is **not** permission for an opaque foreign helper to implement compilation, guest transitions, event routing or rendering. Reject unknown flags/versions/size; make pointer provenance and lifetime explicit.
- [ ] **v1 result header:** 56 bytes at offsets `0:u32 abi_version=1`, `4:u32 struct_size=56`, `8:u32 status_code`, `12:u32 reserved=0`, `16:u64 source_offset`, `24:u64 executed_guest_commands`, `32:u64 guest_input_bytes_consumed`, `40:u64 guest_logical_cell_count`, `48:u64 guest_output_bytes_emitted`. Use Part 2.4's status code vocabulary where applicable (the native `u32` status widens the wire `u16` status without changing its numeric meaning), with `0xFFFFFFFFFFFFFFFF` for non-applicable source offset; host I/O and physical allocation failures remain separately attributable. Include `status_code` only after completion of the guest as actually observed; do not mistake an untrusted guest-written result header for independent completion proof.
- [ ] **No-service Stage A entry rule:** the design-default Stage A guest has no `,`, pointer travel, loops, state or generic binary stdout. Therefore `runtime_handle=0` is legal only if the BF-generated native code inlines all admitted cell arithmetic, the required output-byte check and the bounded one-byte diagnostic sink, with no hidden guest interpreter. The BF-generated OS adapter supplies real valid 40-byte context and 56-byte result records, arranges correctly aligned/lifetime-bound storage, sets the invocation identity, calls the internal guest using the actual Android AAPCS64 ABI and consumes its return/status before releasing resources. Log delivery is separately verified on the device; neither a zero runtime handle nor a returned status fakes platform observation. For any later feature requiring input, nontrivial tape management, generic binary output, guest fuel or event routing, **first** specify and test its actual BF-generated service/callback interface; do not reuse the no-service shortcut outside the subset.
- [ ] **Freeze the generated runtime service before Stage A AOT acceptance promotion:** document its call surface for raw byte input/output, checked logical tape growth, optional fuel, errors, cancellation and frame ownership; prove it is BF-generated or a narrowly declared OS physical-I/O service, not a hidden second interpreter. For a minimal app with every guest operation and requisite checked helper **inlined into BF-generated native code**, `runtime_handle=0` may mean no separate runtime service is used; a nonzero handle requires a complete BF-generated interface table, declared allocation/lifetime, and independent ABI tests. The guest still receives a real, valid context/result header and cannot omit required traps for its supported subset. Do not publish an ELF as `COCK-NATIVE-ENTRY-v1` compatible before the complete relevant binding, memory ownership and status mapping pass a verified ABI test suite.
- [ ] **Acceptance vectors:** mismatched version/size, unaligned pointers, stale handle, repeated invocation ID, empty valid guest, binary `00/FF`, stdout failure, input EOF, interrupt at original-command fuel boundary, left-trap, right-budget trap, runtime resource exhaustion, Android lifecycle shutdown, and host/target format mismatch. A design header is not evidence that emitted machine code runs.

### 8.1 — Android compatibility gate

Keep release/channel restrictions outside the eight-command language semantics.

**Current-policy checkpoint (externally cross-checked 2026-10-23; re-check for each release):** Google Play's stated target-API requirement for ordinary new mobile apps and updates is Android 16 / API 36+ from 2026-08-31, while new/updated **Wear OS and Automotive OS** apps require API 35+ and **Android TV and XR** apps require API 34+; new Play apps use AAB publishing rather than simply uploading a standalone APK. Applicable extension/exception policy and the distinction between new submissions, updates, and already-published app availability must be checked for each submission; do not treat one global target SDK number as universal across TV, XR, Automotive, Wear OS, private apps, or distribution channels. Google's current page-size guidance says that apps targeting Android 15 / API 35+ on 64-bit Play devices must support 16 KiB pages and identifies **2027-02-01** as the next enforcement date for noncompliant app updates. Check the exact category, target API, channel, and deadline again before publishing. These are **distribution/channel facts to validate at release time, not permanent `COCK` syntax rules**. Consult the authoritative [Google Play target API rules](https://support.google.com/googleplay/android-developer/answer/11926878), [Android target API guidance](https://developer.android.com/google/play/requirements/target-sdk), [App Bundle rules](https://developer.android.com/guide/app-bundle), and [16 KiB page-size guide](https://developer.android.com/guide/practices/page-sizes). In CI and manual verification, record `readelf`/equivalent checks of `PT_LOAD` alignment, `zipalign -c -P 16 -v 4` for relevant uncompressed libraries, runtime page size (`getconf PAGE_SIZE`), ABI/API, packaging mode, and actual launch outcome; do not claim all distributions pass from one emulator.

**Distribution evidence protocol:** This 2026-10-23 policy checkpoint describes current official statements, not future guarantees. At every release review record the retrieval date, app category, new/update/existing status, target/min SDK, distribution channel, extension/exception if applicable, native ABI/page-size and signing validation, and the official guidance revision or archived excerpt. When external policy cannot be verified, mark that distribution claim **NOT VERIFIED**, even if a sideloaded APK installs. Direct-install and Play submission are independent gates.

**Mandatory main-thread boundary:** Android `NativeActivity` callbacks run on the application main thread. The BF-generated `ANativeActivity_onCreate` bridge must return promptly after bounded setup; it must not interpret or execute unbounded guest loops, perform blocking source reads or wait for an external build/router on that thread. For Stage A, reject potentially nonterminating programs by selecting a clearly declared loop-free guest subset, or supply independently tested execution-fuel/cancellation and a correctly synchronized, lifecycle-managed worker execution route. A host test timeout that kills the app is a failure observation, not a substitute for a correct on-device bounded-execution contract. Verify callback return, teardown and responsiveness separately from program output. See [Android NativeActivity callbacks](https://developer.android.com/ndk/reference/struct/a-native-activity-callbacks) and [Android responsiveness guidance](https://developer.android.com/topic/performance/anrs/keep-your-app-responsive).

**Capability-claim boundary:** v1 `NativeActivity` is a feasible initial Android lifecycle/native-input route, **not** evidence that BF code can invoke arbitrary managed-only APIs, render accessible multi-screen UIs, implement background services, or meet Play publication checks without further generated DEX/manifest/runtime work. Keep per-capability matrices with `DESIGNED`, `IMPLEMENTED`, `DEVICE-VERIFIED`, and `UNSUPPORTED` statuses. Do not treat one emulator result as proof of all API levels and device classes.

**Native-only manifest checkpoint:** If an app ships native code but no APK DEX code, explicitly validate `android:hasCode="false"` on the `<application>` element so Android does not expect missing APK DEX classes. If a feature genuinely adds DEX/managed application components, generate and verify the appropriate manifest setting and class/component declarations. For a framework-provided `NativeActivity`, independently test the launchable activity declaration, native-library metadata, entry symbol, exported/intent-filter rules, actual `.so` loading, and lifecycle on target devices. In the default `NativeActivity` model, `android.app.lib_name` selects the native library and `android.app.func_name` optionally selects its OS-facing entry; otherwise the expected entry is `ANativeActivity_onCreate`. That callback takes the NDK-specified `(ANativeActivity*, void* savedState, size_t savedStateSize)` arguments, **not** the two-pointer `cock_guest_run_v1` interface. The **BF-generated** adapter must implement the selected OS-facing entry and call the separately generated guest with its valid context/result records; record control flow, callback cleanup and observed errors. A valid internal guest symbol without this bridge is not an install/launch proof. The exact choice is application-dependent; do not include an empty DEX merely as an unverified workaround. See the [official application manifest attributes](https://developer.android.com/guide/topics/manifest/application-element), [NativeActivity contract](https://developer.android.com/reference/android/app/NativeActivity), and [NDK native-activity ABI](https://developer.android.com/ndk/reference/group/native-activity).

Keep the runtime modular. Include only the lifecycle, UI, graphics, storage, network, audio, or other features that the application needs. Support changing state, multiple screens, navigation, event callbacks, input, and asynchronous work without hardcoded screen/event counts.

Use efficient event-driven scheduling and redraw when possible; do not create an unnecessarily busy render loop. Maintain bounds checks, deterministic cleanup, and lifecycle-safe resource management. Minimize native/managed boundary crossings, unnecessary initialization, redundant work, and memory allocations in measured hot paths; prefer batching only when it preserves ordering, lifecycle, and error semantics.

### 11.1 — Release signing security and independent evidence gate

- [ ] Distinguish unsigned/reproducible payload construction, *disposable-key* test signing, and *release-key* authorization. A valid `apksigner verify` result is necessary but insufficient to prove the signing implementation is safe for real secrets.

An external signer remains permissible only for labeled development debug tests, never as hidden COCK-native release signing. Refuse a release claim rather than weakening language purity or key security.

- [ ] **Build stages:** create unsigned files under a build-scoped staging area, verify each completed stream/file and expected output set, finalize ZIP structure and alignment, perform test/release signing only in its separately permitted gate, and run independent artifact validators *before* publishing final build paths. Match the exact APK bytes independently checked to the bytes published or handed off for installation.

# PART 12 — DYNAMIC APPLICATION MODEL

An application is defined by its Brainfuck program(s), associated data/configuration, and requested platform capabilities, **not by a predefined example application**.

Support as the platform evolves:

- Variable application structure, multiple components, screens, states, and event handlers.
- Dynamic UI construction, data binding, navigation, layout, rendering, and accessibility where implemented.
- User input, timers, asynchronous callbacks, and cancellable work.
- Persistent and transient data, files, network, audio/video, sensors, and device hardware through permitted APIs.
- Multiple modules, separately generated resources, versioned interfaces, and application-specific dependencies.
- Both static native output and optional interpreted application logic selected per application requirement.

Do not bake in any universal maximum for screens, functions, events, assets, modules, permissions, or APK bytes. A limit imposed by the supported device, OS, format, security policy, available resources, or unfinished implementation must be identified honestly and handled safely.

Support configuration-driven choices for target ABI, minimum/target SDK, app identifier, permissions, UI mode, features, optimization priorities, and optional runtime components. Configuration is non-executable input data; all production transformation algorithms remain Brainfuck.

### 12.1 — Versioned application programming ABI and event protocol

Define and freeze `COCK-APP-ABI-v1` as a distinct compatibility contract from `COCK` (language semantics) and the underlying Android/JNI ABI. The application manifest and build configuration are declarative **non-executable data**, never hidden macro languages or authored foreign-code programs. All application behavior and generated dispatch, framing, routing, lifecycle integration, and serialization algorithms must be Brainfuck-authored.

- **Modules and symbols:** Each authored module is an annotated `.bf` byte stream with a declarative, versioned module identifier, declared imports/exports/handler role, compatible ABI/profile version, and dependencies. Follow the isolated, framed dispatcher convention of Part 3.3; document any versioned alternative to composition or invocation; do not pretend standard Brainfuck itself offers named functions or imports.
- **Entrypoints:** Define application initialization, main/background work, shutdown, and event-handler registration through the non-executable manifest and a Brainfuck-generated entry dispatcher. Reject missing, duplicate, incompatible, cyclic (where disallowed), or unresolved declarations with precise diagnostics.
- **Framed input/output:** Use the exact `COCK-FRAME-v1` format in Part 2.4 for version, message kind, event/operation identifiers, payload lengths, binary bytes, result/error status, and correlation IDs where asynchronous work is needed. Specify endian order, length limits/budgets, extension rules, and EOF separately. `0x00` and `0xFF` are ordinary payload bytes.
- **Event semantics:** Define mapping from Android lifecycle/window/input/timer/service events to declared handlers, with the Part 3.3 isolation/state-commit defaults; state transitions; event ordering within a queue; async cancellation; backpressure; reentrancy/thread affinity; errors; and handler completion. Do not require every app to include every Android event module.
- **State and ownership:** Specify whether handlers share a persistent logical tape or exchange explicit state blobs; define initialization, preservation, reset, dynamic tape budgets, lifetime, ownership of native/JNI handles, and restart/process-death behavior. Avoid accidental mutable-state sharing between independent modules.
- **ABI evolution:** Version and validate module signatures, wire protocol, platform gateway, and supported capabilities. Reject incompatible inputs with actionable errors; extend without a fixed list of screens, modules, features, or event kinds.

**Acceptance:** implement two materially different `.bf` applications using the **same versioned ABI** (for example, a tap counter with persistent state and an input-driven screen update), with different declared handlers/resources, real event-to-handler dispatch, correct behavior after lifecycle transitions, and no hardcoded full executable app template. Verify the exact framed bytes and handler routing independently before claiming a general Android application model.

### 12.2 — Minimal event/action wire ABI and state commit

**Normative v1 application message layouts** use the `COCK-FRAME-v1` header/trailer in Part 2.4, checked little-endian numeric fields, and matching `correlation_id` for a request and its response(s). These fields are payloads, **not BF instructions**. The wire protocol's major version stays `1`; changes to observable v1 meanings require a new application ABI version.

| Kind | v1 payload header (all offsets relative to payload start) | Follow-on bytes |
| --- | --- | --- |
| `03` Event | `u32 handler_id` at 0; `u32 event_type` at 4; `u64 state_schema` at 8; `u64 prior_state_len` at 16; `u64 event_data_len` at 24 | Prior-state bytes, then event-data bytes; exactly `32+prior_state_len+event_data_len` payload bytes |
| `04` Action | `u32 handler_id` at 0; `u16 action_type` at 4; `u16 action_flags=0` at 6; `u64 state_schema` at 8; `u64 next_state_len` at 16; `u64 action_data_len` at 24 | Replacement-state bytes, then action-data bytes; exactly `32+next_state_len+action_data_len` payload bytes |
| `02` Status | The exact 36-byte status payload defined in Part 2.4 | No extra v1 fields; `phase=4` for Android-gateway outcomes |

- [ ] Manifest assigns each handler a unique nonzero `u32 handler_id`; the event dispatcher routes only to existing declared handlers and validated capabilities. Event kinds have a **versioned capability registry** (e.g. app lifecycle or input), and action types `0=no-op`, `1=render declared UI update` are initial **ABI design examples**, not claims that Android UI support exists. Unsupported event/action IDs must fail explicitly. IDs impose an ordinary format limit on this versioned ABI, **not** a universal restriction on how many modules or apps the project can ever support.
- [ ] v1 event handlers are **serialized FIFO per application** to make ordering auditable; external OS callback arrival timing is not deterministic. A handler consumes a single full checked event frame and yields **exactly one provisional action frame**; the verified BF-generated dispatcher issues **one terminal status frame after the guest finishes** with the same nonzero correlation ID. The ordered *external result* is therefore one action followed by one authoritative status on success. A failed invocation may emit no valid action but must still surface an out-of-band terminal failure when the transport permits; do not convert a crash or truncated message into `OK`.
- [ ] Check both length sums for overflow, frame trailer, schema version and handler ID; reject nonzero action flags, unknown status, mismatched correlation ID, duplicate or mismatched responses, and extra action bytes. All state and action data are opaque length-bearing bytes until a declared, Brainfuck-authored handler/module interprets them.
- [ ] Stage the replacement state and declared **reversible/local** platform actions, and apply them **only after** a valid action, verified successful guest termination/stream closure, and the dispatcher-authoritative `OK` terminal status; on timeout, invalid frame, cancellation, or nonzero status, retain the previous committed state and do not apply queued effects. **Do not promise atomic rollback of irreversible Android/OS side effects** (network, notifications, file mutations, external service requests): such actions remain unsupported by the initial v1 transactional path until an explicitly versioned acknowledgement, failure, idempotency and partial-effect model is specified and tested.
- [ ] Sample design trace, NOT actual execution: event `handler_id=1, event_type=1, state_schema=1`, prior-state bytes `00 FF`, event bytes `00 00 00 00 00 00 00 00` (touch at pixel `0,0`); success action `handler_id=1, action_type=1, state_schema=1`, next-state bytes `01 FF`, versioned text action-body bytes `01 00 00 00 02 00 00 00 48 69` (the label `Hi` under Part 12.4), then status `OK` with the same correlation ID → commit; on `CANCELLED` status → no commit. This intentionally illustrates a **two-byte opaque application state**, not the separate eight-byte numeric counter fixture in Part 12.4; a handler cannot silently reinterpret one state schema as the other. Verify exact bytes with independent fixtures when implementation begins.

**Completion and commit safety:** The initial v1 handler's trusted BF-generated runtime owns the authoritative kind `02` completion record; an application handler cannot certify its own OS/process success merely by printing `BFIO` bytes. The handler may emit one provisional kind `04` action; the dispatcher validates/buffers it, observes guest termination, checks exact source/trace/budget and process/transport results, then synthesizes the final terminal status. It refuses extra/trailing frames or stdout, a handler-supplied forged terminal status, contradictory state schema/handler ID, and anything emitted after completion. No action or replacement state is applied until **successful guest termination + exact complete action + authoritative `OK` + queue/lifecycle validity** all hold. This is a design ABI contract; it is not a claim that this authority exists today.

**FIFO, reentrancy, and cancellation default:** for v1 there is one logical in-flight handler invocation per application; later valid events queue in arrival order as observed by the dispatcher. No implicit cross-thread reentry or nested direct calls. Cancellation of a queued event discards it; cancellation of an in-flight event prevents commit and requires an observed stop or safe timeout/error conclusion. An app/process restart invalidates outstanding correlation IDs and volatile queued work. Persisted state only survives a restart if a capability-specific BF-generated persistence transaction is separately declared and verified; otherwise reinitialize to the manifest's initial-state rule. Native-JNI thread-affinity and lifecycle transitions are validated before effects, not guessed from FIFO order. Queues and state are bounded by explicit configurable resource budgets and apply defined backpressure/errors rather than unlimited RAM growth.

**v1 action shape constraints:** `action_type=0` has zero `action_data_len`; `action_type=1` requires a registered rendering capability and a separately validated versioned update-body format, or fails `UNSUPPORTED_CAPABILITY`. Neither type licenses arbitrary Android effects. Require strict correlation nonzero and unique among all simultaneously outstanding invocation records; reject replayed, old-session, and duplicate reply IDs. Guest input remains exactly the full single checked `03` frame as required by Part 3.3.

**Negative review vectors:** guest emits a valid action and `OK` then traps; guest emits two actions; guest prints a forged status; valid status but host write fails; late callback after app shutdown; duplicate correlation ID; handler cancellation during action streaming; mismatched state schema; process death between action completion and commit. All must preserve previously committed state and avoid unsupported irreversible external effects.

**Scope distinction:** this framing specifies only COCK's event routing contract. Rendering semantics, accessible UI, persistence, Android lifecycle, JNI handles, permissions, device threads, and interaction behavior still require separately verified Brainfuck-authored gateway/runtime modules. No `NativeActivity` claim follows from a well-formed frame alone.


### 12.3 — Invocation completion, UI capability proof, and state commit

Part 12.2's action-then-status contract describes one **handler invocation**, not the lifetime of the Android application process. An app can process many events without exiting. Waiting for the entire app process to exit after each event would break event-driven operation.

- [ ] **Invocation boundary:** a trusted BF-authored dispatcher or BF-generated Android entry adapter owns a guarded call/return boundary for each handler. It can distinguish guest return, trap, cancellation, timeout and malformed output. A guest printing a status-looking `BFIO` sequence cannot synthesize an authoritative return. External build subprocesses additionally need host exit/stream-close evidence (Part 2.8); long-lived Android apps need verified **handler return and bounded output completion**, not whole-process exit.
- [ ] **Single action candidate:** after one checked kind `03` event frame, buffer at most one checked kind `04` provisional action for its fresh nonzero correlation ID. Disallow extra stdout, guest-printed status, duplicate action, and trailing bytes. The dispatcher creates the kind `02` terminal result after actual guest completion. An action followed by a guest trap never commits. An absent trusted result means **UNKNOWN / NO COMMIT**, even if the action bytes are syntactically valid.
- [ ] **Local commit point:** serialize v1 state/lifecycle transitions and recheck handler identity, matching correlation, schema, capability, available window/surface, and resource budget immediately before applying effects. For the v1 *local/reversible-only* profile, apply and acknowledge its one validated local action, then commit replacement state at a declared transaction point; if application fails before acknowledgement, retain the previous state and emit failure. Do not falsely promise that already rendered pixels or external observation can always be rolled back. Network, notifications, file mutations or other potentially irreversible effects remain unsupported by this atomic v1 path until a separately specified and tested acknowledgement, failure and idempotency contract exists.
- [ ] **UI capability proof:** before declaring the Stage E touch-counter app supported, use Part 12.4's `COCK-UI-BASIC-v1` specified event/action profile and independently verify its native rendering adapter, lifecycle, thread affinity, bounds checks and negative fixtures. A versioned capability name is **not** proof of working implementation; until device tests pass, return `UNSUPPORTED_CAPABILITY`. This is a *feature acceptance requirement* and does not permit changes to the existing `COCK-FRAME-v1` wire bytes in place.
- [ ] **Cancellation and restart:** cancelling queued work prevents invocation; cancelling in-flight work prevents commit unless a separately verified policy expressly handles races. Restart invalidates old correlations and queued events and uses the Part 3.5 empty initial-state default when persistence is absent. Stale actions after window teardown, navigation invalidation or surface replacement must not apply.
- [ ] **Negative fixtures:** forged status; action-then-trap; dispatcher crash; duplicate action; mismatched correlation; render failure before state commit; handler completion with the app process still alive; cancellation while streaming; stale surface after lifecycle change; and an irreversible OS action attempted under the unsupported v1 profile.

**Evidence boundary:** documenting the tests is not proof that Android input dispatch, rendering, native loading or state transactions have run successfully; record actual device evidence when implemented.


### 12.4 — Minimal `COCK-UI-BASIC-v1` event/action subprofile for Stage E

This defines the *smallest planned* native touch/text proof using the existing `COCK-FRAME-v1` envelope and `COCK-APP-ABI-v1` event/action payloads. It changes **no Brainfuck source instruction, frame header, terminal guard, or standard result length**. It is an optional capability profile; unimplemented capabilities still return `UNSUPPORTED_CAPABILITY`.

- [ ] **Registration:** `ui.touch` enables the touch-down event type `1`; `ui.text` enables the surface-ready event type `2` and text-replace action type `1`. Any other event or action type remains unsupported unless independently registered in a new compatible capability profile. The manifest must request the needed capability and declare a matching handler; the adapter must not synthesize an undocumented handler.
- [ ] **Touch event:** kind `03` with `event_type=1`, `event_data_len=8` and exactly two `u32` little-endian integers `(x, y)` in **physical window pixel coordinates**, origin top-left. The adapter responds only to one verified primary `ACTION_DOWN` in a currently live input window; floor valid nonnegative finite platform coordinates, reject outside-surface/overflow/unavailable-window values, and do not silently substitute zeros for invalid float input. Multi-touch, text input, gestures and accessibility actions need separately specified and tested capabilities.
- [ ] **Surface-ready event:** kind `03` with `event_type=2` and `event_data_len=0`, delivered at a verified ready/window-owned lifecycle transition for initial rendering. Surface destruction/replacement invalidates pending render actions; lifecycle clean-up still happens in generated native runtime whether or not a source handler exists.
- [ ] **Text-replace action:** kind `04`, `action_type=1`, `action_flags=0`. Action-body bytes are `u16 profile_version=1`, `u16 reserved=0`, `u32 text_len`, then exactly `text_len` bytes of printable ASCII (`0x20`..`0x7E`), with `action_data_len=8+text_len` checked for overflow and configured output budget. The UI effect is replace the single basic window label and request an event-driven redraw. Length zero clears the label. UTF-8 beyond ASCII, multiline layout, complex widgets, accessibility semantics and rich text require separately versioned/verified capabilities; this small profile is **not** a universal UI limit.
- [ ] **Renderer ownership:** the native `NativeActivity` entry/lifecycle adapter, surface handling, primitive text rasterization and draw logic are BF-generated from eight-command BF-authored algorithms and optional validated non-executable glyph/asset data. Android OS/NDK surface APIs are permitted platform services. An opaque precompiled app renderer or an untracked conventional-language UI library providing COCK app-specific executable logic cannot satisfy production purity.
- [ ] **Commit:** a successful draw/acknowledgement and still-valid surface are prerequisites for committing the returned opaque state under Part 12.3. A surface-lost race or native drawing error fails the action and retains prior state; do not represent redraw visual side effects as mathematically reversible. Rendering speed, font appearance, accessibility and device support remain **UNMEASURED / NOT DEVICE-VERIFIED** until later milestones.
- [ ] **Stage E minimal counter fixture:** initial empty prior state means numeric counter zero in this example; after touch, a BF-authored handler may return an 8-byte little-endian counter and updated ASCII text, using exact modulo-`2^64` example-counter arithmetic. The example's counter encoding is *app data*, not a global mandatory state layout or another BF instruction. Test initial render, one touch, repeated touches, rotation/window recreation, cancellation and deliberate failed redraw against the source/ABI oracle.
- [ ] **Required negative vectors:** event type `1` with 7 or 9 event-data bytes; invalid/out-of-window coordinates; event type `2` with nonempty data; text version `0`/`2`; nonzero reserved value; declared length mismatch; byte outside printable ASCII; text requested without `ui.text`; touch without `ui.touch`; stale surface; forged status; guest trap after valid action; oversized text and interrupted drawing. No rejected frame can commit replacement state.

**Phase boundary:** implementation and device testing of this byte contract are authorized as part of Stage E after prerequisite capabilities are available. A supported Android UI can be claimed only after the required event/action, lifecycle, rendering and device acceptance tests pass; Stage A authorization alone does not prove Stage E functionality.

### 12.5 — Failure visibility and one-action state/visual consistency

**Clarification:** Part 12.3 guarantees atomic **logical state commit**, not exactly-once rendering, visual rollback, durable persistence, or a generic transaction across Android APIs. Android windows may show pixels before a later process crash. Design review must be able to tell a successful state transition from an uncertain visual effect.

- [ ] Per event invocation distinguish `RECEIVED`, `HANDLER_COMPLETED`, `ACTION_VALIDATED`, `EFFECT_ACKNOWLEDGED`, `STATE_COMMITTED`, `FAILED`, and `UNKNOWN`. Only the trusted dispatcher changes authoritative logical state. A guest cannot advance the state machine by printing a plausible status frame.
- [ ] Require one nonzero fresh correlation ID, one checked action maximum, verified handler termination, one dispatcher terminal result, a live surface/window and checked capability before any effect. The action must not run just because bytes are well-formed. A no-op action (`type=0`) can acknowledge without rendering; a text-replace action (`type=1`) can acknowledge only after the registered renderer reports its declared local outcome.
- [ ] Do not claim rollback of **observed pixels**. If rendering occurs but the acknowledgement/commit path fails, retain old logical state, mark visual state `UNKNOWN`, invalidate the pending correlation and schedule a safe full redraw from committed state when the surface is again valid. This is a recovery policy, **not** proof that no user saw the intermediate pixels.
- [ ] Serialized FIFO applies to admitted per-application invocations, **not** an undocumented guarantee that Android delivers every input event once or in a fixed global order. If input is dropped, coalesced, queued under backpressure or cancelled before admission, record it under the event adapter's explicit policy. Prevent a cancelled, stale or repeated action from modifying state after a newer window generation.
- [ ] Persistent restart recovery, filesystem changes and network requests have no v1 all-or-nothing guarantee; they require separate capability-specific durability/idempotency review. Failure to support those advanced actions must result in `UNSUPPORTED_CAPABILITY`, never a fabricated `OK`.
- [ ] Negative fixtures: renderer displays text then process dies before commit; dispatcher reports `OK` without actual handler return; surface generation changes after validation; state schema changes during a pending action; two identical correlation IDs; a no-op without renderer; cancelled event is delivered late; state commit succeeds but host later loses the process. Report exactly which guarantee still holds and mark external side effects `UNKNOWN` when appropriate.

### 12.6 — Capability registry, device-proof and failure-reporting minimum

- [ ] **Registry record per supported feature:** exact capability ID and version, manifest/API/ABI requirements, BF-authored handler/gateway source owner, dependency closure, permitted event/action payload grammar, platform service dependencies, lifecycle/thread behavior, failure/partial-effect policy, resource budgets and a list of independent negative/device tests. **Registered/design-only** is not **implemented**; unsupported requests always fail explicitly.
- [ ] **UI Stage E proof is narrow:** `COCK-UI-BASIC-v1` certifies only its validated pixel-input and printable-ASCII text action when actual on-device trials pass. No implied keyboard, rich widgets, complex-layout, app-store accessibility compliance, persistence or arbitrary JNI support. A demo generated by a conventional app renderer cannot become a COCK-pure Stage E claim by labeling its glue a transport adapter.
- [ ] **OS error separation:** document callback observed/queued/dropped, handler result, transport completion, render-acknowledgement, state commit, and external side-effect uncertainty independently. Do not conflate process lifetime with invocation completion, and do not call an externally observed visual effect rollback-safe merely because internal state was reverted.
- [ ] **Device release matrix:** for every advertised API/ABI/OS/page-size/target-SDK/channel row, record installed package hash, signed-scheme verification, actual device or emulator, native loading, frame round trip, lifecycle and negative test results. An untested row is `NOT VERIFIED`, not inherited from a different phone.

### 12.7 — Android callback threading and bounded guest execution

- [ ] **Never execute untrusted/unbounded BF guest loops synchronously inside a platform callback that must return promptly.** The BF-generated native gateway copies only the required event bytes and validated, invocation-scoped handles while they are live, then queues guest evaluation on a declared worker/executor path with bounded execution fuel and/or a separately enforced timeout. Where an API mandates callback-thread work, perform only its documented minimal setup/acknowledgement there; unsupported scheduling or lifecycle arrangements must fail explicitly.
- [ ] **Thread ownership is per capability:** document where `ANativeActivity` callbacks, input-queue operations, surface locking/drawing, JNI attachment, and native resource release must execute. Marshal any UI operation to the required valid owner thread, check the surface generation again immediately before applying effects, and never dereference a stale native pointer merely because a handler carried its integer ID.
- [ ] **Timeout and cancellation have two independent levels:** a BF guest instruction/fuel limit preserves Part 2 guest-command accounting, while wall-clock watchdogs, process death and external forced stops are *host/device observations*, not synthetic guest traps with deterministic source offsets. Failure to observe a trustworthy completed guest return makes the action/state `UNKNOWN / NO COMMIT`. A nonterminating handler must not indefinitely stall the app's lifecycle, event admission, or shutdown.
- [ ] **Backpressure:** each application has a declared finite event-queue capacity and explicit drop/reject/cancel policy. Preserve FIFO among admitted events, never invent global Android delivery ordering, and ensure rejected events cause no guest work or state commits. Test slow/infinite guests, lifecycle destruction during queued work, surface replacement, callback reentrancy, watchdog termination, and duplicate/late responses on representative devices.

**Proof boundary:** this threading rule is a capability/Android safety condition, not a claim that native glue, workers or watchdogs have been implemented. Stage A only needs the minimal callback/lifetime behavior required by its chosen guest subset and real device proof; broad event scheduling belongs to later capabilities.

# PART 13 — PERFORMANCE, SIZE, AND RELIABILITY POLICY

**Scope and precedence:** This part defines **outcomes, measurements, and high-level build policies**. Part 14 is the sole detailed authority for compiler/interpreter performance mechanisms; Part 15 for optional optimization selection and caching policy; Part 16 for generated-APK dependency closure and cost attribution; and Part 17 for acceptance/promotion decisions. In case of overlap, use those specialized parts and the locked semantics in Part 2. Avoid implementing duplicate policy engines from repeated wording.

Optimize for the **smallest correct application that satisfies its actual requirements**, not the smallest application regardless of functionality. There is **no global APK-size target** such as 256 KiB, 512 KiB, or 1 MiB. A 50 KiB app is acceptable if complete; a 500 MiB app is acceptable if its requirements justify it and the target platform can install and run it. Never pad output to meet a size target, and never omit required features merely to satisfy a nominal size number.

Measure at least: APK size, compressed versus uncompressed bytes, installed footprint, binary sections, dependency/module contributions, build time (clean, incremental, and cached), compilation throughput, executed Brainfuck instruction count, interpreted throughput, allocation count, peak toolchain memory, toolchain/interpreter executable size, launch time, runtime memory, CPU when idle/active, response latency, and crashes/errors. Record target hardware, inputs, compiler/profile versions, optimization modes, and cold/warm conditions.

For each build, report feature-dependent cost and highlight unusually expensive components. Enable dead-code elimination, unused-module stripping, deduplication, constant optimization, streaming serialization, reuse of Android system libraries, and selective compression where correct and beneficial. Attribute output bytes to payload, native code, mandatory runtime/metadata, resources, assets, compression, alignment, signing, and avoidable overhead wherever the formats permit reliable accounting.

Provide **orthogonal** policy dimensions: (a) compilation effort `fast-dev`, `balanced`, or `release`, and (b) primary output objective `size`, `speed`, or `balanced`. A build may also define optional per-target limits or priorities for cold startup, peak memory, responsiveness, battery/power, installed size, and build wall time. These are **trade-off policies, not functional capability restrictions**. No optimizer may weaken safety, purity, or correctness. A build-budget expiry may skip optional optimization passes, but it must never skip required generation, validation, secure signing, or requested functionality.

Resource budgets must be configurable per build or deployment and enforced to prevent runaway compilation, denial-of-service, integer overflow, memory corruption, or resource exhaustion. A security budget is not a permanent product-wide app-size cap. When a limit is reached, give an actionable, accurate diagnostic instead of silently changing program semantics.

# PART 14 — COMPILER, INTERPRETER, AND TOOLCHAIN PERFORMANCE REQUIREMENTS

**Goal and priority.** Build the fastest practical, smallest practical, and most memory-efficient **correct** implementation for its workload. Correct `COCK` behavior, security, traceable Brainfuck authorship, Android compatibility, and required functionality outrank performance. Do not claim "fastest" without reproducible competitive measurements. Speed, size, and memory are distinct targets; measure trade-offs rather than assuming any one technique improves all three.

### 14.1 — Fast frontend and compact intermediate representation

- [ ] Scan the original eight-command source efficiently, validate illegal bytes and unmatched brackets, and avoid unnecessary string copies or token allocations.
- [ ] Precompute bracket partners with a scalable checked stack or equivalently correct method; give loops direct jump targets instead of rescanning source on every iteration.
- [ ] Use a compact, versioned IR with operation kinds, checked operation counts, branch targets, and optional source mapping; prefer streaming or bounded-memory passes on large programs.
- [ ] Combine runs of `+`, `-`, `<`, and `>` only when intermediate pointer-boundary checks, tape-growth behavior, and observable errors remain correct; retain enough information to enforce these semantics.
- [ ] Recognize clear loops, transfer loops, and other common patterns only after proof or differential tests show equivalence under the locked profile; leave unsupported patterns unoptimized.
- [ ] Keep analysis and optimization passes proportional to proven benefit; make costly passes optional for fast development builds.

### 14.2 — Fast Brainfuck interpreter

- [ ] Predecode and validate once where feasible, reuse computed bracket targets, and avoid repeated decoding and symbol lookup inside the dispatch loop.
- [ ] Benchmark stack-based, register-based, direct-threaded, or specialized internal instruction representations only if their actual implementation is feasible and semantics remain unchanged; no representation introduces a ninth source command.
- [ ] Minimize dispatch, branch, loop-test, tape-access, and allocation overhead in measured hot paths.
- [ ] Use compact instruction and jump tables, efficient pointer arithmetic, and safe tape growth with checks appropriate to the locked profile.
- [ ] Keep the build-tool interpreter distinct from the optional on-device interpreter; never ship an interpreter in a generated APK without an application requirement.
- [ ] Treat JIT compilation as optional and demand evidence that its speed gain exceeds compilation cost, memory cost, security surface, and binary-size increase; prefer AOT for normal production builds.

### 14.3 — Fast AOT compiler and native execution

- [ ] Compile verified Brainfuck-authored toolchain modules to native executables using the Brainfuck-authored AOT path once it is operational and compatible with the selected execution host/target; retain reference interpretation for conformance and bootstrapping.
- [ ] Provide fast-development and optimized-release modes, plus independent `size`, `speed`, and `balanced` priorities without changing functionality.
- [ ] Minimize generated instruction counts, redundant tape loads/stores, unnecessary branches, call overhead, and helper dependencies only when semantics and target ABI remain valid.
- [ ] Support selective inlining, constant folding, dead-code elimination, and loop specialization with testable safety conditions and measurable impact.
- [ ] Use checked symbols, relocations, branch distances, alignment, and format offsets; improve code locality and avoid output padding that lacks a platform justification.
- [ ] Track costs of each pass, and disable an optimization when its compile-time or output-size penalty outweighs its measured benefit for the requested mode.
- [ ] Keep a low-overhead baseline compiler path that remains usable when no profiles, cost models, caches, or expensive optimizers are available; the advanced pipeline must not become a prerequisite for making a correct APK.
- [ ] Keep both cold-build and warm-build costs visible; a technique that is fast only with a populated cache must never be advertised as a universally fast clean build.

### 14.4 — Incremental builds, caching, and dependency scheduling

- [ ] Build a dependency graph from the actual application source, configuration, modules, target SDK/ABI, and requested assets; reprocess only changed nodes when correctness can be guaranteed.
- [ ] Implement content-addressed caching of validated IR, compiled modules, and non-secret generated artifacts keyed on source bytes, the locked `COCK` profile, tool versions, target ABI/API, optimization flags, dependencies, and relevant build inputs.
- [ ] Invalidate stale or corrupt cache entries; verify cached artifacts and record their Brainfuck-generation provenance. Never use caching to hide conventional-language production work.
- [ ] Consider parallel work only for truly independent modules when parallelism, communication, resource use, and deterministic output order are demonstrably safe and beneficial.
- [ ] Add fine-grained invalidation when validated dependencies permit it, but avoid expensive graph bookkeeping for trivial projects; always retain a correct coarse-grained fallback.
- [ ] Cache reusable **pre-signing** artifacts by default, and keep private keys and signing secrets out of caches and logs. Any cache serving a signed output requires an explicit, independently validated security/reproducibility model; never reuse a stale signature after modifying APK bytes.
- [ ] Compare clean versus incremental and cache-hit builds; never sacrifice deterministic correctness for a benchmark number.

### 14.5 — Memory, startup, and minimal output

- [ ] Use checked, demand-driven tape and buffer allocation; compare contiguous and segmented backing stores on representative workloads.
- [ ] Reuse scratch cells and bounded temporary regions, minimize copies and pointer chasing, and stream or spill large binaries when practical.
- [ ] Keep build-tool memory and generated-application memory independent; the large toolchain must not be bundled with every APK.
- [ ] Reduce startup work and dependencies, load only required modules, and eliminate unused runtime code, assets, and resources.
- [ ] Choose compression, binary packing, link-time techniques, and optional modules by measured total costs—not binary size alone.
- [ ] Account for real APK/ELF/ZIP alignment, Android startup/linker requirements, signing data, compression behavior, and target-device constraints; do not mislabel required platform overhead as removable bloat.
- [ ] Exclude dormant toolchain features, compiler optimization metadata, build-time profiles, test instruments, and optional app interpreters from installed outputs unless the application specifically requires a runtime equivalent.
- [ ] Preserve memory safety and resource-error contracts when hoisting, merging, or removing memory operations.

### 14.6 — Benchmarks, performance gates, and optimization correctness

- [ ] Maintain reproducible microbenchmarks: arithmetic, loop-heavy code, tape scans, nested loops, binary I/O, source parsing, and large sparse/contiguous tapes.
- [ ] Maintain end-to-end workloads: tiny, medium, and larger application builds; native-only and DEX-requiring builds; cold and warm builds; install and startup; idle and active event handling.
- [ ] Measure compiler throughput (source bytes and Brainfuck operations per second), interpreter executed commands/second, compilation pass costs, peak memory, allocation count, generated size, application startup, and runtime latency.
- [ ] Record environment, tool versions, hashes, benchmark inputs, iteration counts, and raw observations; distinguish measured outcomes from estimates and unverified goals.
- [ ] Compare reference interpretation against optimized interpretation and AOT execution with differential/property-based tests, including EOF, `0x00`, `0xFF`, pointer boundaries, wrapping, malformed source, tape growth, and resource failures.
- [ ] Establish per-target baseline measurements and configurable performance-regression alerts. Treat regression thresholds as diagnostic quality gates, never universal program-size or feature-count limits.
- [ ] Compare optimizers to a frozen, correct baseline under matched inputs/hardware; measure both total build cost and application lifecycle cost, not only hot-loop throughput. Show distributions or repeated-run ranges rather than overinterpreting noise.
- [ ] Identify non-dominated configurations rather than inventing a universal best optimizer; record any speed-for-size, size-for-build-time, or startup-for-memory exchange explicitly.
- [ ] Do not merge unverified optimizations or declare speed, memory, or size improvements without a repeatable measurement and a correctness test.

### 14.7 — Practical fast/small compiler-and-interpreter checklist

The following list translates *general compiler engineering* into the actual eight-command language. **Prioritize top-to-bottom within each stage; check an item only when tested.** Keep unimplemented advanced features marked **deferred**, not "done."

**A. Source handling and parsing — mandatory early**

- [ ] Validate the Part 1 annotated source grammar; accept only safe comment lines and whitespace outside instruction lines; reject illegal bytes and unsafe annotations.
- [ ] Scan once when memory and streaming constraints permit; maintain source offsets for exact errors; allow bounded/spilled scanning for large input.
- [ ] Build matching bracket pairs using a checked stack; detect too many closing brackets and unmatched opening brackets with exact offsets.
- [ ] Represent only what BF needs: operation kind, safe run/count, original source range, paired jump, optional flags and measured execution counts.
- [ ] Avoid the allocation cost of token objects, generic AST nodes, Pratt parsers, complex symbol tables, and type checking for BF programs.

**B. Interpreter dispatch — mandatory baseline, optional fast path**

- [ ] Maintain readable reference behavior and exact guest logical state/error transitions.
- [ ] Predecode byte operations and bracket targets once; benchmark whether decode time is amortized for tiny versus large runs.
- [ ] Minimize guest tape indexing, allocation, branch dispatch, host I/O transitions, and repeated bounds work without dropping traps.
- [ ] Explore compact bytecode, jump-table or specialized internal decoded operations only if BF-authored production implementations can actually emit/use them.
- [ ] Use inline caching or superinstructions only when the encoded instruction semantics, fuel accounting, setup cost, and memory increase are measured and justified.
- [ ] Keep JIT, speculative execution, deoptimization, and multi-tier dispatch optional research rather than startup dependencies.

**C. AOT lowering — mandatory baseline, measured improvements later**

- [ ] Emit correct AArch64 operations for all BF source commands, including nested loops, byte input/output, tape movement, wrapping, and errors.
- [ ] Provide portable/compatible generated runtime helpers for tape growth, checks, and I/O; omit unused helpers from each app.
- [ ] Preserve AArch64 calling convention: stack alignment, callee-saved registers, position independence, symbol visibility, and correct Android/Bionic imports.
- [ ] Fix branches and relocations using checked size/offset arithmetic; keep source-to-native mappings for verification.
- [ ] Offer an `O0`-like correctness/fast-build path and only *independently demonstrated* safe rewrites for higher modes.
- [ ] Measure simple run encoding, zero/clear-loop and transfer-loop recognition, safe pointer-range analysis, known-constant propagation, and code-size-aware inlining individually.
- [ ] Treat loop transformations requiring complex proofs, architecture-specific tricks, register-allocation engines, or profile-guided placement as optional, not foundational.

**D. Memory and I/O — mandatory correctness, measured implementations**

- [ ] Distinguish guest tape, BF-host interpreter tape, compiler scratch space, and the on-device runtime; report each relevant peak independently.
- [ ] Use checked offsets, explicit lifetimes, reusable scratch windows, and demand-driven zero-initialization.
- [ ] Decide between contiguous and segmented tape on measured workload data; preserve the logical budget check on pointer movement regardless of allocation strategy.
- [ ] Stream source/intermediate/output data in bounded chunks when beneficial; never require every output artifact to fit in an 8-bit-cell tape at once.
- [ ] Use a versioned framed protocol for multi-file build inputs and event streams, but leave raw `,` and `.` semantics unchanged.

**E. Fast development and small artifacts — mandatory process goals**

- [ ] Provide one-command source validation, a minimal BF-only reference run, **Stage A BF-in-BF nested self-hosting plus compiler execution** and a source-language audit from the first acceptance gate. Add AOT smoke builds and independent artifact inspection as target support becomes available.
- [ ] Keep mode selection simple: `fast-dev` with only mandatory passes, `balanced` with cheap validated passes, `release` with eligible measured optimizations.
- [ ] Make optimization objective independent: `size`, `speed`, or `balanced`; add startup/memory/energy priorities only with evidence and explicit policy.
- [ ] Build only reachable runtime modules and used assets; never embed build planner, compiler, test harness, optional VM, or profiling data without a feature need.
- [ ] Give clear actionable failures (bad byte offset, bracket mismatch, exhausted logical budget, unsupported ABI/relocation, invalid Android packaging/signature, no host backend).
- [ ] Avoid generic compiler or VM frameworks whose maintenance and runtime cost exceed their measurable benefit.

**F. Verification and quantitative promotion — mandatory gates**

- [ ] Golden output tests for BF byte semantics and generated binaries; fuzz brackets, pointer/fuel traps, I/O, large operands, and malformed ABI/format input.
- [ ] Differential-test reference versus BF-in-BF interpreter versus optimized interpreter versus native AOT; compare bytes, logical state, declared errors, and deterministic budget cutoffs.
- [ ] Benchmark *clean* build latency, *warm* build latency, dispatch rate, executed original BF commands, startup, peak guest/tool/runtime memory, generated size, battery where measurable, and Android install/startup separately.
- [ ] Run the same workload, target ABI, configured resource budgets, and recorded machine conditions; publish raw results with uncertainty rather than percentages without baselines.
- [ ] Disable/defer any optional feature with unclear benefit, hidden production implementation, poor maintainability, or failed safety/equivalence tests.

### 14.8 — Easy-to-develop pure-BF engineering workflow

**Eight-command repository executable purity DOES apply to test code, test launchers, debug drivers, adapters and other development algorithms.** Documentation and passive data need not be Brainfuck instructions; unmodified editors, debuggers, binary inspectors, Android platform tools and standard BF root executors must be installed and run **outside** the source repository. No foreign executable source, script or vendored development code may be committed.

- [ ] Keep small annotated `.bf` source modules with clear contracts: entry tape layout, input/output framing, cells modified/preserved, error states, and time/space scaling.
- [ ] Provide a **single documented smoke-check entry point** implemented in annotated `.bf` (for example, `devtools/smoke.bf`) that validates source grammar and runs BF-authored oracle goldens, including the **Stage A BF-in-BF compiler execution chain**. A README may document how to invoke an externally installed BF executor and independent inspection tools, but no shell/Python/Makefile wrapper or other language implementation belongs in the repo.
- [ ] Ship a tiny **first-contribution path**: one BF primitive, one fixture with binary stdin/stdout, one expected trace/error, and one command to validate it. Record the actual invocation and observed result; do not require a full APK build for every primitive change.
- [ ] Store **non-executable** human-readable cell maps, register descriptions, source-byte-offset annotations, call diagrams, architecture notes, and verified example traces in `docs/` or `devtools/`.
- [ ] Provide BF-authored `.bf` validators, byte-level visualizers, step-through traces, bracket maps and tape-state inspection where implemented. For native disassembly/ABI/package/device checks use preinstalled **independent external tools** without checking in scripts, plugins or foreign source. BF-authored in-repo tools must never forge independent native/device evidence or modify production executable bytes on behalf of the compiler.
- [ ] Make human-readable `#` comment lines and code indentation standard for every authored `.bf` file; never allow comments to contain BF commands or permit macros/DSL/source rewriting to become hidden production executable logic.
- [ ] Organize test fixtures by exact input `.bf`, binary stdin, expected stdout, expected errors, selected budget/profile, and required proof target (reference, BF-in-BF, AOT, Android device).
- [ ] Track commands and real output from each stage; keep sample fixtures small and varied before attempting large programs or full Android builds.
- [ ] When a new abstraction is proposed, first show the simpler no-abstraction alternative, expected runtime/build/memory cost, maintainability impact, and correct fallback.
- [ ] Make unavailable tools, unrun tests, target-only results, performance unknowns, and production-incomplete steps explicit in every milestone report.
- [ ] **Developer-cost budget:** keep an auditable per-slice count of BF source bytes, executable BF commands, touched tape cells, independent fixtures, supporting files, review/debug hours (where measurable), baseline compilation time, and incremental maintenance burden. Simplify or split a slice when an abstraction increases this cost without reducing a proven failure rate or improving measured output. Readable annotations may document cells; they do **not** permit preprocessing a macro language, foreign code generation, or an executable DSL into BF.
- [ ] **Operator-friendly diagnostics:** every checked failure returns an exact source offset where known, selected profile/subset, unsupported command/capability, failure phase and relevant configured resource budget. Every in-repo formatter/visualizer is BF-authored; externally installed tools may display facts from declared host/OS boundaries but may not invent success or rewrite emitted bytes.
- [ ] **Bounded draft review:** before executing the consolidated test batch, inspect only the specification, full file inventory and interface consistency; a newly discovered mandatory platform impossibility sends the slice back to design/replanning, not into covert implementation testing during drafting. Preserve the required draft-all-files-then-test-all-files user workflow without treating fewer tool calls as a correctness metric.

**Non-negotiable principle (Parts 2.1–2.2):** Optimizations must not silently skip observable intermediate actions. Zero-net movement cannot erase left-boundary faults, deterministically specified logical budget checks, or optional guest-fuel cutoffs. Handle physical allocation failure safely without assuming identical timing across allocators. Internal decoded operations or cached artifacts never change the eight-command Brainfuck language with safe annotations or global production authorship rules.

### 14.9 — Minimal compiler/interpreter acceptance ladder

**Use this as independent component acceptance checks with a mandatory Stage A self-hosting dependency.** The **L0 source gate and L1 BF-in-BF execution of itself and the actual mini compiler are chronological prerequisites for Stage A acceptance**; the rest of the full guest-language/interpreter feature suite may grow later. Multi-file input remains unnecessary for one-file Stage A input. A capability is done only after its own real tests and artifact evidence exist.

- [ ] **L0 — source gate:** BF-authored annotated-source validator and separate BF-authored reference oracle accept legal whitespace/comments, reject unsafe annotation glyphs, illegal bytes and mismatched brackets, and check golden byte-output/error/trace/source-offset fixtures from Part 2.3. External independent BF executors may supply additional comparison evidence without repository source.
- [ ] **L1 — mandatory Stage A self-host gate:** annotated BF-in-BF interpreter running on an externally installed standards-only BF host passes the actual mini compiler as guest, correctly handles the subset of `COCK` semantics and budgets the compiler needs, and proves **one bounded nested BF-in-BF self-interpretation level**: outer BF-in-BF executes its own source as an inner interpreter which runs the same mini compiler with **byte-identical compiler outputs** against independent BF-oracle expectations. Include nested loops, source/input closure, EOF and error/termination tests needed by that compiler; later broaden the interpreter to the complete Part 2 fixture suite. No Stage A compiler is accepted before this proof.
- [ ] **L2 — decoded-VM gate:** validate and predecode guest source once where worthwhile, then compare decoded execution against L0/L1 for exact I/O, input consumption, guest state/status, traps, and cutoff behavior.
- [ ] **L3 — baseline AOT gate:** a **Brainfuck-authored** generator emits correct instructions for all eight commands and tested loop patterns; independently disassemble/execute with a declared OS/ABI, validate branch fixups and byte I/O, and compare against L0.
- [ ] **L4 — optimized AOT gate:** introduce **one** optimizer pass at a time, with explicit preconditions and forced-fallback cases; test source/IR/native mappings, deterministic traps/fuel cutoffs, and cold/warm compiler cost before enabling it.
- [ ] **L5 — artifact gate:** in Stage A validate the generated ELF/native code, Android install/launch and clearly labeled external **debug** packager/signature; check full manifest/DEX/resource variants and native BF packaging only when those features are implemented. Only Stage D passes the full production-signing gate.
- [ ] **L6 — product gate:** build two different input-driven apps through the same declared ABI, with real event dispatch and resource inclusion; test lifecycle and memory; measure cold build, cached build, startup, runtime throughput/latency, installed bytes, and APK breakdown.
- [ ] **L7 — maintenance gate:** keep one-command smoke and regression entry points, deterministic fixture generation and hash manifests, reproducible baseline comparisons, platform-compatibility matrix, and a separate list of deferred/untested capabilities.

**Exit rule:** failure at a mandatory gate blocks claims about dependent functionality, but not independent prototypes. A pass that improves one metric while worsening another must show the exact workload/policy under which the trade-off is accepted. Never award completion credit for documentation alone.

### 14.10 — Falsifiable performance and small-binary measurement contract

**No universal invented benchmark score is a development gate.** The claim is **measured quality relative to a named correct baseline, a declared workload and target budget**, with reproducible raw data. Until real measurements exist, report `UNMEASURED`, even if the design looks efficient.

- [ ] Publish a minimal bench suite with explicit seeds, input/output hashes and timeout/resource bounds: (i) empty and one-byte BF source startup, (ii) long linear `+/-` arithmetic, (iii) loops with many iterations and nested loops, (iv) sparse far-right tape travel, (v) byte streams including `00/FF`, (vi) invalid complete input and trap/fuel cutoffs, (vii) changing versus unchanged build inputs, and (viii) **two materially different target APK manifests** after Android generation exists. Include at least one workload with intentionally little optimization opportunity so pass setup tax is visible.
- [ ] Measure separately (a) complete-source acquisition/preflight, (b) parse/IR, (c) optimize, (d) native codegen/link or VM decode, (e) package/sign/check, (f) process/device cold startup, and (g) steady-state execution. Avoid reporting just guest instructions/s as total end-user time. Keep compile-host, generated host-tool, guest execution and Android-device memory/CPU in separately labeled columns.
- [ ] For every comparison provide at minimum the exact runnable command/protocol, toolchain and source hashes, OS/ABI/API, host and device characteristics, compiler/executor, selected budgets and pass registry versions, outputs, cold/warm cache definition, sample count, failures and raw samples. Prefer at least **3 fresh/cold** and **10 repeated/warm** observations where feasible; if the environment does not support that, say why and do not present strong regression claims.
- [ ] Report median and tail latency (at least observed p95 where sample count supports it), spread, peak memory, source/IR/native/APK bytes and installed footprint. State measurement uncertainty and thermal/noise limitations; compare matched runs and repeat apparent differences near noise. Numerical **acceptance budgets and allowable regressions are project/target configuration values** declared *before* comparing variants, not universal hardcoded COCK limits.
- [ ] A claimed improvement passes only if its runtime or footprint benefit is demonstrated on the target workload and its measured compilation/setup, validation, release-size, and memory costs are recorded. Under `fast-dev`, disabling optional passes is preferred when their cold cost outweighs the targeted improvement; under `release`, long compile cost may be accepted when the selected user objective justifies it. Correctness and security gates are still mandatory.
- [ ] Never use measured native speed to infer interpreter speed, or one APK's small size to assert a universal small app binary. Record optimizations individually before enabling combinations and stop at a non-dominated, reproducible, tested configuration within the chosen budgets.

# PART 15 — WORKLOAD-AWARE, BUDGETED OPTIMIZATION CONTROLLER

**Authority:** This part owns optimization **selection, cost policy, and incremental scheduling**. Use Part 14 for the implementation and tests of individual compiler/interpreter passes; Part 16 for output artifact cost accounting; Part 17 for promotion thresholds. Do not create parallel, inconsistent decision systems.

**Implement this progressively, after an independently verified baseline compiler exists.** The specification's optimization controller must not be a permanent tax on every compilation. A tiny or unchanged project should bypass analyses whose invocation costs exceed their plausible benefit. A larger hot-path-heavy application may justify more extensive passes. All normative production controller and optimization algorithms must themselves be Brainfuck-authored (and may subsequently run as verified Brainfuck-generated native tools).

### 15.1 — Separate hard constraints, objectives, and optimization effort

Support a versioned build policy with separate fields for:

- **Immutable constraints:** `COCK`, source purity, application behavior, error semantics, target ABI/API, Android requirements, required features, security invariants, and valid output artifacts. Never downgrade or reinterpret these to meet a target.
- **Compilation effort:** `fast-dev` (minimal optional passes and short feedback), `balanced` (cheap and profitable passes), or `release` (deeper and potentially profile-informed passes). Build effort is independent of the desired runtime outcome.
- **Output objective:** `size`, `speed`, or `balanced`, with optional declared weights/limits for startup, memory, battery/energy where measurable, installation footprint, and response latency. Weights guide decisions, not guarantees of a global optimum.
- **Configurable budgets:** per-build optional wall-clock/CPU, memory, cache, parallelism, and optimizer-work budgets based on real project/environment constraints. Distinguish an advisory pass budget from a hard resource/security limit.
- **Evidence:** baseline version, workload identity, target hardware/ABI/API, environment, cost-model version, profile provenance, optimization decisions, and confidence. Unknown evidence must be marked unknown, not guessed.

A low-overhead policy parser should choose a correct baseline path before invoking optional analysis. The policy itself is non-executable build data. A change in policy that influences output must invalidate affected cache entries.

### 15.2 — Per-pass benefit/cost decisions

Maintain a versioned optimization-pass registry. For each pass document its Brainfuck-owned implementation, applicable IR/ABI, prerequisites, purity/semantic proof obligations, estimated compilation time and memory, potential runtime/startup/size effects, feature interactions, regression tests, fallback, and cache effects.

- Prefer cheap static heuristics first (program length, instruction/loop counts, tape-access patterns, module dependency size, profile availability). Never require running a full expensive optimizer merely to discover whether to skip it.
- Estimate **net value across the selected objectives**, including the cost of the analysis and pass itself. Treat a prediction as a hypothesis until benchmarked.
- Apply more costly passes only when their preconditions hold, budgets allow, and available evidence supports their selection. Emit the selected/skipped pass list and why.
- Allow the controller to choose **no optional optimization**. Never perform speculative multi-variant compilation for a tiny application when the comparison cost dominates.
- If a pass fails, times out within its advisory budget, violates an invariant, or produces worse validated results, discard its result and use the last independently verified artifact. If underlying resource/security constraints make even the baseline impossible, fail accurately instead of silently omitting a feature.
- Use deterministic rules for production decisions; pin heuristics, profiles, cost-model versions, and any explicit tuning seeds so identical declared inputs can reproduce an output. Do not create unexplained clock-, machine-, or random-dependent artifacts.

### 15.3 — Workload-specific partial evaluation and specialization

Where inputs are known at build time, optionally specialize constant data, configuration, feature selection, API bindings, and parameterized routines without baking in unsupported assumptions about changing runtime input. Optimize safe Brainfuck patterns, including loop specialization, instruction-run combinations, direct tape access, code layout, selective inlining, and dispatch elimination. Keep generic implementations available when static facts cannot be proven.

A transformation is invalid if it changes observable byte I/O, pointer-boundary behavior, deterministically specified logical tape-growth/budget checks, wrapped-cell behavior, EOF behavior, declared event-order semantics, Android lifecycle obligations, errors required by the locked profile, or requested functionality. Physical allocation failure must remain safe and accurately reported but need not occur at an identical step for different allocators (Part 2.1). Net-zero pointer displacement alone does not justify eliminating intermediate movement. Differentially test rewrites under fixed logical budgets and run separate physical-allocation failure-injection tests.

### 15.4 — Profile-guided and offline auto-tuning (optional)

Introduce profile-guided optimization only after repeatable test workloads and validated code-generation paths exist. Profile data are non-executable observations; development test harnesses may gather and independently validate measurements, but the production profile consumer and optimizer must be Brainfuck-authored. Instrumentation inside a shipped app must be generated through the Brainfuck-authored production toolchain, be explicitly opted into, and not be shipped for ordinary release builds.

Prefer **offline, reproducible** autotuning over always-on runtime JIT or perpetual adaptive recompilation. For selected workloads, compare a bounded number of viable configurations; reject noisy or unverified results; store the non-dominated alternatives and select according to the declared policy. Freeze a reproducible chosen configuration for release builds. If a profile is missing, stale, mismatched to ABI/workload, untrusted, or statistically unconvincing, use the reference-safe non-profile path.

### 15.5 — Incremental builds and scheduling without framework tax

Use a demand-driven dependency DAG based on exact source, target, configuration, versions, imported modules, assets, resources, build-policy choices, and relevant profiles. Cache independently verified, content-addressed **pre-signing** artifacts. Reuse stable nodes only when all semantic and security dependencies match; validate corruption/missing artifacts and preserve auditable Brainfuck-generation provenance. Avoid including secrets in keys or recoverable logs.

Add function/section-level incrementality and deterministic parallel scheduling only after measurements show savings beyond bookkeeping, serialization, synchronization, and memory costs. Support a straightforward single-worker/coarse-cache route when the project is small or available RAM/CPU is limited. Rebuild and re-sign affected final artifacts correctly; do not assert that post-signing APK edits preserve a valid signature.

# PART 16 — MINIMAL GENERATED APPS AND END-TO-END COST ATTRIBUTION

**Authority:** This part owns the generated application's dependency closure, mandatory Android packaging, and independently inspectable size/installation cost reports. Compiler algorithms are specified in Part 14, build pass policy in Part 15, and the acceptance decision in Part 17.

**The generated APK pays only for the application, real Android/format requirements, and explicitly requested runtime capabilities—not for COCK being overengineered.** “Zero overhead” means *zero proven-unnecessary overhead relative to the required functionality and target*, never literally zero unavoidable platform bytes, time, or memory.

### 16.1 — Demand-driven inclusion and minimal execution paths

- Trace each required app capability to its actual closure of native functions, ABI glue, Android components, manifest declarations, resource entries, DEX classes/methods, optional runtime modules, assets, and permissions. Unused or unreachable elements must be excluded where safe.
- Distinguish compile-time-only modules (compiler, build driver, optimizer, cost model, profiler, verifier, packager, signer) from app runtime. No compiler, benchmark suite, build metadata, or optional interpreter is bundled by default.
- Prefer verified native AOT paths for static app logic. Include interpreted execution, dispatch/VM code, JNI gateway components, managed classes, background services, networking, graphics, or extra architecture slices only when their requested features need them.
- Allow a correct simple-app fast path without imposing fixed screen, package, module, or asset limits on larger apps. Additional app complexity must emerge from inputs, not from fixed templates.
- Preserve Android lifecycle, security, accessibility (where implemented/requested), compatibility, relocation, alignment, signing, and minimum required metadata. Do not delete necessary checks or incorrectly claim that all managed glue is avoidable.

### 16.2 — Artifact bill of materials and size accounting

For each generated app, produce a separate **build-side artifact cost report**, not necessarily packaged into the APK. Where reliable, list compressed and uncompressed ZIP entry bytes; native code/data/relocations; DEX and resource contributions; assets; manifest/metadata; signing structures; and padding/alignment. Identify reachable and stripped modules and permissions, the inclusion reason, source/provenance reference, and optimization decision. Account for ZIP container overhead and necessary platform constraints; unknown or shared costs should be reported transparently rather than fabricated or double-counted.

Measure **APK download size, installed footprint, launch and initialization cost, runtime memory, CPU at idle and under load, response latency, and (where available) energy use** separately. An APK can shrink yet install slower or consume more memory. A compiler can optimize a hot loop yet degrade clean-build latency. Report all material trade-offs.

### 16.3 — Cost-aware, compatibility-correct packaging

Select stored/compressed entries, alignment, native library placement, resource representation, and deduplication only after respecting the chosen Android target and signing scheme. Compression must not be assumed to be free; measure packaging time, installation/startup effects, and memory impact. Maintain correct ordering of generation, ZIP assembly, final alignment, and signing so no post-signing mutation invalidates integrity. Validate the actual target environment rather than assuming arbitrary ELF/ZIP extensions are accepted.

### 16.4 — Independent performance dimensions

Use distinct reproducible suites for: reference/interpreted/toolchain AOT execution; clean, warm, incremental, and cache-hit builds; first/cold and warm launches; tiny/medium/large configurations; code and data scaling; interpreter-needed versus native-only apps; static versus dynamic app behavior; and major Android ABI/API combinations when available. Include failures and pathological inputs, not only favorable microbenchmarks.

Compare to the smallest *correct* baseline that satisfies the same features. The output requirement is **no avoidable bloat**, not a fixed size in KiB or a forced win in every metric. Expose Pareto trade-offs and allow configuration to select among independently validated alternatives.

# PART 17 — COMPLEXITY GOVERNANCE AND OPTIMIZATION ACCEPTANCE

**Authority:** This part alone determines **when an optimization or architectural layer is promoted, deferred, or disabled**. It evaluates evidence generated under Part 14 (benchmark correctness), Part 15 (decision accounting), and Part 16 (APK effects); it must not reimplement their mechanisms.

For every proposed advanced feature, optimization pass, cache layer, parallel executor, compiler IR extension, runtime abstraction, or new build component, record an **engineering return-on-complexity decision** before enabling it by default:

1. **Need:** which real limitation or workload it addresses, and whether a simpler approach already suffices.
2. **Location:** whether it is build-time-only, development-only, optional app runtime, or mandatory app runtime. Prefer build-time-only wherever technically sound.
3. **Cost:** implementation/maintenance risk; cold and warm build overhead; CPU, memory, I/O and cache cost; binary, APK and installed footprint; runtime/startup/energy effects where measurable.
4. **Correctness:** exact Brainfuck-profile and Android invariants, dependency/security implications, independent differential tests, resource-error/negative tests, and fallback behavior.
5. **Activation:** scope, prerequisites, chosen workload classes, expected benefit, proof/evidence threshold, and cases where it should remain disabled.
6. **Outcome:** raw observations, variance/uncertainty, changed artifacts/hashes, independently verified improvements or regressions, and a keep/disable/rework decision.

**Promotion rules:**

- Keep a **correct minimal baseline** as the fallback throughout development. A new system is not justified simply because it is sophisticated.
- Enable a complex optional pass by default only when repeatable measurements show an acceptable *net* benefit for its targeted workload; preserve specialized opt-in paths for passes with narrower usefulness.
- Respect **Pareto non-dominance** rather than asserting a universal best configuration. A regression in one objective is permissible only when an explicitly selected objective or mandatory requirement justifies it, the regression is quantified, and configured limits are respected.
- Set per-target, user-configurable performance-regression alerts; handle benchmark noise and hardware variation. Do not invent strict numeric performance promises or arbitrary feature/output-size limits.
- If trustworthy data are unavailable, say **unmeasured**, fall back to the verified baseline, and retain the feature as experimental. Never represent theoretical potential as achieved speed, APK-size, memory, or build-time reduction.
- Stop adding overhead-producing machinery once its marginal net benefit becomes negative for the relevant workloads. Engineering scale is permitted; indiscriminate complexity is not the objective.

# PART 18 — SELF-HOSTING AND BUILD REPRODUCIBILITY

**Self-hosting is mandatory from the FIRST Stage A accepted compiler build.** Author the BF-in-BF interpreter in `.bf` as part of the initial slice, prove it can interpret **its own annotated `.bf` source as a guest and then execute the real compiler inside that interpreted copy**, and execute the real BF-authored mini compiler as a guest of that interpreter for every accepted Stage A Android build. An externally installed, unmodified standards-only BF evaluator may execute the BF-in-BF interpreter as the irreducible *root bootstrap*; the root evaluator is not source in the repository, not COCK build logic and not permission to skip BF-in-BF. A BF-in-BF demo interpreting a simple app while a separate conventional or directly root-executed compiler does the build is **NOT self-hosting**. Prove exact compiler input/output identity across at least two distinct programs and a held-out third, including one bounded root-host → outer BF-in-BF → inner BF-in-BF → mini compiler chain, show nested-execution provenance, and compare against the BF-only independent oracle and external ABI/device inspectors. Require BF-in-BF interpreter code to be genuinely BF-authored, and use the resulting chain to rebuild/execute relevant BF toolchain modules as they become available. Once a verified host-compatible BF-authored AOT path exists, it may accelerate this chain, provided the BF-in-BF bootstrap remains independently reproducible and the compiler execution identity is proven. Retain interpreter-versus-native differential tests and an auditable bootstrap path. No new document/protocol versions are required.

Keep a clear separation between original source, intermediate data, bootstrap execution, toolchain compilation, generated native code, and on-device app runtime. Self-hosting is a toolchain property; it is **not a requirement to embed the self-hosting compiler inside every application**.

For reproducibility, record source hashes, exact configuration, target ABI/API, module versions, binary generation steps, signing inputs (without exposing private keys), build-tool version, and independent validation results. Explain unavoidable nondeterminism explicitly.

Record all **optimization policies, pass implementations/versions, profile IDs and provenance, cost-model revisions, cache dependencies, feature-closure decisions, artifact attribution data, and tuning seeds if any** when they affect reproducible build output. A cache hit must not hide unverified or non-Brainfuck production work. Prefer release-policy pinning: the same declared inputs and fixed toolchain/profile set should select the same transformations and produce reproducible unsigned bytes where the file formats and environment allow it; describe signing-related reproducibility separately.

# PART 19 — SECURITY AND FAILURE REQUIREMENTS

Treat all input source, configuration, binary data, API requests, assets, signatures, and external callback payloads as potentially malformed. Validate lengths, offsets, arithmetic, nesting, file paths, encodings, symbol tables, ELF structures, ZIP metadata, DEX references, and JNI handles before use.

Require well-defined failures on malformed brackets, unsupported Android features, invalid permissions, missing symbols, relocation errors, allocation failure, incorrect signature keys, and OS compatibility mismatches.

Avoid unsafe writable-executable memory, uncontrolled JNI reference growth, use-after-free, double free, integer overflow, and asynchronous lifecycle races. Respect Android permission, process, storage, background execution, and signing models.

Treat cache metadata, telemetry, cost models, imported performance profiles, build policies, and optimizer-pass metadata as untrusted input. Prevent cache poisoning and incorrect dependency reuse; constrain parsing and optimization budgets. Do not allow profiling/configuration data to introduce hidden executable code, weaken source purity, leak signing material, suppress mandatory verification, or cause an optimizer to drop required checks.

Perform boundary testing, negative testing, randomized/property-based testing, reference-model differential testing, and independent binary inspection. Security-critical cryptography requires independently checked test vectors and practical audit before it is trusted for real production secrets. **Default all initial signing tests to disposable test keys; do not accept real release signing keys until the BF-generated signer has passed cross-tool vectors, corruption tests, side-channel/key-exposure review, and an explicit security gate.** Signing-key generation/entropy must use an approved, declared secure source; never improvise pseudorandomness inside BF as a substitute. Android AAB upload-key signing and Play App Signing have distinct responsibilities from direct-installable APK signing.

### 19.1 — Security trust boundaries and prohibited shortcuts

- [ ] Treat `BFIO` guard bytes as length/EOF sentries only, not tamper protection. On hostile channels, select a separately specified authenticated outer channel or BF-authored authenticated payload protocol; if neither is available, explicitly reject cross-trust communication instead of asserting the guard is secure.
- [ ] A BF host/executor, untrusted app handler, BF-generated dispatcher, device OS, signer, and independent test verifier are different authorities. Document which may attest guest completion, which holds credentials, which may finalize bytes, and how failures propagate. A self-printed success message is not independent verification.
- [ ] Never let external diagnostic helpers or profiles inject executable release bytes. External development-only debugging/signing is still allowed for the labeled test pathway in Part 21, with no upgrade to production-release status.

### 19.2 — Signing trust-boundary feasibility and crypto-release decision record

- [ ] Before *any* real production key is admitted, identify the key origin, entropy source, format, transfer into BF-addressable cells, executor isolation, extra host copies, side-channel exposure, memory clearing limitations, incident response, authorized signing identity, and whether key custody can satisfy the declared deployment threat model. ### 19.3 — Finalization authority and least-privilege physical services

- [ ] **Trust classification:** distinguish user-selected build inputs, BF-authored trusted planner/producer, untrusted guest-app output, conventional physical file/router service, Android OS calls, independent verifier and separate release/signing authority. # PART 23 — WORKING METHODOLOGY — BULK DRAFT → BULK TEST → BULK OPTIMIZE

**Purpose:** minimize AI usage-limit consumption, repeated context reconstruction, and tool-turn overhead. Each operation below applies to a bounded, independently deliverable feature slice. It is **not** an instruction to draft the entire COCK platform before obtaining feedback. Maintain the last independently verified compiler while building the next slice. The gates are sequential: no testing while drafting, and no optimization without a passing baseline.

- [ ] **Plan the entire slice first:** specify exact supported/unsupported behavior, target/ABI, **mandatory Stage A self-hosting proof** and observable acceptance; enumerate all required `.bf` executable source (including BF-only tests/debug adapters/oracle), inert fixtures/configuration and documentation files. Never inventory other executable source languages. Define interfaces and expected oracle results before creating implementations. Pick a size that can be drafted, diagnosed and retested within practical AI-usage and resource limits.
- [ ] **BULK DRAFT — complete every inventoried file:** write complete first-pass **BF-in-BF/interpreter/compiler/test/launcher/adapter** implementations as annotated `.bf`, together with contracts, inert fixtures and docs. Prefer grouped file creation/edit operations and a single consolidated change manifest. **Do not run implementation/unit/compiler/device tests, benchmarks or optimizers during this phase.** Drafted does not mean tested. If a required file is discovered later, update the inventory and finish the new draft before opening the test gate.
- [ ] **Draft completion gate:** confirm the inventory accounts for every file, that required functions/byte streams and test inputs are written, and that no unfinished placeholders are falsely presented as supported behavior. This is a *documentary readiness check*, not a runtime test or a PASS. Preserve an immutable or reproducibly restorable pretest snapshot and its input identity.
- [ ] **BULK TEST — run one coordinated acceptance batch:** execute all relevant lexer/source, byte-level, independent oracle, malformed-input, binary format, security, regression and available Android/emulator/device tests together. Record exact commands, target, output, failures and test artifacts. Mark unavailable tools/devices `NOT RUN`; tests not performed never pass by assertion.
- [ ] **Bulk repair loop:** group related failures, fix the affected files in one batch, and rerun affected tests followed by the whole slice acceptance suite. Repeat until all mandatory acceptance gates pass. If an unresolved critical bug, failing check or unavailable mandatory target remains, **STOP / BLOCKED**: do not optimize, integrate or represent the feature as working.
- [ ] **Establish a passing unoptimized baseline:** preserve the verified pre-optimization source and artifacts and record baseline build time, execution speed, memory, startup and APK/installed bytes wherever measurable. Missing measurements remain explicit; do not invent optimization benefits.
- [ ] **BULK OPTIMIZE — optimize together, then validate together:** profile the passing baseline, select a bounded set of justified transformations and their exact semantic preconditions, write the candidate changes as a grouped batch, then run the **complete differential, failure, security, platform and performance regression suite**. Individual transformation evidence must remain attributable; a batched speed gain cannot conceal a broken or unjustified pass. Revert failed/regressive changes to the verified baseline and retest. Optimizing is optional when no measurable benefit exists.
- [ ] **Integrate and preserve:** promote only a validated candidate, publish its evidence and keep the last known-working mini compiler available. Report output identity and every deferred/unsupported capability. Begin the next bounded feature slice with a fresh inventory.
- [ ] **Track five statuses separately:** `DRAFTED`, `IMPLEMENTED`, `TESTED`, `OPTIMIZED`, `INTEGRATED`. None is inferred from a file existing or from the absence of reported errors. An accepted unoptimized feature can be `TESTED` and `INTEGRATED` without `OPTIMIZED`.
- [ ] **Usage-limit discipline:** minimize needless incremental chat/test cycles, consolidate file writes, error reports and benchmark summaries, and save enough context in the on-disk evidence ledger for session handoff. Do **not** use quotas as a reason to hide failures, omit required tests, authorize untrusted signing or bypass Stage A/release acceptance controls.

**Simplicity rule:** stay with the smallest vertical slice that **self-hosts from the beginning** (BF-in-BF kernel actually running the restricted Android debug compiler), **not** a huge untested multi-stage rewrite or a direct-host compiler masquerading as self-hosting. The draft/test separation is deliberate, but a batch that cannot be reliably debugged is too large and should be reduced at the next slice boundary. Security and correctness outrank performance and token savings. No emulator/device means `NOT RUN`, never a claim of Android usability.

# PART 24 — INITIAL TASK AND EXECUTION RULES

**Development is authorized now.** The engineering agent may create source, tests, build tools and debug artifacts for Stage A immediately, following the documented feasibility and bounded-slice workflow. Do not treat this authorization as permission to falsely claim a finished or production-ready system.

**FIRST DEVELOPMENT ACTION: start Stage A with its mandatory minimal BF-in-BF self-hosting kernel, not a comprehensive compiler.**

- [ ] Select the narrowest independently supportable Android AArch64 target and simplest observable app behavior.
- [ ] Determine whether the simplest proof needs a NativeActivity `.so`, minimal manifest/resources, and which debug-only packaging/signing steps may be delegated to existing development tools.
- [ ] List **all Stage A files**, including the BF-in-BF interpreter, BF-only oracle/validation/test launcher and real compiler guest, before creating source implementations; reject any planned foreign-language source or script.
- [ ] **BULK DRAFT** every inventoried file, including complete human-readable annotation of every `.bf` file, **nested self-hosting test runners written in BF** and inert fixtures; finish first-pass implementations **without executing isolated or integration tests**. A draft checkpoint is not proof of correctness.
- [ ] Complete the **BF-in-BF interpreter and the BF-authored mini compiler as its executed guest**; capture input/output provenance and document any temporarily unsupported *application guest* BF instruction or Android feature. The nested interpreter itself must support whatever the real compiler executes.
- [ ] **BULK TEST** only after every slice file is drafted and implemented: run **BF-in-BF self-hosting, repository BF-only source audit**, BF-only source/oracle checks and externally installed independent native inspection, malformed-input and regression tests together, then build, install and launch development/debug APKs from two different BF app programs; group fixes and rerun the acceptance batch.
- [ ] Record actual observed behavior, file sizes, correctness failures, timings where measurable, and explicit `DEBUG-ONLY` dependencies; do not claim production purity based on external packaging.
- [ ] **BULK OPTIMIZE** only the verified unoptimized baseline: profile, apply a measured group of candidate improvements, rerun the complete regression and target suite, roll back failures, retain this working compiler as the default and begin the next Stage B–F **draft-all-files-first** upgrade.
- [ ] When BF-native packager/signing and full Android platform behavior are eventually implemented and independently proven, promote only the exact tested target to full COCK-produced status.

**FINAL MISSION:** COCK is a BF-only-code repository and becomes a truly **self-hosted from Stage A** scalable compiler/interpreter and Android build platform, beginning with the **smallest BF-in-BF interpreter that actually executes the BF mini compiler and can create a debug Android app**. Developers can use it immediately within its proven capabilities, rather than wait for the entire ambitious platform. All BF `.bf` source is annotated for humans; only the eight original commands execute. The toolchain adds features one small inventoried draft/test/optimize/integrate slice at a time. No fake completion, unsupported Android guarantees, unmeasured performance claim, arbitrary universal app-size limit, hidden conventional production compiler, or confusion between debug APKs and fully BF-authored releases. Every optional complexity must earn its cost in measured value.

# PART 25 — DEVELOPMENT READINESS, TECHNICAL ACCEPTANCE, AND EVIDENCE DISCIPLINE

**Purpose:** ensure the already-authorized development work produces a real, usable and reproducible Brainfuck-authored Android compiler. This part is a practical engineering checklist and issue-handling contract, **not a specification-score process or an implementation-start permission gate**. Begin Stage A now; only a specific feature's own safety, correctness or platform acceptance failure prevents declaring **that feature** complete or publishing its output. Unbuilt code, unrun tests and unmeasured performance remain explicitly unverified.

### 25.1 — Non-negotiable engineering invariants

- [ ] **BF-only entire-repository semantics and Stage A self-hosting:** all checked-in executable code—including tests, devtools, CI helpers, debuggers, adapters, build tools and production transformations—is annotated Brainfuck. The BF-in-BF interpreter must execute the mini compiler from Stage A onward; only externally installed root BF bootstrap, narrowly mechanical OS I/O, independent validation and disclosed external debug-only package/sign tools remain outside the repo. No external app-specific executable logic or opaque native template (Parts 1, 3 and 20).
- [ ] **Locked guest behavior:** source grammar, exact-byte source identity, cell/pointer/EOF/loop semantics, source-offset traces, fuel, deterministic traps and logical budgets reproduce Parts 1–2. Verify against a separate reference oracle.
- [ ] **Trustworthy binary transport:** select the session grammar before parsing; check BFIO/BHIO byte lengths, closure, frame trailer, file identities, input/output completeness, producer authority and process/host results. Neither a forged `OK` nor an expected file path proves success (Parts 2.4–2.11 and 3.7–3.10).
- [ ] **Android contract:** pin AArch64 target/Android `arm64-v8a` ABI/API, native entry/loader, threading and lifecycle, input/output observation, packaging and target test path. Do not substitute host-Linux execution for an Android proof (Parts 0.3, 7.4, 8–12).
- [ ] **Lean, scalable architecture:** first make the restricted mini compiler work. Grow multi-module apps, optional runtime facilities and optimizers as demanded by requirements and passing measurements, with no universal arbitrary APK or app-feature cap (Parts 3, 13–17, 21).
- [ ] **Real security and release evidence:** enforce source/cache provenance, path isolation, container and crypto validation, safe signing-key custody, reproducible receipts and real release authorization separately from ordinary development (Parts 11, 18–20).

### 25.2 — Immediate Stage A execution sequence

1. Complete the Part 0.3 decision sheet: device/emulator and API/ABI, loader-visible native entry and callback signature, one sealed source-acquisition/host-closure route, exact admitted commands, observable app-specific result and bounded execution policy. An unknown mandatory Android loader or guest-safety contract is a **slice-level blocker requiring adjustment**, not an instruction to halt all project development.
2. Define two admitted Brainfuck programs with distinct output and a held-out third, malformed-source and capability-rejection cases, byte-level expected native instruction differences, and source-to-output provenance checks. Specify exactly what external debug packaging can do without supplying guest algorithms.
3. Inventory the **BF-in-BF interpreter, one bounded self-interpretation/re-execution test, real BF mini compiler as its guest, BF-only test/oracle/launcher files** and inert fixtures/docs. Enforce repository-wide BF-only executable source and draft the entire Stage A slice in bulk without implementation tests, preserving draft identity.
4. Run the consolidated acceptance batch after drafting: **prove the BF-in-BF interpreter executes the actual compiler** and check exact compiler output against a separate BF-only oracle. Audit tracked executable source for non-BF languages; independently inspect generated AArch64/ELF using external tools, check source-derived instruction bytes, build/install debug APKs, observe expected Android behavior and capture logs/failures. If no target is available, report `NOT RUN` and do not claim Android usability.
5. Repair in batches, rerun mandatory tests, preserve a verified unoptimized baseline, and attempt only evidence-supported optional optimization followed by full regression. Integrate passing results and update the feature evidence tracker (Parts 14.9, 21–23).

### 25.3 — High-priority negative tests and feasibility checks

- [ ] **Source and EOF:** illegal `0x00` in annotated `.bf`, legal empty source, false source lengths, read/close failures, dangerous annotations and bracket failures before guest effects (Parts 1–2.7).
- [ ] **Framed sessions and snapshots:** malformed length/trailer, interleaved chunks, duplicate declarations/END/status, injected build-input frames in artifact-output mode, forged guest `OK`, mutated snapshots, alias paths, missing host completion and changed published bytes (Parts 2.8–2.11, 3.4–3.10).
- [ ] **ABI and provenance:** unresolvable Android imports or entry signature, runtime guest nontermination, NativeActivity thread blocking, compiler emitting identical code for different admitted source behavior, source-name lookup masquerading as compilation, and foreign hidden executable helpers (Parts 0.3, 7.4, 12).
- [ ] **UI and state:** stale handler/session identity, unsupported event/action, lost render acknowledgement, cancellation, partial external effects and false claim of atomic visual rollback (Parts 12.1–12.7).
- [ ] **Signing and publication:** malformed ZIP/APK or signing block, insufficient key custody, accidental release-key exposure, unverified final file hash, unsupported distribution-policy combination and unprovable file durability (Parts 11, 18–19).
- [ ] **Optimization and usability:** changed fuel/trap behavior, missing source maps, hidden codegen overhead, performance regression, arbitrary caps, unmanageable BF scaffolding and an optimizer required by a trivial guest when the unoptimized path is sufficient (Parts 14–17, 21–23).

### 25.4 — Issue tracking, severity and scope of blockers

Keep an ordinary engineering log of affected section/feature, expected and observed behavior, reproducer, severity, fix, test command, evidence location and remaining limitations. `CRITICAL` means a purity or correctness contradiction, unsafe authority boundary, or false success/security claim; `MAJOR` means a mandatory observable behavior, target entry, transport or feasibility proof is missing; `MINOR` means a nonblocking clarity, documentation or optional-improvement issue. Investigate and resolve issues as engineering proceeds—**no external ballot, unanimous rating or arbitrary score threshold is required**.

A critical or major unresolved issue blocks claiming acceptance for the **affected feature or release path**, not the ability to work on a safely isolated simpler slice. Unavailable emulators, signing-key safeguards and advanced Android services block their own evidence claims; they do not retroactively cancel authorization to implement and test independently supportable Stage A components. Update design contracts when technical evidence requires it, while preserving compatibility rules for already published protocols and ABIs. Do not add a document release/revision number.

### 25.5 — Publication and reporting rules

- [ ] Mark each feature separately as `DRAFTED`, `IMPLEMENTED`, `TESTED`, `OPTIMIZED` and `INTEGRATED` with real evidence; a status is never inferred from planning text.
- [ ] Keep Stage A debug outputs explicitly `DEBUG-ONLY` while external packaging or debug signing is used. Successful debug execution does not certify BF-native production signing or broader Android API support.
- [ ] Require exact tested bytes, independent binary/artifact checks, source/provenance identity and host/target result before publishing any completed artifact. Unknown closure means `UNKNOWN / NO-COMMIT`.
- [ ] Require the concrete Stage D production signing/key-custody checks and explicit release instruction before using real release keys. Stage A development permission is not release-key permission.
- [ ] Do not invent commands, hashes, tests, benchmark numbers, emulator observations or production claims. State `NOT RUN`, `UNSUPPORTED` or `BLOCKED` accurately for each missing capability.

**Execution summary:** **START STAGE A DEVELOPMENT NOW.** Build the smallest Stage A **self-hosted BF-in-BF interpreter executing the BF-authored AArch64 Android debug compiler**, with **zero non-Brainfuck executable source anywhere in the repository**, prove that two materially different annotated Brainfuck programs generate their own executable behavior, and extend the working baseline by bounded slices. Keep source human-readable, preserve eight-command purity, test in consolidated batches after each slice draft, then optimize only proven behavior. **Development does not depend on specification scores or any further start authorization.** Technical verification and real production-release safety requirements remain fully in force.
