# BF-generated Android native entry feasibility probe

> Checkpoint document. See [current status](status.md) and [physical-device evidence](windows-device-evidence.md). Results, hashes and environment paths below belong to their recorded checkpoint; use that Git checkpoint to reproduce old commands. Designs are not implementation or whole-stage acceptance.


This bounded test addresses a specific missing A01 observation: whether the selected emulator can load and execute an ARM64 NativeActivity entry. It is **not a compiler, COCK guest runtime, app-output demonstration or A01–A14 acceptance substitute**. It accepts no application source and must not be called a self-hosted mini compiler. The prior Linux files are invalid Android libraries and remain negative fixtures.

Before testing this new probe, complete and freeze `tests/android_native_entry_probe.bf`, `fixtures/android_native_entry_probe/vectors.json`, and this plan. Existing BF source gate/normalizer, wide request serializer and byte comparator are unchanged executable test dependencies. Record results with the emulator retry evidence. No foreign app source, assembler, host linker or native binary template produces the library; its entire serialization and one native instruction are actual BF output.

The program emits a fixed 1,232-byte ELF64 little-endian AArch64 ET_DYN library. Its only executable instruction is AAPCS64 `ret`, file/virtual offset `0x300`, exported as `ANativeActivity_onCreate`. It ignores the three valid OS callback arguments, holds no memory, performs no guest computation or I/O, creates no worker/callback/state, and returns promptly. It deliberately does not export or claim `COCK-NATIVE-ENTRY-v1`, context/result records, liblog or source-dependent arithmetic.

The complete intended layout is: ELF header at 0, three program headers at 64, read-only dynamic table at `0x180` (112 bytes), SysV hash at `0x200` (20), dynamic strings at `0x220` (43), two dynamic symbols at `0x250` (48), section names at `0x280` (48), native return at `0x300` (4), seven section headers at `0x310` (448). RX PT_LOAD maps file/memory `0..0x304`, alignment `0x4000`; PT_DYNAMIC points at the seven-entry dynamic table, and GNU_STACK is RW/non-executable. There is no writable executable mapping, import or relocation. SONAME is `libcockstagea.so`; dynamic strings contain the exact callback export.

After freezing the complete first-pass BF source, run BF annotation admission and normalization, direct root generation, exact byte-count/header/return comparisons with the existing BF comparator, independent readelf/disassembly inspections, and the same generator as a COCK-interpreter guest with whole output plus success-byte comparison. Group any repairs and rerun this whole probe batch. Root/guest equality alone does not prove an Android loader accepted it.

Package only the actual BF-produced library, unchanged, with the existing native-only manifest and disposable debug certificate using the disclosed external debug tools. Verify signature, native ZIP alignment, decoded manifest, executable inventory and extracted native identity. Install only on task-owned emulator-5554 after package/activity services are available. Capture exact install/launch/process/foreground/log outcomes and check the OS callback returns without native/Java error. A verified normal NativeActivity launch of this one-instruction entry would demonstrate only native loading/entry feasibility; a blank no-render activity is expected and does not prove UI or app output. Independently test Settings UI and completed boot for emulator readiness.

If ABI bridging, loader, callback, package services or framework stability fails, preserve the exact failure. Do not claim a positive test from package metadata, APK signature, an absent crash log, a boot property alone or the two deliberately invalid negative APKs. Full source admission, actual compiler, native guest runtime/ELF, BF artifact/build/test orchestration, nested real compiler and distinct printable Android app proofs remain mandatory separate gates.
