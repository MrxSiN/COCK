# Native guest implementation batch

> Checkpoint document. See [current status](status.md) and [physical-device evidence](windows-device-evidence.md). Results, hashes and environment paths below belong to their recorded checkpoint; use that Git checkpoint to reproduce old commands. Designs are not implementation or whole-stage acceptance.


Implement the restricted Android guest backend as actual annotated BF, retaining the existing compilers. This is a native ABI component, not yet the complete Stage A compiler or Android activity. Inventory: `src/android_guest_entry.bf`, `tests/android_guest_cpu_elf.bf`, `fixtures/android_guest_cpu/acceptance.json`, this plan and subsequent evidence. Finish both implementations and literal fixtures, then freeze the first pass before executing them.

The backend receives eight little-endian bytes giving the original final-dot source offset, then an already admitted normalized arithmetic source ending in one dot and physical EOF. Source admission, exact closure and the offset ledger are caller preconditions. Each plus/minus emits one real AArch64 arithmetic instruction in source order. The output is a position-independent guest entry at library virtual offset 0x1000 with a relocated log-function slot at 0x100000. It implements context/result validation, one inline byte, a 30-byte invocation-specific tag, a two-byte message, checked log return and result accounting. The normalizer and existing source gate remain separate; this backend does not independently authorize untrusted source.

Native layout: 224-byte fixed prologue; four bytes per arithmetic command; 232-byte suffix including tag and count/offset literals. Save x19–x22 and x29/x30 in a 96-byte aligned frame. Context and result layouts are the frozen 40/56-byte v1 headers. Invalid result headers return 14 without writing them. Valid result plus invalid context returns/stores 14 before app effects. Native mapped-pointer provenance remains the caller's responsibility. Successful execution reports count including dot, one cell, one output and offset all ones. Log return other than one reports 9, dot offset and zero emitted. A defensive nonprintable value reports 14 without calling the log function. Arithmetic wraps through final UXTB; no intermediate observable effects exist in this restricted subset.

The BF-only Linux CPU test wrapper places exactly the same guest bytes at virtual 0x401000 and an independent diagnostic sink at 0x400500, with a writable function slot at 0x500000. Its ET_EXEC header and syscall instructions are BF emitted, never assembled or linked by a conventional tool. Input is context 40 bytes, result 56 bytes, then an eight-byte diagnostic sink return value. Output is the attempted 30-byte tag and two-byte message when called, followed by the 56-byte result and four-byte native return. The wrapper checks one complete 104-byte Linux read; fixture stdin is a regular file. Its fixed one-page guest limit is a diagnostic limitation, not a claimed production compiler budget.

Acceptance includes source-ordered plus/minus and wrap cases, low/high printable edges, nonprintable defense, nontrivial invocation hex, sink rejection and non-one positive return, context version/size/flags/handle/zero ID/reserved, result version/size, immutable invalid result, zero effects on invalid context and exact complete native results. Independently disassemble output using LLVM, execute under an installed unmodified QEMU AArch64 CPU emulator and compare bytes with BF comparator and independent cmp. Run the real emitter through BF-in-BF on a selected application and compare its complete native output. Preserve legacy compiler regressions. A held-out arithmetic source is selected after freeze.

No authored foreign-language harness or assembler may provide runtime behavior or production bytes. External tools perform evaluator bootstrap, literal fixture materialization, counts, byte routing, checksums, disassembly and CPU emulation only. QEMU CPU/ABI evidence does not establish Android Bionic loading, actual liblog, NativeActivity, lifecycle, APK installation, complete nested self-hosting or Stage A–E completion. No optional optimization is planned. Record unavailable target checks explicitly.
