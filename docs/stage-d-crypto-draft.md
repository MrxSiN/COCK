# Stage D cryptography, v2 signing and key boundary draft

**Design only, not certified cryptography.** No key material is part of this package. All cryptographic algorithms, encoding, certificate/signature creation and APK scheme semantics in the production path must be BF-authored. External standard tools provide independent verification only; external signing remains a separately labeled disposable debug fallback.

## Fixed first scheme profile

Use SHA-256 and RSA PKCS#1 v1.5 SHA-256 algorithm ID `0x0103` in APK Signature Scheme v2, block ID `0x7109871a`, one signer and one matching certificate/public key. The selected target is API 35 direct installation. No v1/pre-24, v3 rotation, v4, AAB or store claim follows. Current [Android scheme documentation](https://source.android.com/docs/security/features/apksigning/v2) and [independent signer verifier](https://developer.android.com/tools/apksigner) are authoritative references to pin/review before implementation and actual release; URLs are not evidence this draft fetched a new policy revision.

SHA-256 uses exact specified 32-bit modular operations, message schedule/compression, big-endian block words, padding and bit length. Streaming updates preserve arbitrary binary bytes. Enforce checked input-length representation; no loss through floating-point or BF byte-counter carry. CRC-32 is ZIP's reflected polynomial `0xEDB88320`, initialization/final XOR all-ones; it is integrity metadata, not a signature/hash substitute.

RSA uses declared modulus length >=2048, exponent 65537 and validated key components. Strictly validate positive/minimal integer encodings, modulus/exponent consistency and any CRT relations used. Initial design may use full modular exponentiation; CRT/other fast paths require independent equivalence and security assessment. Arithmetic correct on toy examples is not cryptographic correctness. Independently verify the standard SHA-256 DigestInfo and EMSA-PKCS1-v1_5 `00 01 FF…FF 00 DigestInfo` encoding at exact modulus byte length; never accept short padding, alternative hash OIDs or ambiguous DER.

The test key is supplied as an independently identified controlled disposable input; BF parses the selected documented key format. No real key generation/entropy/custody claim is made. If key generation becomes part of production, it needs additional exact BF source, entropy/data boundary and security tests before use; no host key generator may become a hidden BF-native algorithm.

BF DER emission creates a profile-fixed self-signed X.509 certificate: matching SubjectPublicKeyInfo, explicit SHA256-with-RSA identifiers/parameters, canonical lengths/integers/BIT STRING, chosen nonzero serial, sealed subject/issuer/validity data and signature. Validity/identity metadata are non-secret invocation data with checked exact encodings; do not use a current timestamp implicitly in a reproducibility claim. Pin DER/PKCS#1/certificate profile and complete known-answer bytes before first crypto/signature tests. Independent certificate parsing checks signed contents and public-key equality.

## APK v2 structure and digests

The signing block is `u64 size | ID/value pairs | u64 same_size | 16-byte ASCII APK Sig Block 42`. Size excludes the first size field and includes the trailing size/magic. Each pair has checked u64 length followed by u32 ID and value. v2's value and nested signer/digest/signature/certificate fields use the exact specified length-prefixed little-endian structures. Reject duplicate signer/block IDs, mismatched algorithm lists, truncated/overflowing lengths, wrong magic/size, key/certificate mismatch and ambiguous extra signer records in this one-signer profile. Freeze the full nested-byte layout independently before source tests; a correct magic alone is insufficient.

Protected contents are the region before the signing block, central directory and EOCD; the signing block is excluded from the content digest. For digest calculation, EOCD's central-directory-offset field is treated as the signing-block start, as defined by v2. Partition each region independently into chunks of at most 1 MiB. Each chunk digest is SHA-256 of byte `A5`, u32 little-endian chunk size and exact chunk bytes. The aggregate content digest is SHA-256 of byte `5A`, u32 little-endian total chunk count and concatenated chunk digests. Checked representation/region boundaries are mandatory. The signer signs the exact v2 signed-data bytes containing that content digest and certificate/attribute records, not a bare whole-file SHA-256 substituted for v2.

Generate the final central-directory offset after signing-block insertion; EOCD/ZIP must remain consistent under final independent verification. Test region/chunk boundaries around 1 MiB, empty relevant chunks/regions under the official algorithm, EOCD comment handling, mismatched duplicate lengths, wrong adjusted offset and post-signing changes. Any future extra scheme requires separately selected API/distribution policy and cross-scheme downgrade/tamper tests.

## Independent crypto evidence and secret lifecycle

Before implementation test gate, supply independently published SHA/CRC/bigint/RSA/signature/certificate/scheme known-answer vectors with complete inputs and expected bytes. The [literal seed data](../fixtures/stage_d_full/acceptance.json) supplies a few public hashes/arithmetic cases and malformed-format requirements; it does not supply a complete RSA/APK KAT corpus or certify the planned implementation. Do not capture implementation output and relabel it an oracle. Identify independent vector sources/revisions, algorithms, target profile and full-file validator versions.

Keep four distinct states: CRYPTO-CORRECT, TEST-KEY-SIGNED, KEY-CUSTODY-REVIEWED and PRODUCTION-SIGNING-AUTHORIZED. None is inferred from another. Assess key origin/entropy, host executor and outer tape, paging/snapshot/copy/log exposure, variable-time BF arithmetic, isolation, zeroization limits, custody policy and incident response. Clearing BF cells does not prove host copies are erased or establish constant-time execution.

No real production private key may enter the implementation before the documented threat model, approved entropy/custody/security/leakage assessment, independent cross-tool/device proof and explicit release authorization required by master Parts 11.1/19.2. This drafting request does not satisfy that release gate. If BF/host constraints cannot meet the approved threat model, production signing is UNSUPPORTED while independently verified disposable-key tests may remain available. Hardware-backed custody requirements cannot be bypassed by delegating production signatures to an external program and claiming BF ownership.
