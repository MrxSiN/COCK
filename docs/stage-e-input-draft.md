## Physical file authority and BHIO

The user selects one root and manifest path as non-executable parameters. A declared physical service confines secure opened handles to that root, excludes traversal/symlink escapes/device/special files, and reports actual counts, read errors, object replacement and read/close outcomes. BF parses the manifest, selects every source/asset path, computes semantic hashes and decides order/roles; the host cannot parse JSON/build dependencies, validate BF or generate BFIO records.

The exact BHIO record is magic `BHIO`, u8 version 1, u8 kind, u64 request ID, u16 status, u64 metadata length, u64 data length, exact metadata/data and guard A5: **33+M+D bytes**, checked. Host→BF kinds are bootstrap manifest 1, stat result 3, read chunk 5, read end 6, read error 7; BF→host requests are stat 2/read 4. Initial serial-v1 permits no overlapping outstanding requests. Bootstrap request ID is zero and metadata is the selected normalized manifest path. Subsequent IDs are fresh/nonzero and bound to the same sealed set/process, not treated as authentication.

Stat success carries one u64 size. Read chunks carry `(u64 sealed_size,u64 offset)` and nonempty exact data, contiguous from zero. Read end carries `(u64 sealed_size,u64 actual_total)` and no data, even for an empty file. Read error has a declared nonzero physical status and no metadata/data; no successful END may follow it. Reject unknown versions/kinds/status, wrong/stale IDs, duplicate/missing/overlapping responses, changed size, guard/overflow/truncation and extra bytes. Error status meaning remains master 3.7's 1–5 physical vocabulary, not BF guest status numbering.

Only the bound trusted BF assembler stdout may multiplex complete BHIO requests and BFIO input frames by distinct magic/checked lengths. Guest application stdout is isolated raw data. The router must service requests independently of downstream compiler backpressure using bounded queues/spillable staging; no cyclic pipe waits. Test streams larger than every pipe/window and repeated chunks. Current Tritium buffering and absent verified adapter do **not** establish timely flush/full duplex; unavailable physical channel capability blocks this mode. No conventional semantic assembler may be substituted.

The first manifest is read completely before BF discovers later paths. Secure copies provide an exact verified materialized set; they do not imply a simultaneous project-wide snapshot. Record actual OS atomic snapshot evidence separately if present. Detect observed replacement/mutation/count/hash/close disagreements, abort the whole collection and restart; no mixing old and new bytes. Compilation reads sealed copies only.

## Strict configuration and paths

Parse full valid UTF-8 JSON with checked nonnegative decimal integer tokens only for integer fields; reject sign/fraction/exponent, booleans/null-as-integer, overflow and lossy conversion. Decode escapes and surrogate pairs before duplicate key/ID/path/capability checks; reject lone surrogates, overlong/invalid UTF-8 and unknown keys at every level. Required v1 fields and types are exactly master 3.3/3.5: config_version=1, application_id, supported target_abi, positive checked min/target SDK with min<=target, nonempty modules, recognized resolving entrypoints and unique requested_capabilities. Optional assets/features/optimization_policy retain their frozen meanings, not executable hooks.

Module IDs follow `[A-Za-z_][A-Za-z0-9_]*`, source paths are normalized relative paths and profile is COCK. Event modules require unique nonzero u32 handler_id and u64 state_schema; main modules have neither, and state_schema alone is invalid. Reject unresolved/wrong-role entrypoints, cycles, duplicate/self/missing dependencies and nonempty named imports/exports/direct calls. Topological order uses bytewise ASCII module-ID tie-breaks. Dependencies order builds/provenance, never tape sharing or implicit calls. Capability requirements/features must be unique registered requested IDs with verified target/runtime support.

Paths are relative UTF-8 NFC bytes with one canonical separator policy. Reject absolute paths, `..`, NUL, empty/ambiguous components, target-host case/normalization collisions, escape aliases and unsupported normalization/host equivalences. Do not silently translate or lowercase. A first implementation may explicitly reject unsupported non-ASCII normalization cases until a complete BF NFC implementation is independently tested; it cannot advertise full Unicode path support. OS confinement is defense in depth, not the BF semantic path algorithm.

Canonical manifest AST uses master 3.11's typed S/U/A/O binary serialization, sorted decoded object keys and specified set-like arrays; preserve explicitly ordered arrays. Compute BF SHA-256 content-set identity using `COCK-SNAPSHOT`+00 domain, canonical AST, ordered role/path/count/exact source/asset bytes and all eleven fixed-position profile/config/frame/input/host/app/native/UI/producer/target/policy identifiers. Raw JSON/source hashes and routing invocation identity remain distinct. Unknown output-affecting identity disables cache/reproducibility claims; optional caching is not required to compile. Whitespace/key-order equivalence is semantic interpretation, not equal raw hashes.

## Build-input and output sessions

Build-input declarations use kind 01 payload `u8 role | u64 file_id | u64 declared_size | u64 path_len | path`, exactly 25+path_len. First/sole manifest has role 1, ID 1; remaining sources role 2/assets role 3 sort by unsigned canonical path bytes and IDs 2..n. Declared set exactly matches the validated plan. No source/asset role alias or surplus file is accepted. In declaration order receive contiguous nonempty chunks, one END per file including empty files, then one trusted phase-5 terminal status. All sealed/stat/declared/received/END counts must agree. Full source preflight and independent host closure precede any application compilation/execution.

Artifact-output declarations have the **different** payload `u64 file_id | u64 path_len | path`, not an input-role prefix. Canonical paths/IDs precede noninterleaved file chunks/ENDs and exactly one terminal result, with no trailing bytes. Validate envelope, selected session and independent producer/physical completion as three separate verdicts. A good A5, correlation ID or guest-printed OK cannot authorize completion. Missing declaration/END/status, forged producer, extra bytes, process failure and uncertain close remain NO-COMMIT.

BF chooses output names, complete set and publication decision; the physical service stages/writes/syncs/renames only the requested paths. Receipt binds invocation, sealed input, BF producer identity, actual completion, exact received count/session, write/close, validator result and staged/published hashes. Only independently validated exact bytes may publish. Preserve prior output on interruption; do not claim multi-file atomicity or crash durability without actual filesystem evidence. Unknown published identity/sync/close remains UNKNOWN/NO-COMMIT, even after a successful rename. Secret material is never included in these receipts.
