## Event and action validation

`ui.touch` admits touch-down event type 1 with exactly eight event-data bytes: two little-endian u32 physical-window pixel coordinates `(x,y)`, origin top-left. Copy one verified primary ACTION_DOWN from a live input window; accept only finite nonnegative coordinates, floor them, check integer overflow and surface bounds, and reject invalid/unavailable/multitouch/other event kinds explicitly. No density scaling or substitution of zero for invalid values. Complete the platform input-queue acknowledgement on its required thread regardless of guest success; record handled/rejected independently.

`ui.text` admits surface-ready type 2 with empty event data and text-replace action type 1. Text body is u16 version=1, u16 reserved=0, u32 text_len, then exact printable ASCII bytes 20..7E; checked body size 8+text_len. Empty clears the label. Reject unknown version/reserved/length/nonprintable/budget/capability. Surface-ready comes from a verified live owned window transition, not a fake startup text log. Surface generation is trusted dispatcher metadata bound to the invocation, not an invented extra v1 payload field.

## BF-generated renderer ownership

The BF native gateway owns lifecycle, window/input queue, generation and valid owner-thread transitions. BF-generated renderer code locks a supported native window buffer through declared NDK physical APIs, checks actual width/height/stride/pixel format and checked offsets, paints background and rasterizes the label from validated non-executable glyph data, then posts/unlocks and reports actual outcome. No host renderer, precompiled app-specific UI library or copied native template may provide drawing logic.

Proposed glyph asset is fixed 8x8 bitmap rows for printable ASCII, 95 glyphs/760 bytes, with exact dimensions/bit order independently specified and authored before the UI source freeze. It is NOT CREATED. Label origin/margins, palette, scaling and overflow/clip policy are explicit per-capability data; initial design uses origin (8,8), scale 1 and rejects a label that cannot fit the selected single-line drawable bounds before applying effects. Zero-length clears. Validate background/glyph bounds and buffer stride without assuming tightly packed pixels. Unsupported surface formats fail rather than corrupt memory. Font legibility/appearance is device evidence, not established by this proposal.

Recheck surface generation immediately before lock/draw/post and before logical commit. Cancel old work after replacement. Never treat a successful pixel write as proof of post/visible presentation; record window API acknowledgement and independently captured visible output separately. A lost acknowledgement or process death after drawing leaves visuals UNKNOWN and old state authoritative until safe redraw; do not claim pixel rollback. Keep callbacks responsive and prove worker/library/window lifetime and correct platform-thread ownership on the selected device.

## Two materially different illustrative apps

The inert [counter manifest](../fixtures/stage_e_full/counter.build.json) proposes one event module, schema 1, no main module, and a glyph asset. Its BF source will interpret empty state as u64 zero, surface-ready renders its committed decimal count without increment, and valid touch increments modulo 2^64 and emits matching decimal label/replacement state. It must parse the full event frame and create the complete action itself; the native gateway cannot perform counter semantics. Test zero, one, repeated touches, maximum wrap, cancelled redraw and window recreation from committed state.

The inert [coordinate manifest](../fixtures/stage_e_full/coordinates.build.json) proposes a separate main conversion module plus a schema-2 coordinate handler, different app/package/module/resource/asset set and dependency graph. The main module reads two raw bytes (EOF-zero), then emits them in reverse order, on its own zeroed tape; additional input is unconsumed. It cannot share tape or implicitly call the handler. The handler renders READY on initial empty-state surface-ready and ODD/EVEN on touch based on x parity, returning exactly eight state bytes `(u32 x,u32 y)` little endian; nonempty state rerenders parity of the last committed x. Reject other nonempty state lengths. Main input `00FF` independently expects `FF00`, consumed=2; input empty expects `0000`, consumed=0. No gateway source-name/output lookup is allowed.

The coordinate app's BF sources now exist and execute their stated main/event behavior; the counter BF source and both projects' asset bytes remain missing. The manifests are illustrative schema data, not complete runnable Android projects. BF must derive code, app metadata, actual assets/resources and layout from the supplied input plan. Tests need both full builds through the same accepted compiler plus new held-out app/module/source configuration selected after actual source freeze. Distinct package names alone do not prove E07; compare real generated instruction regions, event/state behavior, resource/entry inventory and actual visible device results. Multiple screens/rich layouts require separately registered capabilities; these examples claim only the current single-label UI profile.
